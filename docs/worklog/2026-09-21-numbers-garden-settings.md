# 箱庭の「動かす側の数」を、利用者が変えられる場所へ（S5b-3）

計画書 `docs/plans/shared-crate-plan.md` の段階 **S5b-3**。一覧は `docs/numbers.md` の §2
（Garden の Rust）のうち分類 **(c)**。手本は `docs/worklog/2026-09-20-numbers-shared-crates.md`
（S5b-1）と `docs/worklog/2026-09-21-numbers-battle.md`（S5b-2）。
着手時は main と同じ `835b992`、作業は worktree の `shared-crate`。

**著者が決めていたこと**（2026-09-20）: 分類案のとおり。出どころ不明の数は「不明」と書いたまま
移す。**既定値は 1 つも動かさない。**

この段階には、数を移すことのほかに 2 つ宿題が付いていた。**S6 が見つけた穴**——生き物の VM は
予算も `frame_time` も rubevy の既定のままで、ゲームはどこでも何も言っていない——と、**S7 が
残した食い違い**——窓のチェックの上限フレーム数が、その 200,000 を数として式に入れている。

### 箱庭は同じバイナリでも 2 回同じ文を出さない

先に確かめておく必要があったことが 1 つある。`Dice` は時計から種を取る
（`platform::clock_seed`）ので、**同じバイナリを 2 回走らせても行の中の数は全部違う**。
前の版を 2 回回して確かめた: 生の `selftest:` 行の `diff` は 20 行以上出るが、
`tools/fixedlines.sh` の集合は完全に同じ。だから前後の比較はこの段階でも**行の集合**でやる
（`docs/verification/selftest-lines.md` が言っているとおり）。Battle の「当たりの数が
走行ごとに 3 倍振れる」と同じ話で、原因が違うだけである。

## 1. どこへ置いたか — 7 つの Resource と、店を読む場所

S5b-1 は共有 crate の口を `read_from(|key| …)` のクロージャにし、店を読むのを
`PanelSettingsPlugin`（`PreStartup`）に任せた。S5b-2 は Battle の `Look` を **`main` の中で**
読んだ——窓の大きさは `App` を建てる前に要るからである。

箱庭は S5b-2 側に倣った。理由は 1 つではなく 4 つある: 窓の大きさ、カメラの既定距離、
**畑の広さ**（`make_look` が `Startup` で地面のメッシュを作る）、そして**旗の既定**
（`--headless` の引数解析は `App` を建てる前）。`PreStartup` はどれにも間に合わない。

| Resource | 何の数か | 鍵の接頭辞 | 件数 |
|---|---|---|---|
| `Place` | 畑の広さ、壁の余白、押し分けの回数 | `field_*` / `wall_margin` / `separate_passes` | 4 |
| `Furniture` | 新しい庭の家具と、それを置く間隔 | `start_*` / `plant_min` / `plant_max` | 18 |
| `Light` | 夜と昼の光、影、夜明けの位相 | `light_*` | 17 |
| `Scenery` | 地平線・空のドーム・霧・縁の木 | `horizon_*` / `sky_*` / `fog_*` / `edge_*` | 17 |
| `Picture` | 窓、地面の色、空腹バー、模型の倍率、アニメ | `window_*` / `look_*` | 19 |
| `Eye` | 3D オービットのカメラとクリック | `eye_*` | 13 |
| `Budgets` | 2 本の VM の予算と `frame_time`、待ちと熱 | `script_*` / `world_script_*` ほか | 7 |
| 旗の既定 | `main` が直接読む | `headless_seconds` / `shot_file` / `shot_seconds` / `at_seconds` / `save_file` | 5 |

鍵の名前で 3 つ決めたことがある。

**`script_budget` / `script_frame_time_ms` は Battle と同じ鍵にした。** 2 本のゲームで
「スクリプトの VM が 1 フレームに使ってよい量」を別の名前で呼ぶ理由が無い。世界の VM は
箱庭にしか無いので `world_script_budget` / `world_script_frame_time_ms`。
`window_width` / `window_height` も Battle と同じ鍵である。

**カメラは `camera_*` ではなく `eye_*` にした。** `camera_*` は `games_shell::CameraControls`
——共有 crate のパン・ズーム 2D カメラ——が既に握っている鍵で、箱庭はその `CameraPlugin` を
足していないので実際の衝突は起きない。それでも、`garden.settings.txt` を開いた人が
「`camera_zoom_per_notch` は効くのか」と迷う状態を作らないほうがいい。箱庭のカメラは「眼」である。

**色は数として出した。** S5b-1 は「色を文字列から読むには構文解析が要る」ので `Settings` に
出さなかった。夜の空だけは出した（`light_night_sky_r` / `_g` / `_b`）——**測った 3 つ組の 1 つ**で、
著者が動かすかもしれない数だからで、3 つの数に構文解析は要らない。地面の色と霧の色も同じ形で
出した。バーの色や太陽の色のような「ただの色」は Resource のフィールドのままにした。

### `const` は既定値の名前としてだけ残した

`Place::default()` は `FIELD_W` を読み、`FIELD_W` の rustdoc が出どころを言う。S5b-1・S5b-2 と
同じ形である。**新しく決めた数は 0**。無名だった数（縁の木の散らし方、起動時の霧、初期配置の
5 つの間隔、オービットの回転感度……）には名前を付けたが、値は 1 つも動かしていない。

### `const` でなくなったものが 3 つ

* **`HALF_W` / `HALF_D`**（`FIELD_W / 2.0`）→ `Place::half_w()` / `half_d()`。
* **`MIDNIGHT`**（`(0.75 - DAWN_OFFSET) * DAY_LENGTH`）→ `fn midnight(&Light)`。
  `--at midnight` が指す時刻は `light_dawn_offset` から導く。**導出された数を設定にすると
  2 つの数が食い違える**ので、関数にするのが正しい（S5b-1 が行番号の桁の色を `kinds[3]` を
  読む 1 行にしたのと同じ判断）。
* **`MEADOW_AT`**（`Vec2::new(-HALF_W + 6.0, HALF_D - 6.0)`）→ `fn meadow_at(&Place)`。
  畑を広げると判定の隅も一緒に動く。

### `Look` が模型の倍率を持ち運ぶ

`spawn_plant` / `spawn_tree` / `spawn_rock` / `spawn_creature` は `Option<&Look>` を取り、
倍率を使うのは `if let Some(look)` の中だけである——つまり**「`Look` がある」と「倍率が要る」は
同じ集合**。そこで倍率 6 つとアニメの 2 つは `make_look` が `Picture` から `Look` に複写する形に
した。4 つのヘルパの引数も、ヘッドレスが倍率を 1 度も見ないことも、そのままである。

代償は 1 つ: **走行中に `Picture` を書き換えても `Look` は変わらない**（起動時の 1 回の代入
なので）。設定は起動時に読むものなので今は害が無いが、気づいた点に挙げた。

捨てた案: 4 つのヘルパに `&Picture` を足す。呼び出し側 8 か所が長くなるだけで、
ヘッドレスに「使わない引数」を運ばせることになる。

### `draw_hud` が Bevy の上限に当たった

`draw_hud` は既に 15 個で、空腹バーに `Picture` を、夜のスライダに `Light` を渡すと 17 個になる。
S5b-2 が Battle の `selftest` にやったのと同じ手で `HudLook`（`SystemParam`）に 2 つをまとめた。
`window_selftest` も 16 個ちょうどなので、上限フレーム数は**そこで読まずに `WindowTest` に
持たせた**（§3）。

## 2. 店をヘッドレスでも読むようにした

G6b が `games_shell::remembered` を窓の腕の中に置いたのは、店にあったのが 2 つ——ガイドの言語と
夜のスライダ——で、どちらもヘッドレスには無いものだったからである。S5b-3 で店に入るものは
**畑の広さ・家具・2 本の VM の予算・旗の既定**で、これは全部ヘッドレスの走行のものでもある。
だから `main` の頭に上げた。Battle が S5b-2 で同じ場所に動かしたのと同じ理由である。

ヘッドレスで店を読むことの安全性は `Settings::load` が読むだけであることに拠る——
書き込むのは `set`（夜のスライダとガイドのボタン）だけで、どちらも窓にしかない。
**`garden.settings.txt` を持たないヘッドレスの走行は、前と 1 バイトも違わない。**

## 3. `SCHEDULER_FRAMES` を設定から計算する（S7 の宿題）

S7 はこう書いていた: 上限は `2 + ceil(budget ÷ 1 フレームが買う命令数)` で、`budget` は
「rubevy の既定 200,000」、1 フレームが買うのは S6 の実測 45,600。`2 + ceil(200000/45600) = 7`。

その 200,000 が `script_budget` で動かせるようになった以上、式に数として入っていては困る——
10 倍の予算をもらった走行が、10 分の 1 の時間で判定されることになる。

```rust
pub fn scheduler_frames(budgets: &crate::Budgets) -> u32 {
    STRUCTURAL_FRAMES + (budgets.creature as f32 / INSTRUCTIONS_A_FRAME_BUYS).ceil() as u32
}
```

2 つの部品はそれぞれの出どころを持ったままにした。`STRUCTURAL_FRAMES = 2` は S6 が測った
「構造で縮められない 2 フレーム」、`INSTRUCTIONS_A_FRAME_BUYS = 45_600.0` は S6 の実測
（5.7 命令/µs × 8,000 µs）で、**これは (d) の判定の側の数**——この機械の壁時計についての数なので
設定にしない。判定が「自分が走っている機械の速さ」を知っているのは構わない。

`window_selftest` は引数 16 個ちょうどなので、`Budgets` をそこで読むことはできない。
`WindowTest::after(3.0, &budgets)` が起動時に 1 回計算して持つ形にした。

単体テスト `a_bigger_budget_buys_the_checks_more_frames`: 既定で 7（今までと同じ数で、
`docs/verification/selftest-lines.md` を取ったときの数）、予算 1,000,000 で 24、予算 1 でも
構造の 2 フレームは残って 3。

## 4. 生き物の VM を、上限の庭に座って測った（S6 の宿題）

世界の VM の 45,000 は「上限の庭（90 株・24 匹）で 392 フレーム測り、最悪 25,837 命令の 1.74 倍」
という出どころを持っている。生き物の VM には何も無い。**同じやり方で測った。**

### 測り方

S5b-3 で畑も家具も設定になったので、**W3 のように「rig した build」を作る必要が無くなった**——
`garden.settings.txt` に 3 行書けば上限の庭になる:

```text
start_plants=130      # world.rb の plant_cap は 90。上から近づける
start_beetles=14
start_rabbits=10      # 合わせて 24 = world.rb の pop_max
```

測る側だけは一時の仕掛けが要った。`GARDEN_MEASURE=1` のときだけ動く 1 システムを足し、
毎フレーム `ScriptWorld::last_frame()`（rubevy の `FrameStats`）の `instructions` と `time_ns` を、
そのフレームの株の数・匹数と一緒に 1 行印字する。**これはコミットに入っていない**
（測った後に外した。S5b-2 が弾の速さを測ったときと同じ扱い）。

`--headless 60` を 3 回、機械は idle 99%。10,749 フレームのうち、**株 90 以上かつ 24 匹**の
フレームが 1,533。

### 測った分布（上限の庭、3 走行合計）

| | 中央値 | 99 パーセンタイル | 最大 |
|---|---|---|---|
| 生き物 VM の命令数/フレーム | 362 | 3,954 | **23,686** |
| 生き物 VM の tick | 70 µs | 760 µs | 1.72 ms |
| （参考）世界 VM の命令数/フレーム | 26,103 | 28,007 | 28,142 |
| （参考）世界 VM の tick | 2.16 ms | 4.02 ms | 4.79 ms |

**最大 23,686 は最初のフレームで、3 走行とも 1 命令まで同じ数だった。** 24 体のスクリプトが
一斉に最初の 1 パスを走る、1 回きりのフレームである。それを除く（最初の 1 秒を捨てる）と:

| | 中央値 | 99 パーセンタイル | 最大 |
|---|---|---|---|
| 生き物 VM の命令数/フレーム | 368 | 3,460 | **4,955** |
| 生き物 VM の tick | 73 µs | 536 µs | 1.72 ms |

### 測り方の検算 — 世界の VM が W3 と同じ数を出すか

この仕掛けが信用できるかは、**出どころの分かっている数を測り直して合うか**で見られる。
上の「株 90 以上」は `start_plants=130` から始めているので、規則の上限（90）を**超えた**庭の
フレームも入っている（草の上限は新しい芽を止めるだけで、既にある株を減らさない）。
そこで株が 88〜93 のフレームだけに絞ると、世界の VM は:

| | 中央値 | 99 パーセンタイル | 最大 |
|---|---|---|---|
| S5b-3 の実測（416 フレーム） | 24,982 | 25,643 | 25,659 |
| **W3 の記録（2026-09-17、392 フレーム）** | **24,670** | **25,782** | **25,837** |

**3 つとも 1〜2% 以内で一致する。** 同じ帯での生き物の VM は
命令数 中央値 432 / 99 パーセンタイル 2,835 / 最大 3,954、tick 77 µs / 513 µs / 758 µs で、
上の「株 90 以上」の表より**少し安い**——つまり §4 の数は規則の上限より少し太った庭の数で、
**安全側に寄っている**。

* **既定の 200,000 には一度も近づかない。** いちばん高いフレーム（起動時）でその **12%**、
  定常の最悪フレームで **2.5%**。`carried_reflect` / `carried_in_tick` は 10,749 フレーム全部で 0
  ——予算が足りずに次のフレームへ回された問いは 1 つも無い。
* **`frame_time` の 8 ms にも近づかない。** 生き物 VM の tick の最悪は 1.72 ms（21%）。
* **2 本の VM の tick を足しても**、上限の庭の定常フレームで中央値 2.25 ms・99 パーセンタイル
  4.33 ms・最大 5.01 ms。60 Hz の 1 フレーム 16.7 ms に対して **13% / 26% / 30%**。
  2 本の予算が独立なので理論上の最悪は 8 + 8 = 16 ms（1 フレーム丸ごと）だが、実測はその 3 分の 1 である。
* 上限の庭での生き物 VM の速さは **6.85 命令/µs**。S6 が `frame_time` を 300 µs に絞って測った
  5.7 命令/µs と同じ桁で、`INSTRUCTIONS_A_FRAME_BUYS` 45,600 の根拠は今も立っている
  （6.85 で計算すると 54,800 になり、上限フレーム数は 2 + 4 = 6。7 はそれより緩い側）。

### 導ける案（**実装していない。著者の判断待ち**）

世界の VM の理屈をそのまま当てると:

| 案 | 式 | 数 | 何が起きるか |
|---|---|---|---|
| A. 起動フレームを含む最悪の 1.74 倍 | 1.74 × 23,686 | **≈ 41,000** | 今の 200,000 の約 5 分の 1。起動フレームも定常も絞られない。世界の VM の 45,000 とほぼ同じ数になるのが面白い |
| B. 定常の最悪の 1.74 倍 | 1.74 × 4,955 | **≈ 8,600** | 定常には十分（99 パーセンタイルの 2.5 倍）だが、**起動フレームが 3 フレームに割れる**。24 体のスクリプトが走り出すのが 1 フレーム遅れる |
| C. 据え置き | — | 200,000 | 実測の最悪の 8.4 倍。「暴走した 1 本のスクリプトを 1 フレーム以内に止める」という予算本来の仕事はしているが、余裕の倍率に根拠が無い |

`frame_time` については、**2 本合わせて 1 フレームの 30% しか使っていない**という実測が
そのまま材料になる。8 ms を据え置くなら「2 本で 16 ms、60 Hz の 1 フレーム丸ごと」が理屈の上の
最悪として残り、絞るなら測った 1.72 ms（生き物）と 4.79 ms（世界）の上に余裕を取ることになる。

**どれも実装していない。** 世界の 45,000 が著者の判断で決まった数であるように、これも数字を
見てから決める種類の数である。**既定値は 1 つも動かしていない。**

なお一覧（`docs/numbers.md` §2.9）の 200,000 の出どころは、この測定の後も
**「rubevy の既定を引き継いだ。rubevy 側の出どころは不明」**のままにしてある——測ったのは
「今の値で足りている」ことであって、「200,000 という数がどこから来たか」ではない。
測った分布をここに書いて、出どころの欄からここを指した。

ほかに `cargo build --workspace --all-targets` **警告 0**、`cargo test --workspace`
**53 → 56 通過**（足した 3 本は §3 の上限フレーム数、「店が 7 つの Resource に届くこと」、

**+37,693（+0.105%）と ±0**。箱庭が伸びたのは 7 つの `impl Default` と `read_from` と
70 個の鍵の文字列、Battle が 1 バイトも動かないのは触っていないからである。

### 設定が効くこと — 種類ごとに 1 つ

「設定にした」と「設定が効いている」は別の主張である（S5b-1 の教訓）。本物の走行で見た:

**畑（`Place`）**: `field_width=80` を置くと、判定の 3 つの仕込みが全部一緒に動く——
断食甲虫 `(-17.0, -12.0)` → `(-37.0, -12.0)`、プローブ `(17.0, 12.0)` → `(37.0, 12.0)`、
つがいの隅 `(-14.0, 9.0)` → `(-34.0, 9.0)`。**`meadow_at` が `const` でなくなったことの証拠**でもある。

**家具（`Furniture`）**: `start_plants=9, start_trees=1` で、`world.rb` が最初のフレームに
印字する「7 trees, and 30 plants to start with」が「1 trees, and 12 plants to start with」になる
（12 は 9 + 判定の仕込み 3 つ）。

**生き物 VM の予算（`Budgets`）**: `script_budget=10` で、甲虫の `insn/frame` が 17 → 6〜7。

**世界 VM の予算**: `world_script_budget=300` で、世界 VM が 13,408 insn/frame → 309 になり、
HUD の行が「waiting for a component read the tick ran out of budget before answering」に変わる
——予算が実際に噛んでいる姿である。

**旗の既定**: `headless_seconds=4` で `--headless`（数なし）が **4.04 秒**、`--headless 8` は
**8.03 秒**——**旗が店に勝つ**。

**光（`Light`）**: これは**測った数**なので、実際に測り直した。docker の窓で
`--shot night.png 6 --at midnight` を 2 回——既定と、`light_moon_lux=3000` +
`light_night_ambient=600`——撮り、G6b と同じ「パネルが覆わない帯」（画像の下 1/3、横は中央半分）の
平均輝度を取った:

| | 地面の帯の平均輝度 |
|---|---|
| 既定 | **43.31 / 255** |
| `light_moon_lux=3000`, `light_night_ambient=600` | **75.71 / 255** |

既定の 43.31 は **G6b が 2026-09-18 に記録した 44/255 とほぼ同じ数**である（帯の取り方が
完全に同じではないので 0.7 ずれている）。つまりこの設定は効いていて、**既定は測ったときの
庭のままである**——1 つの走行で両方が言える。

**見た目（`Picture`）**: 同じ `--shot` で `window_width=1280` / `window_height=720` を置くと、
出てくる PNG が **1600×900 → 1280×720** になる。窓の大きさは `App` を建てる前に要る数なので、
これは店を `main` の頭で読んでいることの確認でもある。

**眼（`Eye`）**: `eye_distance=20` を置いて窓のチェックを回すと、カメラのログの 1 行目が
`camera: yaw 0.000 pitch 0.850 distance 18.18` で、最初のホイールが
`distance 20.00 -> 18.18`——**既定の 42 ではなく 20 から始まっている**。
ついでに、その走行でも 44 行 FAIL 0 だった（ホイールの判定は比で書いてあるので、
カメラの既定距離が変わっても通る）。

**そのほか**は単体テスト 2 本。`a_line_in_the_store_reaches_the_garden` が 7 つの Resource に
1 鍵ずつ届くことと、**書いていない鍵が既定のままであること**（古い店との互換の全部）を見る。
`the_store_names_the_save_and_the_flag_beats_it` がセーブのファイル名。

**確かめていないもの**: `save_file` が実際に F5 の書き先を変えるところは動かしていない。
F5 を押す道が窓にしか無く、箱庭の窓のチェックは「リポジトリに書いてしまうので Save は
わざと入れていない」（`window.rs`）。単体テストが見ているのは「どの名前を選ぶか」までである。

### セーブと設定ファイルの互換

**鍵を 1 つも変えていない。** `lang`・`night`・`editor_*`・`vm_*`・`hud_*`・`guide_*` は
そのまま読める。`Settings::load` は書いていない鍵について何もしないので、古い
`garden.settings.txt` は前と同じ意味を持つ。`localStorage` の接頭辞 `garden:` も
`garden.save.json` という既定のファイル名も変えていない。

ブラウザでは、`lang=ja` と `night=1.30` だけの古い店を `addInitScript` でページが動き出す前に
入れて `?selftest` を回した（§6）。

## 8. 気づいた点

1. **一覧に無い直書きの数が箱庭にまだある。** 昼の色の傾き（`sky_colors` の昼側 6 つ、
   太陽の色、月の色、環境光の 2 色、空の勾配の押し上げ `t × 1.25 − 0.1`）と、新しい庭の
   最初の草の大きさの下限 0.3（`plant_min` 0.18 とは別の数）。**夜の 3 つは測ってあって一覧に
   あるのに、昼の同じ形の数は 1 つも無い**——S5a の網が `const` と名前のある数に寄っていて、
   昼の色は全部関数の途中に書かれているためである。S5b-1・S5b-2 と同じ理由で移していない
   （段階が自分で範囲を広げない）。一覧には §2.2 / §2.3 / §2.5 の 1 行ずつとして載せた。
   属する話: 一覧の抜け。
2. **`Picture` の模型の倍率は `Look` が起動時に複写する。** 走行中に `Picture` を書き換えても
   `Look` は変わらない。設定は起動時に読むものなので今は害が無いが、将来「パネルから倍率を
   動かす」ような口を足すなら、そこが効かない場所になる。属する話: 箱庭（設計）。
3. **`world.rb` の `plant_max` 1.4 と Rust の `plant_max` は、今も 2 つの数である。**
   繋いでいない——Rust のは「庭を建てるときの株の大きさ」、Ruby のは「成長が止まる上限」で、
   `main.rs` がその区別を書いている。同じ値であるのは今日のことで、片方を動かした人は
   「育ちきらない草」か「最初から育ちきった草」を見る。属する話: (b) と (c) の境目（S5b-4）。
4. **`save_file` が実際に F5 の書き先を変えるところは動かしていない。** F5 を押す道が窓にしか
   なく、箱庭の窓のチェックは「リポジトリに書いてしまうので Save はわざと入れていない」
   （`window.rs`）。単体テストが見ているのは「どの名前を選ぶか」までである。
   属する話: 確認の穴（S5b-5 が (d) を見るときに、Save を安全に押す道があるかを考える価値はある）。
5. **`draw_hud` と `window_selftest` が Bevy の引数の上限 16 に張り付いている。**
   S5b-3 は `HudLook`（`SystemParam`）を足して前者の天井を上げ、後者には上限フレーム数を
   `WindowTest` のフィールドとして持たせて回避した。3 本目や S5b-5 が何かを足すなら、
   また同じことをすることになる。属する話: 箱庭（判定の形）／本の素材。
6. **`INSTRUCTIONS_A_FRAME_BUYS` 45,600 は、今回の実測から見ると安全側（緩い側）だった。**
   S6 は `frame_time` を 300 µs に絞って 5.7 命令/µs を測ったが、上限の庭の普通の走行では
   **6.85 命令/µs** で、1 フレーム 8 ms が買うのは 54,800 になる。それで割ると上限は
   2 + 4 = 6 フレームで、今の 7 はそれより 1 フレーム緩い。**直していない**——45,600 は S6 が
   測った数で、数を動かすなら測り直した条件（絞っていない `frame_time` での 6.85）を
   `INSTRUCTIONS_A_FRAME_BUYS` の出どころとして書き直すことになり、それは判定の側の (d) の
   仕事（S5b-5）である。属する話: (d) の閾値。
7. **rubevy の `FrameStats` に「そのフレームに走ったタスクの数」が無い。** 1 フレームの
   命令数と tick は分かるが、「1 タスクあたりいくら」は言えない——生き物の VM の予算を
   「1 体あたり」で考えたいときに要る数である。S5b-2 が `ScriptWorld::budget` に
   タスクごとの持ち分が無いと書いたのと同じ場所の話。属する話: rubevy（API）。
8. **`docs/web.md` の wasm の大きさの表がまた 1 段ずれた**（S5b-1 +0.12% / +0.20%、
   S5b-2 +0.18% / +0.002%、S5b-3 +0.105% / ±0）。S4 が取り直したきりで、段階ごとに直す
   約束にはなっていない。属する話: 文書と実物のずれ。
9. **設定になったことで、測るための「rig した build」が要らなくなった。** W3 は上限の庭を
   測るために build を作り替えたが、S5b-3 の測定は `garden.settings.txt` に 3 行である
   （`start_plants=130`、`start_beetles=14`、`start_rabbits=10`）。**数を利用者が変えられる
   場所に置くと、測る人にとっても変えられる**——これは本（移植の章）の素材になる。
   属する話: 本の素材。
10. **箱庭は同じバイナリでも 2 回同じ文を出さない。** `Dice` が時計から種を取るので、
    生の `selftest:` 行の `diff` は前後で必ず 20 行以上出る。`tools/fixedlines.sh` の
    「行の集合」で比べる約束が、Battle の当たりの数だけでなく箱庭にも要る理由である。
    属する話: 確認の作法／本の素材。

# F3a — 地図の大きさは利用者のもの（`data.rb` へ）、上限は本当に壊れる所だけ

2026-09-21。計画書 `docs/plans/factory-plan.md` §6 の F3a の行。
著者「サイズは自由に変えられるようにしたい」（`map_tiles` の既定値をどうするかを聞いたことへの答え。
**既定値を決める前に、自由に変えられる形が先**）。

着手前: `factory` ブランチ `1b2bf16`（F3 と S10 まで）。`cargo test --workspace` **106 passed**、
`cargo build --workspace --all-targets` 警告 0。

## 0. 何が今そうなっているか（手を付ける前に読んだ）

* `factory.settings.txt` の `map_tiles`（既定 32、**正方形**）を `main()` が読み、
  `Ore::smallest_map(ore_patch_radius)` で**黙って `.max`** して `Map { tiles: u32 }` を作る
  （`main.rs:325-330`）。ページには設定を渡す口が無いので、**ブラウザでは 32 以外にできない**。
* `Grid`・`Lanes`・`Ore`・`Flow`・`TilemapChunk` は全部 `tiles * tiles`、つまり正方形前提
  （`grid.rs:192,199,203,223`、`belts.rs:190`、`draw.rs:185-201`）。
* `ore_patch_radius` が設定に残っていた理由は 1 つだけ（`numbers.md` §9.2 の最後、
  `docs/factory.md` の「Why `ore_patch_radius` did not go into `data.rb`」）:
  **下限が `main()` で要り、そこにまだ VM が無い**。地図が data stage の後に組まれるなら理由は消える。
* カメラは `main()` で `CameraPlugin::showing(half_height).with(CameraControls { bounds: 地図 })`。
  `size_the_map_for_the_stress_run` が `--stress` のときだけ `bounds` を書き直している
  （= **地図が `Startup` で変わる形は既にある**）。

## 1. 語と綴り — 決めたことと理由

**`map :world, size: [32, 32]`。** 8 語目。

* **なぜ新しい語か。** F2 が 6 語に分けた理由（`data.rs` の見出し「Why eight words and not three」）
  に照らして、地図の大きさは `belt` のものでも `ore` のものでもない。`ore` に `map_size:` を足すのは
  「かまどの `capacity:`」の形である。
* **なぜ `size:` で `tiles:` ではないか。** `machine :assembler, size: [2, 2]` が既に
  「**タイル何枚ぶん、横と縦**」の意味でこの綴りを使っている。地図の `size:` も同じ意味の同じ単位である。
  F3 が `inserter` に `miner` の `seconds_per_item:` をそのまま使った判断（「意味が同じなら綴りも同じ」）
  と同じ原則。計画書の例は `tiles:` だったが、**同じ意味に 2 つ目の綴りを作らない**ほうを採った。
* **名前 `:world`。** `belt :conveyor` / `chest :crate` と同じくラベル（`ore` だけが例外で、
  名前がアイテムを指す）。ちょうど 1 つ（`exactly_one("map", …)`）。
* **`ore` に 2 つ足した**: `patch_radius:`（設定から来た。`ore_` の接頭辞は語が言っているので落とした）と
  **`patches: [2, 2]`**（新しい。§3）。既定値は `serde` に持たせていない — 3 つとも必須で、
  書かなければ「missing field」がその行で出る。「Rust の側に遊びの数の既定値は 1 つも無い」（§9.3）を保つ。

**著者が変えたければどこか**: `factory/ruby/data.rb` の `map` の行と `ore` の行。
Rust には既定値が無いので、この 2 行が全部である。

## 2. `main()` から何が動かせたか（全部動かせた）

`main()` に残っていた「地図を要る所」は 4 つで、**4 つとも `Startup`（data stage の後）へ動いた**:

| 何 | どこへ |
|---|---|
| `Map` を作る | `lay_the_land`（`Rules::map_tiles` から作って `insert_resource`） |
| `Grid`・`Lanes`・`Ore` | もともと `lay_the_land`。`Map` もそこで作るようになっただけ |
| `TilemapChunk` 2 枚 | もともと `draw::start_drawing`（`lay_the_land` の後） |
| カメラの端・見える高さ・ズームの上限 | 新しい `point_the_camera_at_the_map`（§4） |

**動かせなかったものは無い。** `CameraPlugin::showing(half_height)` だけは `main()` で `App` に足すが、
渡すのは設定の数だけで地図は要らない（`CameraHome`・`CameraView`・`CameraControls` は全部 Resource なので、
`Startup` で書き換えられる）。`--stress` の `size_the_map_for_the_stress_run` は `ResMut<Map>` から
`ResMut<Rules>` になり、**`lay_the_land` の前**に走るので、F3 にあった「古い地図でカメラを作って後から直す」
が消えた。

## 3. 畑の口 — `patches: [2, 2]`（数ではなく格子）

**「4 隅に 4 つ」のままにはしなかった。** 256×256 の地図に畑が 4 つだと遊べない（畑 1 つは半径 3 で
32 タイル = 1,920 個で、鎖 1 本ぶんの鉄にもならない）。自由に大きくできるようにする段で、
畑の数を固定にしておくのは「自由」と言えない。

**数（`patches: 4`）ではなく格子（`patches: [2, 2]`）にした**理由:

1. **既定の絵が 1 画素も変わる余地が無い。** 今の置き方は「地図を 4 分割して各中心」で、
   これはちょうど `[2, 2]` の格子の各セルの中心である（`Ore::patch_middle` の
   `(2i+1)/(2n)`）。テスト `four_patches_one_to_a_quarter_of_the_map` は F1 が書いた
   タイル番号（8,8 と 24,24）をそのまま残して通る。
2. **種を発明しなくて済む。** 「4 つを散らす」には乱数の種が要り、種は出どころの無い数である。
   しかも `Ore::laid_out` の rustdoc が言うとおり「2 回の走行が同じ所に鉱石を見つける」ことは
   判定の前提でもある。
3. **導出がそのまま伸びる。** 下限は `tiles/(2n) − radius − 0.5 > 0`、すなわち
   `tiles > 2 × n × (radius + 0.5)`。**n = 2 を入れると F2 の `4r + 2` そのもの**で、
   F2 の導出に隠れていた 2 が「畑の数」だったと分かる形になった。
4. **長方形に意味がある。** 96×16 に `[6, 2]` と書けば、セルが正方形に近くなり畑が 12 個均等に並ぶ。
   数 1 つでは「6×2 か 4×3 か」を誰かが決めなければならない。

`size:` と同じ `[横, 縦]` の綴りなので、覚えることは増えていない。

## 4. カメラ（大きい・細長い地図で遊べるか）

`point_the_camera_at_the_map`（`Startup`、窓のある走行だけ）が 3 つを地図から言う:

* **パンの端** = 地図（`CameraControls::bounds`）。もともと `main()` でやっていたことの引っ越し。
* **既定の見える高さ** = `camera_half_height`（設定、150 のまま）**と地図の高さの小さいほう**。
  16 タイルの地図（256 世界単位）で 300 を見せると上下に無が映るので、そこだけ地図が言う。
  実測: 96×16 の走行が `the camera shows 256 world units`、32×32 と 512×512 は `300`（**既定は不変**）。
* **ズームの外側の限界** = 共有 crate の限界は「既定の見え方の倍数」なので（`camera::zoom_by`）、
  そのままだと 512 タイルの地図で全体を見ることが**できない**。地図の半分の辺 ÷ 既定の見え方を
  下限として `zoom_out_limit` を**上げる**（下げはしない）。既定の地図では 4096/150 = 27.3 でなく
  256/150 = 1.7 < 2.619 なので**今までどおり**。

**共有 crate に足りない口**: 無かった。`CameraHome`・`CameraView`・`CameraControls` が Resource で
公開されているので、ゲーム側の `Startup` で全部言える。`crates/` には 1 行も書いていない。

**`--shot` で「全体が写る」か。** 既定の見え方は「窓に対して整数倍ズーム」から導かれた数（`CAMERA_HALF_HEIGHT`
の rustdoc）で、地図からは導かれていない。**地図から導くのはやめた**: (a) 既定の 32×32 の絵が変わる、
(b) `draw::snap_zoom` が整数倍に丸めるので「ちょうど全体」にはならない、(c) Factorio を含め工場ゲームは
寄った所から始まる。代わりに**ズームで全体まで引ける**ようにした。証拠として
`camera_half_height=4096` を置いた走行の `--shot` を撮ってある（512×512 の全体、畑 16×16 が均等に並び、
縁の輪が見える）。既定の見え方のままの `--shot` は地図の真ん中の工場が写る。

## 5. 上限 — 実物で調べて、壊れる所が言う数だけにした

計画書「**上限は発明しない**」に従って、候補を 1 つずつ実物で見た。

| 候補 | 何が起きるか | それが言う数 |
|---|---|---|
| タイルの添字の型 | `What::Covered { origin: u32 }`、`Grid::built: Vec<u32>`、`Grid::index` が `u32` で掛ける | 辺 65,535（`w × h ≤ u32::MAX`） |
| **`TilemapChunk` のタイル情報テクスチャ** | 1 タイル 1 テクセルの `Rgba16Uint` 2D テクスチャ（`bevy_sprite_render-0.19.1/src/tilemap_chunk/tilemap_chunk_material.rs:96`）。辺が `max_texture_dimension_2d` を越えると wgpu がテクスチャを作れない | **辺 2048**（下記） |
| `Lanes`・`Grid`・`Ore`・`Flow` の確保 | 1 タイル **113 バイト**（`Option<Building>` 72 + `VecDeque<OnBelt>` 32 + `Steps` 4 + `u32` 4 + `Dir` 1。`size_of` で数えてログに出している） | 機械に依る → **上限にしない** |
| `draw` の毎フレーム | `draw_floor` は鉱石が変わったときだけ、`draw_buildings` は建物の一覧だけ。ただし**タイル情報の更新は Bevy 側が chunk 全体を詰め直す**（`update_tilemap_chunk_indices`、`Changed` で発火）。ベルトのアニメは 0.125 秒ごとなので毎フレームではない | 上限にしない |
| `belts::step` と `Tally` | **ここが毎フレーム、タイル数に比例する** — 尻尾の控え（`lanes.tails` 全走査）と `lanes.count()`（全レーンの長さの和）。§6 で測った | 上限にしない（遊べるかの話で、壊れる話ではない） |

**`max_texture_dimension_2d` は機械に依る。** Bevy は `WgpuSettingsPriority::Functionality` の既定で
**アダプタの limits をそのまま要求する**（`bevy_render-0.19.1/src/renderer/mod.rs:310`）ので、
`downlevel_webgl2_defaults` の 2048 に落ちるわけではない。実測:

| 描画系 | `max_texture_dimension_2d` |
|---|---|
| lavapipe（コンテナの窓） | **16384** |
| SwiftShader（Playwright の Chromium） | **8192** |

機械ごとに違うということは、**ここで採るべきは「この機械の値」ではなく「どの機械でも通る値」**である。
WebGL2 はこの値が **2048 以上**であることを保証していて、それが wgpu の `downlevel_defaults`
（`wgpu-types-29.0.4/src/limits.rs:498`）でもある。ページとして公開するゲームなので、
**上限は 2048（辺ごと）** とし、`draw::MOST_TILES_ACROSS` に出どころつきで置いた。
2048² = 4,194,304 は `u32` に収まるので、添字の型の上限（65,535）はこれに隠れて効かない。

**chunk を分ければこの上限は外れる**（floor と buildings を chunk の格子にする）。**やらない**と決めた:
値段は「2 枚の `TilemapChunkTileData` の書き込みが全部 chunk 探しを通る」「`draw_floor` /
`draw_buildings` が入れ子になる」で小さくないのに対し、買えるのは
**その機械のメモリより大きい地図**である（2048² は下の実測で 452 MB、4096² なら 1.8 GB）。
実際に 3,000 タイルの地図が要るようになったら、ここに戻る（`MOST_TILES_ACROSS` の rustdoc に書いた）。

**メモリは上限にしなかった。** 「壊れる」が機械に依るので、`lay_the_land` が
`262144 tiles is about 28.2 MB of grid, lanes and ore (113 bytes a tile)` と 1 行出すだけにした。

## 6. 断り方と、実測

下限・上限とも `.max`/`.min` せず **`data.rb:行` つきで断る**（`data::a_map_that_can_be_played_on`）。
文面は F2a の `items_per_tile` の作法（「何が書けるか」を言う）に合わせた:

```
data.rb:45: a map 14 tiles across has no room for 2 patches of ore of radius 3 without them
            touching the wall: make it 15 tiles across, or ask for fewer patches, or a smaller patch_radius
data.rb:45: a map 2049 tiles across cannot be drawn: the floor is one texture of one texel a tile
            and 2048 is as wide as one goes
```

下限の文が**3 つの数を全部言う**のは、直し方が 3 通りあるから（地図を広げる／畑を減らす／畑を細くする）。
断る行は `map` の行である — 下限を決めているのは `ore` の 2 つの数だが、**利用者が直しに行く行**は
地図の行のほうだから。

**実測（release、窓なし、2026-09-21）:**

| 地図 | 結果 |
|---|---|
| 15×15（下限ちょうど） | 起動し、判定 19 行が既定と diff 空 |
| 14×32 / 32×14（下限 −1） | `data.rb:45` で断られ、ゲームは始まらない |
| 2048×2048（上限ちょうど） | 起動する。452.0 MB、step p50 **5,894 µs** |
| 2049×2048（上限 +1） | `data.rb:45` で断られる |

## 7. 空の大きい地図の値段（タイル数に比例する毎フレームの仕事）

`--arms 1`（ベルトの蛇を敷かず、腕 1 台だけ）で「ほぼ空の地図」を走らせ、**交互に 2 巡**。
`step us` は `items::run_the_factory` が測っている区間（`belts::step` + `lanes.count()`）。

| 地図 | タイル | 巡 1 step µs p50 | 巡 2 step µs p50 | フレーム ms p50 |
|---|---|---|---|---|
| 32×32 | 1,024 | 4 / 4 / 4 | 5 / 5 / 4 | 16.75 |
| 512×512 | 262,144 | 607 / 635 / 759 | 564 / 546 / 568 | 16.75 |
| 2048×2048 | 4,194,304 | 5,894 / 5,833 / 5,864 | — | 16.72 |

**タイル数にほぼ比例している**（256 倍のタイルで 130 倍、4,096 倍で 1,300 倍）。出どころは 2 か所:

* `belts::step` のパス 1 — `for tail in &mut lanes.tails { *tail = Steps::MAX }` が**地図全体**を書く。
* `items::run_the_factory` の `tally.items = lanes.count()` — **全レーンの長さを足す**（`VecDeque` は
  32 バイトなので 512² で 8 MB を舐める）。

512×512 で 0.6 ms は 16.7 ms の 3.6% なので遊べる。**2048² の 5.9 ms は 1 フレームの 35%** で、
上限の近くは「起動はするが快適ではない」。これは**壊れる話ではない**ので上限にはせず、§9 の気づいた点に
書いた（どちらも「建っているタイルだけ」に直せる形で、直せば上限まで平らになるはず）。

## 9. 気づいた点

（報告と同じもの。`implementer.md` の形式 6）

1. **`belts::step` と `lanes.count()` が毎フレーム地図全体を舐める。** 空の 512×512 で 0.6 ms、
   2048² で 5.9 ms（§7）。`lanes.tails` の初期化は `lanes.order`（建っているタイル）だけにできるが、
   撤去のときに残る古い値を消す必要がある。`count()` は `Lanes` が増減のたびに数を持てば O(1)。
   **地図が自由になったので初めて意味のある話になった** — どこ: `factory/src/belts.rs` の
   `step` パス 1 と `factory/src/items.rs:62`。属する先: そのゲーム固有（F5 の HUD がこの数を使う）。
2. **`main()` で `warn!` を書いても何も出ない。** `LogPlugin` は `DefaultPlugins`/`MinimalPlugins` の
   中なので、`App::new()` の前に書いたログは subscriber が無く捨てられる。F3a の「移った設定の鍵」の
   警告を最初 `main()` に書いて、窓の走行で**何も出ずに**気づいた（`Startup` の system に移した）。
   属する先: 3 本に共通の作法（`docs/verification` に 1 行の価値）。
3. **`Ore::laid_out` は F1 以来「地図全体 × 畑の数」を走っていた。** 4 つなら気にならないが
   `patches: [16, 16]` = 256 個だと 512² × 256 = 6,700 万回になる。F3a で畑の外接矩形だけを
   走る形に直した（同じ絵が出ることはテストで確かめている）。属する先: そのゲーム固有（直した）。
4. **判定が畑の位置を「地図の 1/4」として知っていた。** `Ore::patch_middle` に聞く形へ直したが、
   同じ性質のものが他にもある（`lay_out_the_machine_lines` は地図の真ん中が空いていることに
   寄りかかっている — `patches` が奇数×奇数なら真ん中に畑が来る）。今は `[2, 2]` なので当たらない。
   属する先: そのゲーム固有／F4 以降の判定。
5. **`--shot` と判定を同時に使うと `done` の行が 1 行増える**（`CHECKS_EXIT_WHEN_DONE && shot.is_none()`）。
   `selftest-lines.md` の「窓 22 行」は `--shot` 無しの数である。属する先: 確認の作法（文書に 1 行）。

## 10. F5 へ渡す注意

* **世界を組み直すのは 1 つの関数にまとまっている**: `lay_the_land`（`Res<Rules>` と `Res<Data>` から
  `Map`・`Grid`・`Lanes`・`Ore` を作って `insert_resource`）。`data.rb` を読み直す
  （`data::read_the_declarations` は何度でも呼べる。F2 から）→ `Rules` と `Data` を差し替える →
  `lay_the_land` をもう一度走らせる、で**大きさが変わる**。`insert_resource` は上書きなので、
  古い `Grid` は消える。
* ただし **`lay_the_land` は世界を作り直す＝建てたものが全部消える**。「書き換えて読み直す」を
  F5 でどうするか（大きさが変わっていなければ建物を残す／常に作り直す）は決める必要がある。
  大きさが変わったのに残すのは無理（添字が `y * width + x` なので幅が変われば全部ずれる）。
* **窓のある走行では `draw::start_drawing` と `point_the_camera_at_the_map` も呼び直す**必要がある
  （chunk の `chunk_size` は固定で、`TilemapChunkTileData` の長さが合わないと Bevy が warn を出して
  何も描かない）。今はどちらも `Startup` の system。
* `Map` は `Startup` で入るので、**`Update` の system が `Res<Map>` を取るなら `the_factory_is_up`
  か `resource_exists::<Map>` で守る**（今そうなっている）。F5 が足す窓の system も同じ。

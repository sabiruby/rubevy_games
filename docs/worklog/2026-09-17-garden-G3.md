# 箱庭 G3 — 世界と「覚えていること」を JSON に（`sabiruby-serde`）

2026-09-17。`docs/plans/garden-plan.md` の G3。`garden-g3` ブランチ、main は `d221d68`（G0 / G0a / G1 / G2 がマージ済み）、
rubevy は `fa37eaa`、sabiruby は 0.5.0、`sabiruby-serde` は 0.1.0。コミットは `09e8a8c`（コード）と本文書を含む docs のコミット。

この段階の主題は **serde が 2 方向に使われること**で、その 2 つは対称ではない。
世界（草・木・岩・生き物）は Rust のデータで、`#[derive(Serialize, Deserialize)]` を載せれば終わる。
生き物の `@memory` は **Ruby の Hash** で、ゲームは VM の中からそれを読み出す。
そして `garden.spawn` の Hash は逆向きで、Ruby が書いた Hash を Rust の構造体として読む。
成果は `docs/garden.md` の「Saving and loading (G3)」。

## 0. 依存を 1 本足す（VM を 2 つにしない）

`sabiruby-serde` は crates.io にもあるが、workspace には **sabiruby と同じ git source** で足した。

```toml
sabiruby-serde = { git = "https://github.com/sabiruby/sabiruby" }
```

crates.io の copy を使うと、それが連れてくる `sabiruby` 0.5.0（crates.io 版）が rubevy の git 版と別 crate になり、
バイナリに VM が 2 つ入る。`Value` は片方のものでしかない。`cargo metadata` は同じ rev（`9c8ebf2`）を選び、
`Cargo.lock` に増えたのは `sabiruby-serde` の 1 エントリだけ。`serde` / `serde_json` / `indexmap` は
bevy が既にグラフに入れていて、**バージョンは 1 つも動いていない**。

Ruby 側の `JSON` は計画書が「rubevy に `with_vm` を足すかもしれない」と書いていたが、**足す必要は無かった**。
`ScriptWorld::vm` が公開されていて、G2 で `Genome::register` を呼んでいる `Startup` のシステムに 1 行増やすだけ:

```rust
fn install_host_api(mut world: ResMut<ScriptWorld>) {
    if let Err(e) = Genome::register(&mut world.vm) { … }
    sabiruby_serde::install_json(&mut world.vm);   // JSON.parse / .generate / #to_json
}
```

**rubevy には 1 行も足していない**（G2 と同じ）。`JSON` がゲームのものでエンジンのものではない、という
sabiruby 側の設計（`docs/design/serde.md`「Why JSON lives here」）が、そのままこの 1 行になっている。

## 1. `@memory` はどこにあるのか — task の self は全タスクで共有されている

計画書は「`ivar_get(script_self, "@memory")`」と書いている。最初に確かめたのは *script_self とは何か* で、
答えは「使えない」だった。`sabiruby` の `src/builtins/ext_task.rs:390` で、task が走り始めるときの self は

```rust
let self_ = match env.map(|e| vm.env_value(e, 0)) { Some(v) => v, None => Value::Obj(vm.top_self) };
```

つまり **VM の `main` オブジェクト**で、これは全タスクで 1 つしかない。生き物のファイルのトップレベルで
`@memory` と書けば、それは**別の生き物の `@memory` と同じ変数**になる。prelude が `Creature` のサブクラスを作って
`being = klass.new` する（G1 からある形）のは、まさにこれを避けるためだった。

ホストが持っているのは rubevy の `ScriptTask`（＝ task の `ObjId`）だけなので、task から生き物のオブジェクトへ
行く道は**こちらで敷く**しかない。prelude の `run_creature` に 1 行:

```ruby
Task.current.instance_variable_set(:@being, being)
```

rubevy 自身が entity を task の `@rubevy_entity` に置いているのと同じ手で、Rust 側は 2 回の `ivar_get` で届く。

```rust
let being = vm.ivar_get(task, "@being").obj()?;
let memory = vm.ivar_get(being, "@memory");
sabiruby_serde::from_value::<serde_json::Value>(vm, memory)?
```

**スクリプトには何も聞いていない**。`Rubevy.ask("memory.dump")` にして Ruby 側に `to_json` を書かせる案は捨てた:
そうすると保存はスクリプトの協力が要る動作になり（寝ている生き物、`loop {}` で預金を使い切った生き物は
答えない）、保存ボタンが生き物を起こすことになる。今の形なら、生き物は「覚える」だけで、保存の存在を知らない。

## 2. 戻すほうは 1 フレーム遅れる — `sleep 0.05` を 1 行

書くほうは同期的だが、**戻すほうはそうはいかない**。`@memory` を置く相手のオブジェクトは
`run_creature` が作るので、`Script` が `ScriptTask` になり、そのタスクが最初の命令を走らせるまで存在しない。
だから復元は「タスクが最初に走ったフレームの終わり」（`restore_memory`、`RubevySet::Answer` の後）になる。

ここで実際に踏んだ: **ウサギは `run` の 1 行目で `memory["trees"]` を読む**。復元前なので nil で、
`Rubevy.find(:Tree)` で庭中を歩き直し、そのあと復元が上書きする。ログにそのまま出た:

```
[script] Rabbit: 7 trees, and 41 plants to start with     ← 覚えていたのに探し直している
```

prelude の `run_creature` で、購読を張った**後**、`being.run` の**前**に `sleep 0.05` を 1 行入れた。
購読より後なのは、この一瞬に publish された出来事を落とさないため。入れた後:

```
[script] Rabbit: 7 trees, remembered: [15.717777252197266,0.0,-3.8954524993896484]
```

「生まれたフレームには考えない」という規則になったわけで、これは G2 の `NEWBORN_GRACE`（生後 2 秒は
反射を数えない）と同じ種類の話でもある。代案（ゲームが「復元が済んだ」と教える出来事を publish する）は、
毎回全生き物に 1 往復増えるので採らなかった。

## 3. 読み込み中は世界を止める — 判定を `diff` 1 本にするため

選んだ確認は「30 秒走らせて保存 → 別プロセスで読み込んで即保存 → **2 つのファイルを `diff`**」。
これが成り立つには、2 つ目のプロセスが「読み込んだ世界そのもの」を書かなければならない。
ところが復元には数フレームかかり、その間に草は伸び、腹は減り、時計は進む。

`Restoring` リソースを入れて、**全部の規則に run condition を付けた**（`is_still`）。さらに
世界の時計そのものを止めた: `Sky::shift` を毎フレーム `saved_tick - elapsed` に置き直すので、
`world_now()` は保存時刻に釘付けになる。復元が終わったフレームの**最後**に `Restoring` を外すので
（`finish_restore` はセーブの後に並べてある）、`--load A --headless 0 --save B` は「読んだ世界」を書く。

捨てた案は「許容誤差つきで比べる」。f32 を JSON にして戻すのだから ±1 ULP は許す、という比較スクリプトを
書けば freeze は要らない。採らなかったのは、(1) 比較スクリプトが育つと何を確かめているのか分からなくなる、
(2) freeze 自体が欲しい規則だから（読み込んだ庭が、頭脳が起きる前に 2 フレーム分歩いてしまうのは
ゲームとしておかしい）。結果として判定は `diff s1.json s2.json` で、11338 バイトが 1 バイト違わない。

## 4. 最後の 1 ULP は serde_json の読み側だった

最初の round trip は 4 行だけ落ちた。全部ウサギの「覚えている木の位置」で、

```
<             9.595357894897461,
---
>             9.59535789489746,
```

1 ULP 下。犯人を VM だと思って探したが違った。この 4 つは **ファイルの中で唯一 f32 に丸め直されない f64**
（生き物の座標は `[f32; 2]` なので読み込みで f32 に戻り、1 ULP の差は消える）。同じバージョン（1.0.151）の
serde_json だけで 4 行のプログラムを書いて確かめた:

```
parsed bits 402330d2bfffffff  back to text 9.59535789489746     ← 読んで書くと 1 ULP 下がる
literal bits 402330d2c0000000 printed 9.595357894897461         ← 書くほうは正確
```

`serde_json` の**パーサは既定では正しく丸めない**（書き手は ryu で常に最短かつ正確）。`float_roundtrip`
feature がその保証で、`garden/Cargo.toml` でそれを付けたら `diff` は空になった。読むのが 1 回きりの
セーブファイルに、パースの速さで払うものは何も無い。Python の `json`（strtod）は最初から `…c0000000` を返すので、
「JSON は text だから精度が落ちる」ではなく「この実装の既定がそうだった」が正しい。

## 5. Hash の鍵は String にした

`to_value` が map の鍵をどう書くかは `serde/src/ser.rs` を読んで決めた。`Options::symbol_keys` は
**struct のフィールド名と variant 名**にしか効かず、`serde_json::Value::Object` の鍵は map の鍵なので String で出る。
つまり Symbol 鍵で書いた `@memory` は、保存 → 復元で String 鍵の**別の Hash**になり、`memory[:meals]` は
`"meals"` の隣で何も見つけられない。

だから G2 で `@memory[:meals]` と書いていたところを全部 `memory["meals"]` にした。庭の他の場所の Hash は
Symbol 鍵のまま（VM から出ないから）。prelude に `memory` という 1 つのアクセサ（`@memory ||= {}`）を置いて、
そこにこの規則をコメントで書いてある。

## 6. `garden.spawn` の Hash: 手書き 72 行 → serde 7 行

G2 が `Vm::hash_entries` と `FromRuby` で 1 鍵ずつ読んでいた `read_birth`（47 行）と `read_genome`（25 行）を消し、

```rust
#[derive(Debug, Clone, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct CreatureSpec { pub species: Species, pub genome: Genome, pub at: [f32; 2] }
```

の 7 行にした（コメントと空行を除いた行、G2 の数え方と同じ）。呼び出しは 1 式:

```rust
sabiruby_serde::from_value::<CreatureSpec>(&mut scripts.vm, asked).map_err(|e| scripts.vm.describe_error(&e))
```

消えた 65 行がやっていたのは、鍵の名前を文字列と突き合わせること、Symbol を `Species` に `match` で移すこと、
遺伝子が何個来たか数えること、間違え方ごとに別のメッセージを組み立てること。行数に出ないほうが大きくて、
**`Genome` と `Species` はそれぞれの derive が読む**ので `CreatureSpec` はその 2 つについて何も書いていない
（手書き版には入れ子の Hash のために `read_genome` があった。`read_species` に当たるものは、ここには無い）。

残したのは clamp（`CreatureSpec::into_birth`、10 行）。デシリアライズは形の話で、範囲は規則だから。

メッセージも良くなった。`{speed:, appetite:}` に対して、手書き版は
`"genome: wants speed, sight and appetite; got 2 of them"`、serde は **``missing field `sight` (TypeError)``**。
9 つ目の selftest はこれで、テスター用のスクリプト（4 行の Ruby を `main.rs` の中に持っている。
唯一の生き物でないスクリプト）が `sight` の無い genome で `garden.spawn` を呼び、答えに `sight` が出ることを見る。

**native にはしなかった。** `Serde<T>` は `define_fn` のためにあり、`vm.define_fn(garden, "spawn", |spec: Serde<CreatureSpec>| …)`
と書けばもう 1 行短い。しかし native が受け取るのは `&mut Vm` だけで Bevy の `World` に触れない
（rubevy `docs/host-api.md`）。今いる生き物の数を数えられず、entity を作れず、`true` か理由かを返せない。
結局「後でシステムが拾うメモを置く」ことになり、それは `Request` そのものなので、`ask` のまま
`RubevySet::Answer` に置いた。`Serde<T>` は引数を読む半分だけ使っている。

## 7. 確認

* `cargo build --release -p garden` — 通る。警告なし。
* `GARDEN_SELFTEST=1 ./target/release/garden --headless 90` を 4 回。9 つ目（G3 の分）は 4 回とも ok。
  **3 回目だけ 6 つ目が落ちた**（触られた甲虫が向きを変える、39/40）。これは G2 の記録にある
  「もともと不安定な判定」で、G1 のバイナリ（`a61a611`、G2 も G3 も入っていないもの）でも 4 回に 1 回落ちる。
  4 回の内訳は 34/34、42/42、**39/40**、そして 4 回目（下に貼ったもの）。40 回の接触のうち 1 回が
  45 度に届かなかった、という形なので、G2 が書いた診断（取りこぼしか遅れであって反射が壊れたのではない）と同じ。
  G3 で触った範囲（保存・復元・`garden.spawn` の読み方・prelude の `sleep 0.05`）はどれも
  この判定の経路に無いので、ここでは追っていない。
* round trip（保存 → 読み込み → 保存）— 2 つのファイルが同一（11338 バイト）。
* `cargo check -p garden --target wasm32-unknown-unknown` — 通る。**ブラウザで動かしてはいない**:
  web の分岐（`localStorage`）はコンパイルが通ることしか確かめていない。実際に動かすのは G5。
* 窓（F5 / F9）は**押していない**。この機械は WSL で GPU ドライバが無く、窓は docker 越しになる
  （`docs/wsl-gpu.md`）。鍵を読むシステムは 10 行で、保存と読み込みの本体は headless 側と同じ関数を呼ぶ。
  ただし **F9 が通る道（動いている世界への読み込み）は headless で 1 回動かして確かめた**: 使い捨ての
  `GARDEN_RELOAD_AT` を足して 5 秒で `Loading` を差し込み、`--headless 12` で回した。

  ```
  TEST: reloading at 5.0 s
  loaded 10 creatures, 44 plants, 7 trees, 9 rocks at 12.0 s (73 entities made way)
  [script] Rabbit: 7 trees, remembered: [0.7445030212402344,0.0,1.4797134399414062]
  10 creatures, 43 plants, day at phase 0.38
  ```

  73 個の entity（草・木・岩・生き物）が消え、世界が作り直され、記憶が戻り、時計は保存時刻（12.0 s）から
  続いた。panic も ERROR も WARN も無い。**この `GARDEN_RELOAD_AT` はコミットしていない**（確かめたあと戻した）。
  起動時の `--load` と同じ `load_world` を通るので、残る未確認は「キーボードの 2 行」だけになった。

## 8. 決めなかったこと・残したもの

* **`Memory` コンポーネントは空のまま**にした。G0 の時点では「G3 で中身が入る」と書いてあったが、
  覚えていることの実体は VM の中の Hash で、コンポーネントに写すと**同じものが 2 つ**になり、
  どちらが本物かを誰が保つのかという問題が残る。ECS に置いたのは「この entity は記憶を持つ」という事実だけ。
  （規則が記憶の中身で分岐したくなったら、そのときは写す側の設計を決めることになる。）
* **`Velocity` は保存しない。** 拾い上げられた生き物は、頭脳が何か言うまで止まっている。
* **岩の潰し具合と草の見た目（bush か tuft か）も保存しない。** モデルの都合なので読み込みで振り直す。
  窓で見ると、読み込んだ庭は同じ場所に同じ大きさの草が生えているが、丸いか尖っているかは変わりうる。
* **セーブファイルの版番号を付けていない。** 今は形が変われば読めなくなる（`serde_json::from_str` が
  `missing field` で落ちてログに出るだけ）。版が要るのは公開する形になってからなので、著者の判断待ち。

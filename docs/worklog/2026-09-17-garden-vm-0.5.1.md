# 直った VM に乗せ替える — 回避を 1 つ消し、原因不明を 1 つ潰す

2026-09-17。ブランチ `vm-0.5.1`、main は `de6fa9c`（G0〜G5 merge 済み）。
sabiruby が 0.5.1（`bd6829b`）になり、G4 と G5 が「VM 側の仕事」として上げていた
「一度に何匹も入れ替えると新しいタスクが走らない」が直った。やることは 3 つあった:
ゲーム側の回避（`window.rs` の待ち行列）を消すこと、G5 が原因を突き止められなかった
「動いている庭への F9 で記憶が戻らない」を測り直すこと、そしてブラウザで両方を確かめること。
結果として**ゲームのコードで直したのは 1 か所だけ**で、それは VM とは関係が無かった。

## 1. lock を上げる

```
$ cargo update -p sabiruby -p sabiruby-compiler -p sabiruby-serde -p rubevy
    Updating rubevy v0.0.1 (…#fa37eaaa) -> #ec6f0ce0
    Updating sabiruby v0.5.0 (…#9c8ebf2d) -> #bd6829b3
    Updating sabiruby-compiler v0.2.2 -> #bd6829b3
    Updating sabiruby-macros v0.1.0 -> #bd6829b3
    Updating sabiruby-serde v0.1.0 -> #bd6829b3
```

`sabiruby-macros` は名指ししていないが同じ git source なので一緒に上がる。rubevy が
指示にあった `b8fe362` ではなく `ec6f0ce` になったのは、`ec6f0ce` が `b8fe362` の 1 つ上の
docs だけのコミットだから（`git log` で確認した）。VM は同じ。

## 2. 待ち行列を消す — 「同じフレームで全部」に戻す

G4 が書いた回避はこうだった。`restart_species` は入れ替える生き物を `Restarting` に積むだけで、
`restart_queued` が `RESTARTS_PER_FRAME = 1` と `RESTART_GAP = 0.4` で 1 匹ずつ渡す。
**この形はもう要らない**ので、`Restarting`・2 つの定数・`restart_queued`・`main.rs` の
`init_resource` と system 登録を消し、`restart_species` を「`&mut Commands` と
`Query<(Entity, &mut Mind)>` を取って、その場で種の全個体を入れ替える関数」にした。

`Restarting` を残すかどうかは少し考えた。`do_editor_actions` と `reload_changed` は
どちらも「入れ替えたい」と言うだけの側で、実際に `Commands` を叩くのは別のシステム、という
分け方には形の上の筋がある。**残さなかった。** system は `.chain()` で
`do_editor_actions` → `reload_changed` → `restart_queued` の順に並んでいたので、
待ち行列は「同じフレームの 3 行あとに渡すための箱」でしかなく、
時計を外した時点で中身が 1 フレームも待たない。名前が `Restarting` のまま
「待たない待ち行列」が残るほうが、読む人を誤らせる。呼ぶ側 2 つの `minds` を
`&mut` にして `Commands` を足す、で足りた。

窓の判定からも待ちが 2 か所消えた。ステップ 7 と 10 は
`if !queue.waiting.is_empty() && now < test.deadline { return }` で行列が空になるのを
待っていた（そのための `WindowTest::deadline` も消した）。いまは Apply の 0.6 秒後に見る。
この 0.6 秒は G4 が「行列が空になった瞬間に見ると最後の 1 匹がまだ 1 フレームも走っていない」で
入れたもので、**理由は変わっていない**（作られたタスクが最初の命令を走らせるのに 1 フレーム要る）ので
そのまま残した。Apply から判定までは約 5 秒から 0.65 秒になった。

### 表を取り直す

G4 は `GARDEN_ONE=<n>`（先頭 n 匹だけ入れ替える）という一時スイッチで境界を測っている。
同じものを**また一時的に**書いて（`restart_species` に cap、`window_selftest` に
`DBG at apply / +0.6 s / +3.6 s` の 3 行、`WindowTest::after` を `GARDEN_TEST_AT` で動かす）、
docker + lavapipe の窓で 6 通り回した。**この計測用パッチはコミットしていない**（測り終えて戻した）。
`GARDEN_TEST_AT=25` にしたのは、既定の 3 秒だと甲虫が 10 匹前後しか居らず 12 の行が作れないため。

| 一度に入れ替えた数 | Apply の 0.6 秒後 | その 3 秒後 | 差 |
|---|---|---|---|
| 1 / 13 匹 | 242,913 | 248,619 | +5,706 |
| 4 / 10 匹 | 174,569 | 179,731 | +5,162 |
| 9 / 11 匹 | 112,371 | 118,692 | +6,321 |
| **10 / 10 匹** | **87,777** | **93,941** | **+6,164** |
| 12 / 12 匹 | 91,039 | 98,871 | +7,832 |
| 全部（11 / 11 匹） | 96,086 | 103,681 | +7,595 |

G4 の表では 10 の行が `18704 → 18704` で、そこから二度と動かなかった。**崖は無くなっている。**
行ごとに総数が違うのは、判定が Apply に辿り着くまでに庭が繁殖したり餓死したりするから。
Apply の瞬間に命令数が下がるのは、入れ替わったタスクが 0 から数え直すため（`spent()` は
生きている `ScriptTask` の `task_instructions` の和）。

窓の判定は **21/21 ok**（docker + lavapipe）。落ちていた
`every restarted beetle's new task has run` も `the whole VM is still running afterwards` も通る。

## 3. 動いている庭への F9 — 犯人は `restore_memory` ではなかった

G5 の 1 つ目の指摘はこうだった。ブラウザで F9 を押すと `load_world` が全部 despawn して
11 匹を同じフレームで作り直し、`11 creatures never started; the garden is running anyway` が出て
`@memory` が空のまま戻ってくる。起動時の `--load` では 11 匹とも戻るので、
**「動いている庭に読み込む」側だけが踏んでいる**。

headless で踏めなかった理由ははっきりしている。`MinimalPlugins` には `ButtonInput` が無く、
F9 を押す手段が無い。G3 は使い捨ての `GARDEN_RELOAD_AT` で 1 回だけこの道を通していて、
そのスイッチはコミットされていない。**同じものを、今度はちゃんと足した。**

`ReloadAt { at, path, asked, restored }` と `reload_while_running`。`GARDEN_SELFTEST` が
立っているときだけ `GARDEN_RELOAD_AT` を読み（`platform::reload_asked_at`、wasm 側は `None`）、
その秒数まで `--load` のファイルを開かずに置いておく。庭は t=0 に新しく建ち、自分の心で
その秒数だけ生き、それから F9 と同じ `Loading` が入る。**別の読み込み経路は 1 行も足していない。**

もう 1 つ考えたのは、「バイト単位で同じ」を成り立たせる方法。読み込んだ世界をそのまま書き出すには、
復元が終わったフレームでセーブしなければいけない（1 フレームでも歩くと座標が変わる）。
`--headless 0 --load a --save b` の往復がそうなっているのは、`stop_when_over` が
`restoring.done` を待ち、その後ろに `save_world` が居るから。同じ形を借りて、
`restore_memory` が `done` を立てるときに `ReloadAt::restored` も立て、`stop_when_over` が
それを待つようにした。`stop_when_over` は `restore_memory` と `save_world` の**間**に居るので、
`--headless N` と `GARDEN_RELOAD_AT=N` を揃えれば、読み込んだ庭がそのまま書き出される。

`finish_restore` で立てる案も考えたが、あれは `save_world` の**後ろ**なので 1 フレーム遅れる。
`load_world` が `Commands` で `Restoring` を入れた直後のフレームに `stop_when_over` が
それを見られる保証も無い（system 間に直接の順序が無いので sync point が入るとは限らない）。
`ResMut` で直接立つ `restored` を `restore_memory` に置いたのは、その 2 つを避けるため。

### 測ると、これも同じバグだった

新しい VM では通る:

```
$ ./target/release/garden --headless 30 --save a.json
saved 12 creatures, 47 plants at 30.0 s to a.json (13057 bytes)
$ GARDEN_SELFTEST=1 GARDEN_RELOAD_AT=20 ./target/release/garden \
      --headless 20 --load a.json --save b.json
GARDEN_RELOAD_AT: loading a.json into the running garden
loaded 12 creatures, 47 plants, 7 trees, 9 rocks at 30.0 s (69 entities made way)
saved 12 creatures, 47 plants at 30.0 s to b.json (13057 bytes)
$ diff a.json b.json && echo IDENTICAL
IDENTICAL
```

`never started` は出ない。ただし**これだけでは「VM が直ったから通った」と言えない**ので、
同じソースを古い lock（`git show de6fa9c:Cargo.lock`）で焼いて、**同じコンテナで**回した。
こちらも通る:

```
loaded 12 creatures, 41 plants, 7 trees, 9 rocks at 30.0 s (61 entities made way)   11:54.2206
saved 12 creatures, 41 plants at 30.0 s to /tmp/b.json (12557 bytes)                11:55.6967
IDENTICAL
```

**通るが、1.48 秒かかっている。** 同じコンテナの 0.5.1 は
`15:15.691239` → `15:15.697685` で **6 ms**。ここが答えだった。
`RESTORE_PATIENCE` は 5 秒で、1.48 秒はその内側だから **PC は一度も落ちなかった**。
ブラウザはこのコンテナより 1 秒あたりのフレームが少ないので、同じ待ちが 5 秒を越えて
`11 creatures never started` になっていた。12 匹を一度に despawn するのは反射タスク 72 本が
`nil` で終わることで、0.5.0 ではその 1 本 1 本がホストの 1 フレームを丸ごと食う
（sabiruby `docs/worklog/2026-09-17-task-end-nil.md`）。
**`restore_memory` のタイミングの問題ではなく、G4 の待ち行列が回避していたのと同じバグ**だった。
ゲーム側に直すところは無い。

## 4. ブラウザ — 3 つ目が 1 時間かからずに落ちた

`web/build.sh garden` + `web/serve.sh` + playwright-core（隣の
`sabiruby-playground/node_modules`、Chromium 153、SwiftShader）。G5 の道具立てをそのまま使った
（`waitUntil: 'commit'`、使い捨てのドライバはスクラッチパッド、コミットしていない）。

* `garden/?selftest` 150 秒 — **窓の判定 21/21**。G5 で落ちていた
  `every restarted beetle's new task has run` が通る。page error 0、404 0。
* `garden/` 45 秒 → F5 → **F9（リロードせず、動いている庭に）** →
  `loaded 10 creatures, 46 plants, 7 trees, 9 rocks at 45.3 s (78 entities made way)`。
  `never started` は 1 行も出ない。その直後にもう一度 F5 して `localStorage` を読むと
  **10 匹中 10 匹に記憶があり**、中身は `{"meals":10,…}` や `{"trees":[…]}` で、
  G5 の「`{"meals":1}` から数え直している」ではない。

### G5 の (a) — 判定のあとページが鍵に答えなくなる

「1 時間まで」と言われた分の作業。G5 は DOM（canvas にフォーカス、`keydown` は `#garden` に届く）と
`EguiWantsInput` の guard（外しても直らない）を潰したうえで、
「`window_selftest` が `ButtonInput` を手で押しているせい」か「egui がキーボードフォーカスを
離さないせい」だろう、と書いていた。

最初に見たのはログの**末尾**で、そこで終わった。判定の最後の行のあと、
`[script]` も `was born` も `night at` も **1 行も出ていない**。
egui がフォーカスを握っているなら世界は動いているはずで、動いていない。
つまり止まっているのは入力ではなく**アプリ**である。犯人は `window_selftest` の最後の
`exit.write(AppExit::Success)` だった。PC ではそれが正しい（コマンドラインで頼まれた判定なので、
シェルにプロンプトを返さないといけない）。**ページには終了する先が無い。**
winit の wasm イベントループが回らなくなり、全システムが止まり、
最後に描いたフレームが canvas に残る。だから「パネルは描かれ続け、世界は動いている」ように**見える**。
G5 のその読みも、私が最初に疑ったものも、同じ絵を見て別の話をしていた。

直し方は `platform` の定数 1 つ。`CHECKS_EXIT_WHEN_DONE` は PC で `true`、ページで `false`。
ページでは `selftest: done — the garden keeps running (a page has nothing to exit to)` と言って
庭を続ける。焼き直して同じ 150 秒を回すと:

```
F5 after the checks -> saved 15 creatures, 30 plants at 150.2 s to garden.save.json (13031 bytes)
F9 after the checks -> loaded 15 creatures, 30 plants, 7 trees, 9 rocks at 150.2 s (62 entities made way)
P  after the checks -> [script] lines in 4 s: running 2, paused 0, resumed 3
```

`P` はログを持たないので、**止まるもので測った**: 一時停止の 4 秒間だけスクリプトの出力が 0 になる。
世界も生きている（`night at 145.4 s` は判定が終わってからずっとあとの行）。

* 窓（docker + lavapipe、`docs/wsl-gpu.md`）— **21/21 ok**、判定のあと窓は閉じる（PC の側は変えていない）。
* `web/build.sh all` — 成功。`garden/pkg/game_bg.wasm` は 35,216,938（gzip 10,715,122）で、

* ブラウザ（Chromium 153、SwiftShader）— 上の 2 本。

## 6. やっていないこと・気づいたこと

* **ベンチは取っていない**（指示にそうある）。速さについては何も言えない。
* **古い VM での計測は 1 回だけ**。1.48 秒という数字は 1 サンプルで、
  「5 秒の `RESTORE_PATIENCE` の内側」という結論に必要な精度は十分にあるが、それ以上の意味は無い。
* `sabibots` はブラウザで開き直していない。`web/build.sh all` が通ることだけ確かめた。
* ブラウザのコンパイラがファイル名を渡せない件（G5 の 3 つ目）はそのまま。
  sabiruby-playground 側の変更なので触っていない。
* `GARDEN_RELOAD_AT` は `--load` を必要とする。指定が無いと `error!` を出して何も読まない。
  `--load` を「起動時に読む」と「N 秒後に読む」で使い分ける形にしたのは、
  読み込み元と保存先を別のファイルにできるようにするため（`SaveFile::path` を使うと
  F9 と同じく「保存したのと同じ場所」からしか読めず、往復の比較ができない）。

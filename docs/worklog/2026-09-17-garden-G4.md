32/33、この枝の G3 では 37/39・39/40。落ちた個体は `dot 0.78`＝**約 39 度は曲がっている**ので、
「反射が動かなかった」（dot ≈ 1.0 になるはず）ではない。

まず**今の木で率を測り直した**。90 秒を 10 回、逐次:

```
34/34 ok  23/23 ok  35/36 FAIL  36/36 ok  27/27 ok  36/36 ok  34/34 ok  16/16 ok  16/16 ok  32/32 ok
```

10 回に 1 回、285 件の接触のうち 1 件。これが直す前の基準。

## 2. 1 回の計測で犯人が出た — `@course` が `flee_from` の途中で書き換わる

推測で直さないために、落ちた 1 件について**次の 3 つを同時に吐く**ようにした（一時的な計測、コミットしていない）:

* `"touched"` が甲虫のキューに**届いたか**。`ScriptWorld::publish` は届いた数を返さないので、
  `publish_value` にして「購読者ごとに 1 回走る」クロージャの中で数えた。
* 反射が**走ったか**、走ったとして `flee_from` が**何を計算したか**。prelude の `flee_from` に
  `@dbg = [種別, 入ったときの @course, 逃げる方向, side, 最終 course, 出るときの @course]` を置き、
  甲虫の `reflex(:touched)` がそれを `@memory` に写す。ホストは G3 の `read_memory`（`ivar_get` 2 回）で
  **スクリプトに何も聞かずに**それを読める。
* 判定側の `was` / `now` / `dot`。

6 回並列で 1 件落ち、出力はこれ:

```
DEBUG miss: beetle 88v0 touched at 59.470 was (-1.990,-0.197) angle -174.4deg,
            now (-2.164,1.420) angle 146.7deg, dot 0.778;
            touch Some("rabbit 94v0 beetle_at (8.71,8.74) rabbit_at (8.65,7.49) delivered 1");
            memory {"meals":3,…,"startled":12,
                    "dbg":["flee",-3.0431314215703167,1.560861954221851,1.0,2.560861954221851],
                    "busy_at_start":true}
```

読める順に:

* `delivered 1` — **メッセージは落ちていない**。64 のキュー溢れでも購読の取りこぼしでもない。
* `startled 12` — 反射は 12 回走っている。今回も走った。
* `dbg[4] = 2.5609 rad = 146.7°` が、判定が見た `now` の角度と**一致**。つまり反射の `act` も効いている。
* `dbg[1]`（`flee_from` に入ったときの `@course`）は `-3.0431 rad = -174.36°` で、判定の `was`（-174.4°）と一致。
  **入り口では正しかった。**
* ところが `side = +1.0`。逃げる方向 `away = 89.4°` に対して、`@course = -174.36°` なら
  `angle_diff(-174.36°, 89.4°) = -96.2°` で負、つまり `side` は **-1.0** でなければならない。
  `+1.0` になったということは、`side` を計算した時点の `@course` は `-174.36°` では**なかった**。

`flee_from` は入り口で `here`（1 往復）と `place_of(thing)`（1 往復）を読む。つまり
**2 フレームぶん止まる**。その間に `@course` が別の値になっている。誰が書いたか:

```ruby
def wander(change = 0.25, avoid: nil, from: nil)
  if @course.nil? || rand < change
    @course = rand * TWO_PI          # ← ここで書く
  end
  act Math.cos(@course) * CRUISE, …  # ← act は「ハンドルを持っていない」ので何もしない
end
```

`act` は反射がハンドル（`@wheel`）を握っている間は**黙って帰る**（G1 でそう決めた）。
`wander` はその前に `@course` を書いてしまう。だから「誰も走ったことのない向き」が `@course` に残り、
`flee_from` はその嘘を基準に「反対側」を選ぶ。`busy_at_start: true` が示すとおり、この個体は
別の反射がハンドルを持っている最中に `touched` が来ていて、脳は `busy?` を抜けたあとの
1 パスの途中だった。

**直し方**: `@course` を書くのを `act` の中だけにし、**書き込みが実際に出たときだけ**書く。

```ruby
def act(vx, vz)
  return if @wheel && @wheel != Task.current
  vx = vx.to_f
  vz = vz.to_f
  me[:Velocity] = [[vx, vz]]
  @course = Math.atan2(vz, vx) unless vx == 0.0 && vz == 0.0
  nil
end
```

`wander` / `head_to` / `flee_from` の `@course = …` は消し、ローカル変数にした。
prelude のコメントが前から「everything that sets a heading keeps it true」と書いていたので、
**コメントのほうが正しく、コードが嘘だった**という形の直し方になる。

これで `flee_from` の保証が数えられるものになる: ハンドルを握ってから呼ぶので、
2 回の往復の間に `@course` を動かせるものは無く、向きの変化は
`|@course から逃げる方向までの角| + swerve` ＝ **最低でも swerve（1.0 rad = 57.3°）**。
判定の閾値は `dot < 0.7`＝45.6° なので、**通るのが保証される**。

## 3. それでも落ちた — 2 つ目の犯人は判定の「落ち着き待ち」のほう

`@course` の直しだけで 90 秒を逐次 3 回回したら **2 回落ちた**（39/40 と 31/33）。
同じ計測を仕込んであったので、落ちた 3 件が出た:

```
beetle 107v0 at 63.00  was -15.8deg  now  14.7deg  dot 0.861  delivered 1
beetle  94v0 at  2.37  was  -4.3deg  now -16.7deg  dot 0.977  delivered 1
beetle 106v0 at  8.46  was -127.2deg now -101.2deg dot 0.899  delivered 1
```

曲がりは 12〜30 度。**57 度の swerve ではない**。ところが `now` の**速さ**を見ると 2.495 と 2.20 で、
甲虫の脳が書く速さ（`wander` も `head_to` も `CRUISE = 2.0`）ではない。`flee_from` は `DASH = 9.0` を頼み、
`move_creatures` が遺伝子の上限（1.83〜2.57）に切る。つまり**反射は走って、逃げる向きを書いている**。
それでも判定から見た向きの差が小さい、ということは `was` が**その逃走が基準にした向きではない**。

### 捨てた仮説: システムの順序

最初に疑ったのは並び順だった。`startle` は `Velocity` を読んで「触られた瞬間の向き」を控えるが、
ルールの chain は `RubevySet` のどの集合とも順序が付いていない。`apply_component_writes`
（`RubevySet::Tick` の最後）より**前**に走れば、`startle` が見るのは 1 フレーム前の `Velocity` で、
スクリプト側の `@course` とずれる。

測った。`startle` の中で、控える `Velocity` の角度と、その甲虫の `@being.@course`
（`ivar_get` 2 回）を並べて吐く。順序を付けた版と付けない版の 2 本のバイナリを作り、75 秒を 3 回ずつ:

```
ordered   : |差| < 0.05°  99 件、0.05〜5°  0 件、5° 超  0 件
unordered : |差| < 0.05° 113 件、0.05〜5°  0 件、5° 超  0 件
```

**1 件もずれない。** Bevy は（この構成では）書き込みを先に済ませていた。仮説は外れ、
`.after(RubevySet::Tick)` は入れずに戻した。順序が決まっていないこと自体は残っているが、
今日の問題ではないものを「ついでに」直すと、直した理由が記録に残らない。

### 当たった仮説: 「落ち着き待ち」のリセットが if の中にあった

G1 の `startle` はこう書いてある（コメントは G1 のもの）:

```rust
world.publish(Some(beetle), "touched", Answer::Entity(*rabbit));
if let Some(test) = test.as_mut()
    && velocity.0.length() > 0.5
    && !by_a_wall(at)
    && creature.age > NEWBORN_GRACE
{
    // The clock is reset by *every* touch, so what is measured is always a beetle that was
    // not already running from something.
    let fresh = match test.last_touch… { … seen.1 = now; fresh }
    if fresh { test.touched.push(…) }
}
```

コメントは「時計は**すべての**接触でリセットされる」と書いているのに、リセットは
**3 つのガードの内側**にある。止まっている甲虫、壁際の甲虫、生後 2 秒未満の甲虫に送られた
`"touched"` は、キューには入るのに時計には入らない。だから次の接触が「1.5 秒ぶりの初めての出来事」に見え、
実際には反射タスクが 1 つ前のメッセージを処理している最中（1 通あたり `sleep 0.5` ＋往復で約 0.56 秒）。
0.5 秒後に向きを見ると、それは**前のメッセージへの返事**で、`was` は今回のメッセージのもの。

数えた。判定が数えた接触ごとに「その前 1.5 秒に何通送られていたか」を吐く:

```
90 秒 × 6 回、数えた接触 211 件のうち 41 件（19%）が、
直前 1.5 秒に時計の見ていないメッセージを受け取っていた（ほとんどが 1 通、1 件が 2 通）。
```

多くは開始直後（生き物が固まって湧く 2〜3 秒）と夜（寝ている＝速度 0 なのでガードに弾かれる）。

**直し方**: 時計のリセットをガードの外に出し、ガードは「数えるかどうか」だけにする。
定数にも名前を付けた（`TOUCH_SETTLE = 1.5`）。

```rust
if let Some(test) = test.as_mut() {
    let fresh = …;              // すべての publish でリセット
    if fresh && velocity.0.length() > 0.5 && !by_a_wall(at) && creature.age > NEWBORN_GRACE {
        test.touched.push(…);
    }
}
```

これは**閾値を緩めたのではない**。`dot < 0.7` も 0.5 秒も 1.5 秒も動かしていない。
G1 が書いた除外が、書いたとおりに効くようになっただけで、数える件数は 2 割ほど減る
（90 秒で 35 件前後 → 25〜45 件。もともと回ごとに 16〜49 件と幅がある）。

## 5. 窓 — `rubevy-arena` に足したのは 4 つのフィールド

G4 の本体。エディタと VM パネルは sabibots が使っている `rubevy-arena` のもので、
**箱庭のために書き足したコードは `garden/src/window.rs` の 1 ファイル**。
共有 crate 側に要ったのは `Editor` の 4 フィールドだけで、どれも「2 本目のゲームが来て初めて
決め打ちだと分かった場所」だった:

| 足したもの | なぜ要ったか |
|---|---|
| `apply_label: String` | ボタンの文字が `"▶ Apply (F5)"` 固定だった |
| `apply_all_label: Option<String>` | `None` で 2 つ目の Apply を**描かない**。箱庭には「この 1 匹だけ」が無い |
| `apply_key: Option<KeyCode>` | `F5` 固定だった。箱庭の `F5` は G3 の「庭を保存」で埋まっている |
| `noun: String` | hover の文が `"run this in this robot only"` のように robot 決め打ちだった |

`Editor` は `#[derive(Default)]` をやめて手書きの `Default`（`apply_key` の既定が `Some(F5)` なので）。
sabibots 側の変更は `show_code` の 1 行（`apply_all_label` を毎フレーム組み立てる）だけで、
挙動は変わっていない。

**エディタの単位が違う。** sabibots ではロボット 1 体が 1 ファイルを持つので、Apply は「この 1 体」、
Apply to all は「同じファイルの全員」。箱庭はファイルが**種**そのもの（甲虫は全部 `beetle.rb`）なので、
その 2 つは同じ集合になる。だから Apply は 1 つだけ描き、押すと**その種のスクリプトが全部再起動**し、
`Brains`（`[Option<String>; 2]` のリソース）に入ったテキストは
**そのあと生まれる子にも配られる**（`give_mind` が見る）。ファイルには Save まで書かない。

再起動は sabibots と同じ形 — `ScriptTask` を外して新しい `Script` を挿す。外した時点で rubevy が
タスクを終了し、購読を閉じ、反射タスクを畳む（`stop_removed_task`）。**`@memory` は戻らない**:
記憶は古いスクリプトが作ったオブジェクトの上にあり、新しいスクリプトは新しいオブジェクトを作る。
これは正直な挙動で、書き換えられた脳はそれを覚えた脳ではない。

## 5a. 一度に 10 匹入れ替えると VM のスケジューラが止まる（**報告**）

窓の判定を書いたら Apply の直後に 2 つ落ちた。「VM パネルにフレームがある」と「生き物がまた考えている」。
`GARDEN_SELFTEST=1` を窓で回して数字を吐かせると:

```
DBG pending true tasks 15 spent 20098 (was 50107)
DBG   Rabbit 395v0 insn Some(4999) at rabbit.rb:86     ← 触っていないウサギ
DBG   Beetle 389v0 insn Some(0)    at -                ← 入れ替えた甲虫（新しい task、0 命令）
…
DBG after 3 s: spent 20098 (was 20098) pending true    ← 3 秒後、1 命令も増えていない
```

**VM 全体が止まっている。** `Vm::task_pending()` は true のまま、`task_run_limits` は
Ok を返して 1 命令も走らせず、**入れ替えていないウサギも凍る**。エラーログは 1 行も出ない。

`GARDEN_ONE=<n>` で「先頭 n 匹だけ入れ替える」一時スイッチを付けて境界を測った
（甲虫 1 匹 = 脳 1 + 反射 6 タスク、購読 6 本）:

| 一度に入れ替えた数 | 3 秒後の命令数 |
|---|---|
| 1 | 50566 → 74332（動いている） |
| 2 | 44105 → 72207 |
| 4 | 36748 → 56314 |
| 8 | 22547 → 31077 |
| 9 | 18990 → 28139 |
| **10** | **18704 → 18704（止まる）** |
| 12 / 全部 | 止まる |

**9 は平気で 10 で止まる。** 次に「1 フレーム 3 匹ずつ、4 フレームかけて」を試したが**同じように止まった**ので、
「1 フレームあたりの数」ではなく「短い間に何匹か」の話だと分かる。
最後に**時計で間隔を空けて** 0.4 秒に 1 匹にしたら、12 匹全部が入れ替わり、VM も止まらなかった。

読み方としては、古いタスクの context（1 匹 7 本）が解放されるのに時間が要り、
それより速く新しい context を積むと詰まる、というあたり。90 秒の headless では
`contexts 85 live of 99` と出るので context は終了もしている（増える一方ではない）。
**これは VM / rubevy 側の話なので、ここでは直さずに報告する。**
ゲーム側は `RESTARTS_PER_FRAME = 1` と `RESTART_GAP = 0.4` の待ち行列（`window.rs` の `Restarting`）で渡す。
一列に並んで順に目を覚ますのが見えるので、隠している感じにはならない。
sabibots がこれを踏んでいないのは、ロボットが 4 体・反射 1 本で、入れ替えるのが 1 体か 4 体だから。

**生き物を選ぶ。** クリック（カメラのドラッグと左ボタンを共有するので、**離した**ときに
押した位置から 6 px 以内なら「クリック」）、`Tab`、HUD の行、エディタ上部の 2 つのファイルボタン。
クリックの当たり判定は「カメラから地面（y=0 平面）へのレイ → 落ちた点から 1.6 以内で最も近い生き物」。
Bevy の picking も物理も入れていないので、平面と距離で足りる。

## 6. 「1 判断あたりのフレーム数」をどう測ったか

計画書が HUD に求めているのはこれで、**正確に定義して測る**のが半分の仕事だった。

生き物のタスクは短く走っては止まる。止まる理由は 2 つしかない: 何か聞いた（コンポーネント読み
`me[:Hunger]`、またはゲームへの質問 `garden.nearest`）か、寝た（`sleep`）か。
どちらの質問も `RubevySet::Answer` の同じフレームで答えられるので、次のフレームには起きられる。
なので **frames/decision＝聞いたバーストと答えを受け取ったバーストの間のフレーム数**。
2 種類の見分けは:

* `answer_garden`（＝答えるシステム）が、答えた相手の `Mind::asked_frame` に今のフレーム番号を書く。
  その番号から始まる空白は**ゲームへの質問の往復**で、それと分かっている。
* それ以外の空白で、`ruby/` の中で一番短い `sleep`（0.05 秒、`run_creature` の 1 行）より短いものは
  **コンポーネント読み**。これは rubevy が `answer_components` で自分で答えてしまうので、
  ゲームからは `Request` として見えない。
* それより長いものは `sleep`。判断ではない。

「0.05 秒より短い」は許容誤差ではなく、`ruby/` の中身についての事実（`SHORTEST_SLEEP`）で、
フレーム時間から毎フレーム換算している（60 Hz なら 3 フレーム）。

実測（`--headless 25`、`hud:` 行の最後）:

```
hud: frames/decision — 403 questions the game answered, 1.000 frames each;
                       2352 component reads, 1.000 frames each
```

**どちらもちょうど 1。** これが `answer_garden` を `RubevySet::Answer` に置いていることの値段で、
どこか後ろに置けば全部 2 になる（battle-followups で測った話の、箱庭側の裏取り）。
生き物ごとの数字は HUD の `f/dec` 列と、headless の `hud:` 行。

もう 1 つの HUD の数字、**VM がこのフレームに使った時間**は `RubevySet::Tick` の前後で
`Instant` を挟んで測っている（`VmClock`）。壁時計であって CPU 時間ではないが、
比べる相手（`ScriptWorld::frame_time` = 8 ms）が壁時計なのでこれでよい。15 匹で **1.3 / 8.0 ms**。

## 7. headless でも同じものが出る

窓が無い機械のために、`--headless` の最後に HUD と VM パネルを**文字で**出す（sabibots と同じ形）:

* `hud:` の 1 行目が全体（生き物の数・草・昼夜・VM 時間 / 予算）、
* `hud:   Beetle 99v0  hunger 92.1  13 insn/frame  1.0 frames/decision  beetle.rb:125` が 1 匹ぶん、
* `vm:` は `VmInspector::log_lines()`、つまり VM パネルが描くのと同じ中身
  （フレーム・ローカル・ヒープ・コンテキスト数）。

## 8. 窓の判定（`GARDEN_SELFTEST=1` + 窓）

headless では押せないもの — エディタのボタンと 2 つのキー — を sabibots と同じやり方で押す
（`Editor::action` を立てる＝クリックと同じ経路）。Save だけは repo を書き換えるので外してある。

判定は**キーを先、エディタを後**にしてある。逆の順で書いたら「一時停止しても再開しない」で
落ちて、原因は一時停止ではなく**その前の Apply** だった（5a）。スケジューラについての判定を
スクリプトを入れ替えたあとに置くと、入れ替えについての判定になってしまう。

`docker` + lavapipe で 21 行、全部 `ok`:

```
selftest: ok   P pauses: the scripts' budget is 0
selftest: ok   nothing ran while it was paused
selftest: ok   the VM panel has the creature's frames
selftest: ok   the panel has the heap counters
selftest: ok   nothing that was sleeping woke on the resume frame: the next one is due in 6 ticks, as it was half a second ago
selftest: ok   P again gives the budget back
selftest: ok   the creatures are thinking again
selftest: ok   F2 hides the VM panel
selftest: ok   F2 shows it again
selftest: ok   the editor shows the file of the creature that was clicked
selftest: ok   typing marks the text edited
selftest: ok   Apply restarts every beetle on the edited text
selftest: ok   a beetle born from now on is born running it
selftest: ok   the rabbits are left alone
selftest: ok   Apply does not touch the file
selftest: ok   after Apply the text is what the beetles run
selftest: ok   every restarted beetle's new task has run
selftest: ok   the whole VM is still running afterwards
selftest: ok   Revert puts every beetle back on the file
selftest: ok   Revert shows the file again
selftest: ok   nothing was written
selftest: Rabbit 400v0 — 21 ask round trips, 83 component reads, 1.00 frames/decision
```

`「nothing ran while it was paused」`は最初 FAIL した。`test.insn` を **P を押したフレームで**
取っていたからで、そのフレームのスクリプトはキーを読む前にもう走っている。次のフレーム
（＝一時停止が効いてから）で取るように直した。

`「every restarted beetle's new task has run」`も最初 FAIL した。待ち行列が空になった瞬間に見ていて、
最後の 1 匹がまだ 1 フレームも走っていなかった。空になってから 0.6 秒置くようにした。

## 9. 細かいこと

* **`Editor::show` の鍵は種の番号にした。** sabibots は `Entity::to_bits`。箱庭で entity にすると、
  同じ種の別の個体をクリックするたびに「別のスクリプト」に見えて、打ちかけの編集が draft に
  仕舞われてしまう。ファイル 1 枚＝鍵 1 つなら、甲虫の間を歩き回っても打った文字はそのまま残る。
* **egui とマウスの取り合い。** `orbit_camera` に `EguiWantsInput::wants_pointer_input()` を 1 つ足した。
  これが無いとパネルの中でドラッグした瞬間にカメラが回る。キーボード側は sabibots と同じ
  `wants_keyboard_input()`（コードに打った `p` が一時停止になってはいけない）。
* **HUD の行の順は種→entity 固定。** 生まれたり餓死したりで行が飛び跳ねると読めない。
* **`Mind` に heat を足した。** エディタの行の陰影（どの行に戻ってき続けているか）は
  sabibots では `Robot::heat`。`watch_minds` が毎フレーム 0.985 倍して今いる行に +1 する。

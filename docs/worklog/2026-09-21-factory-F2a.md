# 2026-09-21 3 本目 Factory の F2a — ベルト上の位置を f32 から整数の刻みへ

計画書 `docs/plans/factory-plan.md` §6 の F2a の行が仕様。作業場所は worktree
`rubevy_games-wt-factory`（ブランチ `factory`、着手時の先頭は `3a059bf`）。
着手前: `cargo build --workspace --all-targets` 警告 0、`cargo test --workspace` **95 通過**、
`grep -rn unsafe factory/` 0 件。

この段階でやったことは 2 つある。

1. **ベルト上の位置を「1 タイル = 16 刻み」の整数にした。** F1 が `0..=1` の `f32` で持っていた
   位置を `i32` の刻み（1 刻み = 素材 1 画素）にし、隙間・速さ・描画・機械の出し入れを全部その
   単位に揃えた。F1 が「数として成り立たない」と書いた「隙間 N 個の列に N+1 個」が、通る値の
   全部で厳密に成り立つようになった。
2. **`ore_per_tile` を `factory.settings.txt` から `ruby/data.rb` へ移した**（計画 §7 の 09-21 F2
   の行、本体が原則から決めた (ii)）。新しい語 `ore` を 1 つ足した。

## 1. 位置の型をどう決めたか

計画書は「`u16` か `u32` か `i32` か」を、**渡すときに 1 タイルを越える値**（F1 の `.min(2.0)`）と
**引き算の向き**を見て決めろと言っている。両方見た。

**符号は要る。** 模型の中で位置は 2 か所で負になる。

* `carry` と `hold` の「前の 1 つから `spacing` を引いた所」。列が長ければ引き算の連鎖は
  タイルの後ろへ出ていく（`limit = p.along - spacing` を繰り返す）。
* テストと判定と `--stress` が列を仕込むとき（`-(i) * spacing`）。これは「1 つ前のタイルの
  上にいる物を、このタイルの側から見た位置」で、**世界のどこかを指している本物の座標**である
  （位置 0 はタイルの入口の辺 = 1 つ前のタイルの 16）。

符号なしにすると、この 2 か所が「0 で止まる」か「下から回り込む」かのどちらかになり、
どちらも模型の意味を変える。だから `i16` か `i32`。

**32 ビットにした理由。** 上限の側は 2 つある。

* **渡すときの上限**は 2 タイル = 32 刻み（F1 の `.min(2.0)` がそのまま `2 * tile` になった）。
  これだけなら `i16` で足りる。
* **1 フレームの歩幅**は `tiles_per_second × 16 × dt` で、`tiles_per_second` は `data.rb` に
  プレイヤーが好きな正の数を書ける。既定の 2.0 なら 1 フレーム 0.53 刻みだが、10000.0 と
  書かれたら 1 フレーム 2,666 刻みになる。`i16` だと**データファイルの数がオーバーフローを
  起こせる**（デバッグビルドで panic、リリースで回り込み）。

f32 → 整数の `as` はクランプする（Rust 1.45 以降）ので、変換の側はどんな数でも
`i32::MAX` で止まる。足し算の側は最初 `saturating_add` / `saturating_sub` にした
（**§7 で `i64` の計算に置き換えた** — 同じことを速さの代償なしに言えるから）。
**これで「プレイヤーが書ける数でオーバーフローしない」が型と演算で言い切れる。**
`i16` にすると 4 バイトの `OnBelt` に戻せる（今は `i32` + `u16` + 詰めで 8 バイト、F2 と同じ）
が、そのためには「速さの上限」という**出どころの無い数**を新しく足すことになる。足さなかった。

型は `pub type Steps = i32;` という別名にして、rustdoc に上の理由を書いた（`belts.rs`）。

## 2. 速さの端数をどこに持つか

毎フレームの歩幅は `tiles_per_second × 16 × dt` 刻み。既定（2.0 タイル/秒、60 fps）では
**1 フレーム 0.533 刻み**で、切り捨てると **ベルトは 1 ミリも動かない**。四捨五入すると
1 フレーム 1 刻み = 秒速 3.75 タイルになり、**フレームレートが速さを決めてしまう**。
だから端数は失わずに持ち越す。

**どこに持つか**は計画書が条件を書いている:「同じ速さのベルトが同じフレームに同じだけ進む」。
持ち方の候補は 3 つあった。

| 案 | 同じ速さのベルトが同じだけ進むか | 備考 |
|---|---|---|
| (a) アイテムごと | **いいえ** | 隣り合う 2 個が違う量だけ進めば隙間が壊れる。不変条件と矛盾する |
| (b) ベルト（タイル）ごと | 進む（全部同じ値を足すので同期する） | 地図ぶんの `f32` を毎フレーム舐める。同期していることに意味が無い |
| (c) 工場に 1 つ | 進む（**構造上そうなる**） | `data.rb` の `belt` は 1 つだけなので、速さは 1 種類しかない |

**(c) を選んだ。** 理由は「安いから」ではなく、条件を**構造で**満たすから: 1 つしか無いものは
ばらけようがない。`Lanes::part_of_a_step` に置いた（`Lanes` は「アイテムがどこにいるか」の
資源で、これはその一部である）。rustdoc に「速さが 2 種類になったら、**速さごとに 1 つ**で
あってタイルごとではない」と書いた。

```rust
fn take_a_step(&mut self, rules: &Rules, seconds: f32) -> Steps {
    let wanted = self.part_of_a_step
        + rules.belt_tiles_per_second * TILE_PX as f32 * seconds.max(0.0);
    let whole = wanted.floor() as Steps;          // `as` はクランプする
    self.part_of_a_step = (wanted - whole as f32).clamp(0.0, 1.0);
    whole.max(0)
}
```

`clamp(0.0, 1.0)` の上限が効くのは変換がクランプしたときだけ（余りは定義上 0 以上 1 未満）。
「飽和したフレームはもう地図の端より先を要求しているので、持ち越す意味のある端数は無い」と
コメントに書いた。

**確かめ方**（`belts.rs` の `the_same_seconds_carry_an_item_the_same_way_at_any_frame_rate`）:
同じ 2 秒を **60 fps** と **5 fps**（ブラウザで実際に出る値）で走らせ、進んだ刻みを比べる。
速さが言う距離は 2 タイル/秒 × 2 秒 × 16 = **64 刻み**。

```
60 fps: 64 刻み   5 fps: 64 刻み   速さが言う値: 64 刻み
```

主張は「**1 刻み以内**」にしてある。0 ではなく 1 なのは、位置が整数の刻みだから:
フレームの切れ目がどちらに落ちるかで 1 刻み（= 素材 1 画素）ずれうるし、それより細かい答えは
模型が持っていない。持ち越しが無ければ 60 fps 側は 0 刻みになるので、このテストは
「端数を捨てた実装」を落とす。

## 3. `items_per_tile` の受け方と、断る文面

隙間は `16 ÷ items_per_tile` 刻みで、**割り切れないと隙間が隙間でなくなる**。
だから `items_per_tile` は 16 の約数（1・2・4・8・16）だけ。

**綴りは `2` にしたが、`2.0` も通る。** `data.rb` の既定を整数 `2` に書き換えたうえで、
受け口は `f32` で受けて「整数か」「16 を割り切るか」を見る `deserialize_with`（`fits_a_tile`）に
した。`u32` で受けて serde に型で断らせる案と比べた:

* `u32` で受けると `2.5` は "invalid type: floating point `2.5`, expected u32" になる。
  **何が書けるかを言っていない。** しかも `data.rb` の他の数は全部 `2.0` の形で書いてあるので、
  `items_per_tile: 2.0` と書く手は自然で、それが型エラーになるのは筋が悪い。
* `f32` で受けて自分で断ると、3・5・2.5・0 の**全部**に同じ 1 文が出せる:

```
data.rb:6: an item's place on a belt is one of the 16 steps a tile is long,
           so items_per_tile is one of 1, 2, 4, 8, 16 — not 3
```

約数の一覧は `TILE_PX` から計算して文面に入れている（`1..=16` のうち割り切るもの）ので、
**素材の寸法が変われば文面も変わる**。手で書いた「1, 2, 4, 8, 16」はコードに無い。

なお `items_per_tile: 2`（Ruby の Integer）が `f32` として読めるかは確かめた
（`the_gap_between_items_has_to_divide_a_tile` が `2` と `2.0` の両方を通している）。
sabiruby-serde は自己記述的に数を渡すので、整数でも浮動小数でも `f32::deserialize` が受ける。

## 4. `ore_per_tile` をどの語に載せたか

計画 §7 の 09-21 F2 の行（本体の決定 (ii)）。候補は「`miner` の `digs:` の隣」と
「鉱石の畑を言う新しい語」で、**新しい語 `ore` にした**。

理由は F2 が「6 語にした理由」としてコードに書いたものをそのまま当てただけである:
語を分けるのは、**`deny_unknown_fields` がその行で断れる**ようにするため、そして
「その語のものでない数」を持たせないため。F2 の言葉では「かまどの `capacity:` が serde を
通ってしまう」形を避けるため。`ore_per_tile` は**地面の数**であって、ドリルの数ではない。
`miner` に載せると、避けたはずの形をこちらから作ることになる。

```ruby
ore :patch, per_tile: 60
```

**名前 `:patch` はラベル**で、`belt :conveyor` / `chest :crate` / `miner :drill` と同じく
どこからも引かれない。`ore :iron_ore` と書く案（名前がアイテムを指す）も考えたが、
**罠になる**: `digs:` が別のアイテムを指していても地面から出てくるのは `digs:` の方なので、
`ore :coal` と書いた人は黙って裏切られる。名前をアイテムにするなら `digs:` を消して
「地面が何であるかが、掘って出てくるもの」にするのが筋だが、それは語の形を変える話なので
この段階でやらず、**報告に「著者が変えたければここ」として出す**。

**`ore_patch_radius` は設定に残る。** `map_tiles` の下限（`Ore::smallest_map`）が `main()` の中、
**VM がまだ無い所**で要るから（F2 の §4 と同じ線）。`data.rb` の `ore` の行のコメントと
`Map::ore_patch_radius` の rustdoc に、お互いの居場所と理由を書いた。

**順序は確かめた。** `Ore::laid_out` を呼ぶのは `lay_the_land` だけで、それは
`Startup` の `read_the_data_stage` の**後**に、しかも `run_if(resource_exists::<Rules>)` 付きで
走る（`main.rs`）。だから `rules.ore_per_tile` は必ず読める。`Map` からは `ore_per_tile` が
消え、`main()` の `counted()` は**使う所が無くなったので消した**（0 以下を断る仕事は
`data.rs` の `at_least_one` が引き継いでいる）。

`floor_picture`（半分を切った畑の絵）は `map.ore_per_tile` を読んでいたので、
`per_tile` を引数で受けるようにした（「絵が言うのは**残りの割合**で、量ではない」）。

## 5. 模型の側の書き換え（`belts.rs` の 4 パス）

置き換えは機械的だが、2 か所だけ形が変わった。

* **`tails` が `Vec<f32>` から `Vec<Option<Steps>>` へ。** F1 は「空の列」を `INFINITY`、
  「ベルトでないタイル」を `NAN` で表していた。整数に `INFINITY` は無いので `None` にした
  — **これは §7 で番兵（`Steps::MAX`）に戻した**。F1 の `INFINITY` の直訳はそちらで、
  `Option` は遠回りだった。読む側（`room_ahead` がベルトだと保証した隣）では
  どちらも「何も邪魔が無い」= 2 タイルになる。
* **`.min(2.0)` が `.min(2 * tile)` へ。** 意味は同じ（次のタイルの向こう端）。F1 のコメント
  （「1 フレームで 1 タイル以上進む速さでは渡す順が index に依る」）はそのまま生きている。

`carry` / `hold` / `hand_to` / `item_at` / `lay_the_snake` / 判定の仕込みが全部
「刻み」に揃った。`item_at` は**掛け算が 1 つ消えた**:

```rust
// 前: centre - came_in.as_vec() * (0.5 - along) * 2.0 * half
// 後: centre - came_in.as_vec() * (half - along) as f32      // half は 8 刻み
```

1 刻み = 素材 1 画素なので、**刻みの数がそのまま世界の長さ**である。タイルの中心は整数の
世界座標（`x*16 + 8 − span/2`）なので、アイテムの位置も整数になり、`draw::snapped` が
ズームを整数倍に丸めている限り**画面の画素にぴったり載る**。F1 は毎フレーム
「割合 → 画素」の掛け算と丸めをしていた。曲がりの道（入口の辺 → 中心 → 出口の辺）も
同じ式のままで、中心は `along == 8` の 1 点。

## 6. テストの取り直し

**F1 の 7 値のテストを 16 の約数に取り直した。**
`a_jam_keeps_the_gap_even_when_the_gap_is_not_an_exact_number` は
`a_jam_holds_one_more_than_the_gaps_that_fit` になり、主張が変わった:

| | F1（f32） | F2a（刻み） |
|---|---|---|
| 走らせる値 | 1, 2, 3, 4, 5, 7, 8 | 1, 2, 4, 8, 16（**これが書ける値の全部**） |
| 個数 | 「N か N+1」（3 のとき 3、5 のとき 6） | **N+1 ちょうど** |
| 位置 | 「隣と spacing 以上」（許容誤差 1e-5） | **`16 − k × gap` と一致**（`assert_eq!`） |

「3 のとき 3 個」は**もう起こらない**（3 は data stage が断る）。この記述は
`numbers.md` §9.3 と `belts.rs` のテストの doc から外し、経緯（なぜ f32 では成り立たず、
何を捨てて何を得たか）はここと F1 の worklog §5.2 に残した。**F1 の記録は当日の記録として
そのまま置いてある** — 直すと「測った日に何が起きたか」が消えるから。

断られる側（3・5・2.5・0）のテストは `data.rs` に置いた
（`the_gap_between_items_has_to_divide_a_tile`）。行番号が付くこと、文面が
「1, 2, 4, 8, 16」を含むことの両方を見ている。判定（`selftest`）の壊れたデータファイルにも
1 つ足した（`items_per_tile: 3` が 4 行目で断られる）ので、**ブラウザでも同じことを見る**。

**長時間の保存則**（`nothing_is_made_and_nothing_is_lost_over_minutes_of_a_whole_factory`）:
採掘機 2 台 → 合流 → かまど（取れる量の半分しか食べないので上流は走行中ずっと詰まっている）
→ 組立機（2×2）→ 箱、を **5 分ぶん（18,000 ステップ）**回し、**1 秒ごとに**
「掘った数 = 箱 + ベルト + 機械の中（作りかけの材料も）」を鉱石換算で比べる。
換算は `data.recipes` から計算する（`in_ore`: 出た物は入った物の値段。歯車 = 板 2 枚 = 鉱石 2）
ので、レシピを変えるとテストが追従する。**許容誤差は無い**（`assert_eq!`）。
18,000 ステップで 1 個も狂わなかった。テストの所要は 0.02 秒。

## 7. 速さ — 遅くなったので、理由を見て直した

`--stress` で工場の 1 歩（`items::run_the_factory` が測る `step us`）を前後で取った。
**前**は `3a059bf` の release バイナリをスクラッチパッドへ copy して `md5sum` で別物だと確かめた
もの。前のバイナリは**この worktree の `ruby/data.rb` を読む**（パスがビルド時に焼き込まれる）
ので、走らせる直前に F2 の `data.rb` を置き、終わったら必ず戻すスクリプトにした
（`ore` の語を知らないので、新しいファイルでは data stage が止まって工場が建たない）。

**最初の測定（交互 3 巡、機械はやや混んでいた）で 8〜9% 遅くなっているのが見えた。**

| items | 前 step µs p50 | 後 step µs p50 |
|---|---|---|
| 4,000 | 48・49・49・48 | 52・52・53・53 |
| 16,000 | 185・186・181・179 | 200・198・199・196 |

理由は 2 つあって、どちらも「整数にしたから」ではなく**整数の書き方**だった。

1. **`tails` を `Vec<Option<Steps>>` にしていた。** F1 は `Vec<f32>` で、空の列を `INFINITY`、
   ベルトでないタイルを `NAN` で表していた。整数に `INFINITY` は無いので `Option` にしたが、
   `Option<i32>` は **8 バイト**（`i32` は 4）で、しかも中身を取り出す分岐が運ぶパスの真ん中に
   入る。この配列は**毎フレーム地図ぶん書いて、ベルトごとに 1 回読む**。
   `Steps::MAX` を番兵にすれば F1 の `INFINITY` の直訳になり、分岐も消える。
2. **`saturating_add` / `saturating_sub` を 1 アイテムごとに呼んでいた。** 飽和は
   「加算 + フラグを見て cmov」なので、浮動小数の 1 命令の加算より数命令多い。
   これがアイテムの数だけ効く。飽和が要る理由（`data.rb` に好きな速さを書ける）は本物だが、
   **64 ビットで計算すれば飽和は要らない**: `i32` 同士の和は `i64` に必ず収まり、結果は
   2 タイル以下の `limit` で `min` されるので、`i32` へ戻すときに丸めは起きない。
   x86-64 では 64 ビットの加算・比較は 32 ビットと同じ速さである。

両方直した（番兵 + `carry` / `hold` / `room` を `i64` で）。
**直した後の測定は §7.1。**

### 7.1 取り直し — **中央値ではなく最小値で比べた**

**機械が静かにならなかった。** 隣の担当 2 人の cargo が断続的に走っていて、`vmstat` の idle は
95% と 2% の間を行き来する。この状態で中央値を取ると、同じバイナリの同じ走行が 151 µs にも
501 µs にもなる（実際に取った: 16,000 個で中央値 338 対 349、最小 153 対 156 — 中央値は
2 倍以上ぶれて何も言えないのに、最小は 2 µs しか動かない）。

そこで**最小値（best of）**にした。4 つのバイナリを **1 巡の中で順に** 走らせ（同じ背景の
負荷を 4 つとも受ける）、`taskset -c 2` で同じコアに留め、**8 巡**。各走行は 2 標本を出すので
1 つのバイナリにつき 16 標本、その最小・2 番目・3 番目を並べる。

| バイナリ | 4,000 個 step µs（最小/2 番/3 番） | 16,000 個（最小/2 番/3 番） | 前に対して |
|---|---|---|---|
| **前**（`3a059bf`、f32） | 42 / 42 / 42 | 151 / 153 / 156 | — |
| 後 (a) `Option` の tails + `saturating_` | 46 / 46 / 47 | 167 / 171 / 172 | **+9.5% / +10.6%** |
| 後 (b) 番兵の tails + `saturating_` | 45 / 45 / 45 | 165 / 165 / 211 | +7.1% / +9.3% |
| **後 (c) 番兵 + 64 ビットの連鎖（採った形）** | **42 / 43 / 43** | **149 / 150 / 159** | **±0 / −1.3%** |

別の日時に取った独立な 1 組（交互 10 巡、20 標本）も同じことを言っている:
前 42 / 153、後 (c) 43 / 156 で **+2% 以内**。2 組を合わせて読むと、**採った形は前と同じ速さ**
（測りの再現性 ±2% の中）である。

**直し方の効き目の内訳**は上の表がそのまま答えになっている: `Option` → 番兵で約 2 ポイント、
飽和 → 64 ビットで残り 8〜9 ポイント。**遅さの主因は「整数にしたこと」ではなく
「1 アイテムごとに飽和演算を呼んだこと」**だった。飽和が守ろうとしていたもの
（`data.rb` に好きな速さを書ける）は 64 ビットで計算すれば**ただで**守れる:
`i32` 同士の和は `i64` に必ず収まり、結果は 2 タイル以下の `limit` で `min` されてから
`i32` に戻るので、狭める所で丸めは起きない。

## 8. 段階の終わりの確認（コマンドと結果）

```
$ cargo build --workspace --all-targets      # 警告 0
```

### 8.1 飛ばした確認と、その理由

- **速さの「静かな機械での中央値」は取れなかった**（§7.1）。同じ機械で別の担当 2 人が
  cargo を回し続けていて、`vmstat` の idle が安定しなかった。中央値の代わりに
  **同じ巡の中で交互に走らせた 16 標本の最小値**を 2 組取り、どちらも同じ結論だったので
  「取れなかった」ではなく「別の取り方で取った」と書いている。
- ブラウザでの `--stress` の測り直しはしていない。F1 が書いたとおり SwiftShader では
  アイテム 2 個でも 1,800 個でも同じ 5 fps で、時計は 100 µs 刻みなので**差が測れない**。

## 9. 気づいた点

仕事の範囲の外で気づいたことを、直さずに書く（`implementer.md` の報告の形式 6）。

1. **飽和演算はアイテムごとのループに置くと高い。** `saturating_add` / `saturating_sub` は
   1 アイテムにつき数命令で、16,000 個では 10% 見えた（§7.1）。同じ安全性は
   「1 段広い型で計算して、狭める所で範囲が保証されていることを示す」で**ただで**買える。
   sabiruby の VM にも「毎命令の算術でオーバーフローをどう守るか」という同じ形の選択が
   あるはずで、そこが `checked_` や `saturating_` で書かれているなら測る価値がある。
   **属する先**: 本（mruby の移植の章）の素材／VM（sabiruby）で測るネタ。
2. **`Option<i32>` を大きな配列の要素にすると 2 倍の帯域になる。** ニッチ値最適化は
   参照やゼロでない型にしか効かないので、`Option<i32>` は 8 バイトである。
   毎フレーム地図ぶん書く配列だったので効いた。**属する先**: そのゲーム固有／本の素材。
3. **`--stress` の測定が「机の上の他の仕事」に丸ごと持っていかれる。** 中央値が 2 倍ぶれる
   機械で `p50` を報告する仕組みは、**何も言っていないのに何か言ったように見える**。
   `Stress` が最小値も一緒に出すか、`docs/verification` に「共有された機械では最小で比べる」と
   書くかのどちらかが要る。3 本とも同じ器を使うようになれば共有 crate の話になる。
   **属する先**: 道具／共有 crate（`games_shell` の計測の器）。
4. **`exactly_one` の文面が「a ore」と言っていた。** 冠詞を語の頭文字で選ぶ 5 行を足して
   「an ore」にした（`data::article`）。語が増えるたびに踏む形なので、次に母音で始まる語を
   足す人のために書いておく。**属する先**: そのゲーム固有（直した）。
5. **`data.rb` の `ore :patch` の名前は「ラベル」で、`digs:` と二重に見える。** 今は
   `ore` の名前をどこも読んでいないので、`ore :coal` と書いて `miner digs: :iron_ore` の
   ままにしても地面からは iron_ore が出る。**名前をアイテムにして `digs:` を消す**形
   （地面が何であるかが、掘って出てくるもの）のほうが筋は通るが、語の形を変える話なので
   実装せず報告に出した。**属する先**: 著者判断（`data.rb` の語の名前）。
6. **F1 の「アイテムの表現 2.2〜2.9 倍」は F2a でも取り直していない**（F2 の気づいた点 6 の
   続き）。エンティティ側のコードはもう無いので比は取れないが、lanes の絶対値は
   §7.1 の表が今の数である（4,000 個 42 µs、16,000 個 149 µs、窓なしの PC）。
   **属する先**: そのゲーム固有。

## 10. F3 へ渡すこと

- **インサータが位置を読む・書くときの単位は「刻み」**（`belts::Steps`、1 タイル = 16）。
  Ruby に見せるなら、`answer_in_tick` が返せるのは平たい値なので**刻みの整数をそのまま**
  渡せる（`f32` に直して渡すと、F1 が捨てた丸めが Ruby 側に戻ってくる）。
  「タイルの何割か」を見せたいなら prelude で `along / 16.0` にする。
- **位置 0 はタイルの入口の辺**で、1 つ前のタイルの 16 と**世界の同じ点**である。
  インサータが「後ろのタイルから取る」とき、どちらの側の座標で言うかを決めること。
- **ベルトに載せる口は `machines::hand_to`** で、そこが唯一「隙間が空いているか」を見る
  （`last.along >= spacing`）。インサータもその口を通ること。**位置 0 に置く**ので、
  刻みの計算はインサータの側に要らない。
- 端数（`Lanes::part_of_a_step`）は**ベルトのもの**で、インサータの腕の動きとは無関係。
  腕にも端数が要るなら、同じ理由で「速さごとに 1 つ」を考えること。
- F2 が残した 3 件（建てる依頼のメッセージ、`checks_end_the_run()` への乗り換え、
  `ore_per_tile` の引っ越し）のうち、**`ore_per_tile` は F2a が済ませた**。残り 2 件は
  F3 の最初のまま。

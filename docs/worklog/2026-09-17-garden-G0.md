# 箱庭 G0 — 世界だけを Rust で、3D で

`docs/plans/garden-plan.md` の G0。ブランチ `garden-g0`、worktree は `rubevy_games-wt-garden`。
スクリプトは 1 行も走らない段階なので、書いたものの半分は「G1 で Ruby から名前で見えるための条件」を満たすためのもので、
残り半分は「見えるものが無いと世界が動いているか分からない」ための仮の脳。

## 先に確かめたこと

計画書の「依存関係」を先に見る、という指示に従って、rubevy の `docs/host-api.md` を頭から読んだ。G0 で要るのは 2 つだけだった:

* コンポーネントが Ruby から名前で見える条件 — 「`#[derive(Reflect)]`、`#[reflect(Component)]`、`app.register_type::<T>()`。
  登録されていない型は Ruby 側でエラーにならず、`nil` として読め、`has?` は `false`、`components` に出ない」。
  **登録しないことが唯一のアクセス制御**だと読める。これは実装の方針に直接効いた（後述の `Wander`）。
* `ScriptWorld::publish(entity, name, payload)` — 「誰も subscribe していない名前には何も積まれないので、ゲームは自由に publish してよい」。
  G0 では購読者が 0 なので、`publish` は全部空振りする。それでも呼ぶ場所を先に作っておけば、G1 は `reflex(:touched)` を書くだけで済む。

`MinimalPlugins` は `Transform` を登録しない、と同じ文書に書いてある（bevy 0.19 の `reflect_auto_register` は rubevy が有効にしていない）。
headless が確認の場である以上、`app.register_type::<Transform>()` は自分で呼ぶ必要がある。呼んだ。二重登録はエラーにならない。

## workspace の features

`bevy_pbr` を足すだけでは足りなかった。`Camera3d` の既定のトーンマッパー（TonyMcMapface）は曲線を KTX2 のルックアップテーブルから読むので
`tonemapping_luts` が要り、それは `bevy_image/zstd` を要求する。`bevy_image` の `zstd` は**中身の無いマーカー feature**で、
実装は `zstd_c`（C の libzstd）か `zstd_rust`（ruzstd）のどちらかを別に選ぶ形になっている（`bevy_image-0.19.1/Cargo.toml:63-71`）。
G5 のブラウザ版を考えると C は避けたいので `zstd_rust` を選んだ。結果、workspace の `bevy` に足したのは
`bevy_pbr` + `tonemapping_luts` + `zstd_rust` の 3 つ（`ktx2` は `tonemapping_luts` が連れてくる）。
sabibots は 2D でこれを 1 行も使わないが、workspace の `bevy` は 1 つなのでビルド時間だけ払う。これは「Bevy は 1 つ」という repo の方針の代金で、
分けるなら features ごと分けることになり、それは「binary に Bevy は 1 つ」という前提を壊す。払うことにした。

bevy 0.19 で `DirectionalLight` のフィールドは `shadows_enabled` ではなく `shadow_maps_enabled` だった（コンパイルエラーで気づいた。rustc が
正しい名前を出してくれたので調べ直していない）。`AmbientLight` は 0.19 ではカメラに付ける**コンポーネント**で、既定値の方が
`GlobalAmbientLight` という**リソース**（`bevy_light-0.19.1/src/ambient_light.rs:41-59`）。昼夜で毎フレーム動かすのはリソースの方にした。

## headless で 3D をどう走らせるか

sabibots の headless は `MinimalPlugins` + `LogPlugin` + `AssetPlugin` + `RubevyPlugin` に `.init_asset::<Image>()` を足して、
描画しないまま同じシステムを回している。3D で同じことをすると `Assets<Mesh>` と `Assets<StandardMaterial>` が無い。
`init_asset::<Mesh>()` と `init_asset::<StandardMaterial>()` を足したら、レンダラ抜きでそのまま通った。
おかげで **startup が両方のモードで完全に同じ**になり、headless が確かめている世界は窓が見せている世界と同じものになる。
`GlobalAmbientLight` と `ClearColor` だけは render 側のプラグインが入れるので headless には無く、そこは `Option<ResMut<_>>` で受けている
（`day_night` の中の 2 か所。無ければ光の色を計算して捨てるだけで、`publish` は同じように起きる）。

## 仮の脳（G1 が消すもの）

生き物が `Velocity` を自分で書かない段階なので、誰かが書かないと世界は静物になる。
`Wander { until: f32 }` というコンポーネントを足して、1 秒前後ごとに向きを引き直すシステムを 1 本入れた。
**このコンポーネントは `Reflect` を derive していないし `register_type` もしていない**。上に書いた「登録しないことがアクセス制御」を使って、
Ruby から見える表（`docs/garden.md` のコンポーネント表）を計画書が挙げた 7 つちょうどに保っている。
G1 は `wander` システムと `Wander` を消して、`me[:Velocity] = [vx, vz]` に置き換えるだけでよい — 他のシステムは `Velocity` しか見ていないので、
誰が書いたかを知らない。

## selftest の 3 つ目をどう決定的にするか

「10 秒以内に誰かが食べる」と「60 秒で夜が来る」は世界の作りから素直に出る。3 つ目の「餓死したエンティティが消える」が困った。
餓死は「食べられなかった生き物」に起きるが、仮の脳はランダムに歩くので、40×30 に 55 株ある草地では 90 秒のうちにたいてい何か食べてしまう。
最初は「空腹の初期値を散らして、いちばん空いている個体を見る」案を考えたが、これは運任せで、FAIL が出たときに世界のバグなのか運なのか区別できない。捨てた。

採ったのは、`GARDEN_SELFTEST=1` のときだけ**餓死する個体を 1 匹置く**という形。隅（-17, -12）に空腹 3.0 の Beetle を 1 匹置き、
`Wander` を**付けない**。付けなければ動かない（動かすのは `Wander` だけだから）ので、2 秒ほどで確実に餓死する。
ついでに初期配置で、その地点から半径 6 以内に草を生やさないようにした。世界の規則には一切手を入れていない — 置いた個体は
ごく普通の Beetle で、違うのは「脳が無い」ことだけ。これは G1 で「脳が無い生き物は死ぬ」という形でそのまま意味を持つ。

エンティティが消えたことの確認は `Query<Entity>` に対する `contains` で見ている。草は走っている間に生えては消えるのでエンティティ ID は再利用されるが、
`Entity` の比較は generation を含むので、同じ index の別個体と取り違えることはない。

## 3D で Ruby 側に出る差

計画書が「頭脳のコードは 2 行しか変わらない」と言っているところを、実装の側から確かめた。変わるのは

* 位置が `[x, y, z]` の 3 要素になる（`e[:Transform][:translation]`）。生き物は y = 0 の面にいるので、使うのは 0 番目と 2 番目。
* `act(vx, vz)` — `Velocity(Vec2)` の `x` が world X、`y` が world Z。

の 2 つだけ。`Transform.rotation` は Rust が進行方向から決めていて、Ruby は読む必要がない。
草の大きさが `Transform.scale` にも出るのは 2D でも同じだったので、3D の代金ではない。

メッシュは全部**子エンティティ**に置いた（`spawn_plant` / `spawn_creature`）。親の `Transform` は位置と向きと大きさだけで、
甲虫のカプセルを寝かせる 90 度回転のような「見た目の都合」は子が持っている。こうしておくと G0a で `.glb` に差し替えるときに
コンポーネントが 1 つも変わらないし、Ruby が読む `Transform` に見た目の都合が混ざらない。

## Hunger の向き

計画書の規則の欄に「Creature と Plant が重なったら `Hunger` が減り」とあるが、同じ計画書の
`Hunger(f32)`（0 で餓死）と G1 の `if me[:Hunger] < 30 then 草を探す` とは逆になる。
後者 2 つが整合しているので、**`Hunger` は満腹度（0 が死、100 が満腹、食べると増える）** として実装した。
名前としては「空腹メーター」で、減っていくもの、と読むのが素直。著者の確認が要るなら報告に書く。

## 撮影

WSL には Vulkan ドライバが無いので `--shot` は `docker/run.sh` の lavapipe 経由（`docs/wsl-gpu.md`）。
ただし `docker/build.sh` はコンテナの中で名前付きボリュームに向けてもう一度 Bevy を全部ビルドする。
ホストで release を 1 回ビルドした直後にそれをやるのは無駄なので、**ホストの `target/` をコンテナに mount して、
ホストでビルドした実行ファイルをコンテナの中で走らせた**。ホストは Ubuntu 22.04（glibc 2.35）、イメージは Debian bookworm（glibc 2.36）で、
古い方でリンクした実行ファイルは新しい方で動く向きなので、これで通る。

## 途中で増えた要求 — 当たり判定

G0 のコミット（`2ece3a6`）を打ち、撮影と `web/build.sh` の確認まで終えた段階で、著者が計画書に
**当たり判定**の項を足した（main の `2299365`「garden — collision between creatures, trees and rocks」、
同時に `57fcd2e` で G5 が必須になったが、これは G0 の範囲ではない）。
作業ブランチに main をマージしてから（`4f98a5b`）実装した。増えたのは次の通り。

* `Collider { radius: f32 }` を Reflect 登録して生き物・木・岩に付けた。Ruby からは `e[:Collider]` で読める。
* `Tree` と `Rock` を `Plant` とは別のコンポーネントとして追加（どちらも Reflect 登録）。木 7 本、岩 9 個。
  草に Collider を**付けない**のは、草に触ることが食事だから。この非対称が「食えるもの／避けるもの」の定義そのものになった。
* 移動の後に走る `separate` システム。XZ の円を半径の和まで押し戻す。生き物どうしは半分ずつ、木・岩は動かない。
  近傍は 1.6 単位のマスの格子（`HashMap<(i32,i32), Vec<usize>>`）で拾う。
* 4 つ目の selftest:「90 秒間、中心距離が半径の和の 90% を下回るフレームが無い」。

### 決めたこと 3 つ

**1 フレームに何パス押すか。** 1 パスだと 2 体のもつれは解けるが、3 体・4 体が固まったときに残る。
selftest は「1 フレームでも下回ったら FAIL」なので、残ったフレームがそのまま FAIL になる。4 パスにしたら 3 回の 90 秒走行で
最接近が 0.974 / 0.998 / 1.000（半径の和に対する比）、0.9 を下回ったフレームは 0 だった。2 パスや 3 パスは試していない。
4 で足りているものを削る理由が無かったからで、詰めるなら生き物を数十体にしてから測るのが筋だと思う。

**初期配置。** selftest は最初のフレームも見る。`separate` は `watch_overlap` より前に走るが、生き物が最初から
木の中や互いの中に置かれていると、1 フレームの 4 パスでは押し出しきれずに 0.9 を下回ることがある。
そこで配置の側を直した: 木と岩は互いに 1.5 以上離して置き（**岩どうしは押し戻さない**ので、重ねて置いたら永久に重なったままになる）、
生き物は木・岩から半径の和 + 0.6、互いに 2.0、草から 2.5 離れた場所を最大 40 回の棄却で選ぶ。
「規則が直せないものは配置で作らない」という分担になった。

**`"bumped"` をいつ出すか。** 計画書は「押し戻されたフレームに publish」と書いている。字義通りにすると、木に寄りかかった生き物は
向きが変わるまでの 1.5 秒ほど、毎フレーム（≒90 回）publish することになる。rubevy のキューは 64 で古いものから落ちる
（`docs/host-api.md`「Events」）ので、1 つの出来事でキューが埋まり、G1 の `reflex(:bumped)` が延々と走る。
`"touched"` と同じく**接触が始まったフレームだけ**にした（「押し戻されたフレーム」のうち最初の 1 枚、という読み）。
判定の重複を避ける鍵は 2 つのエンティティの `to_bits` を小さい順に並べた組にしている — クエリが歩く順に依存しないように。
著者が字義通りを望むなら 1 行で戻せる。

### 測ったもの

```
selftest: ok   nothing walked through anything over 5363 frames (closest pair 0.998 of the radii, 0 frames under 0.9)
selftest: ok   nothing walked through anything over 5366 frames (closest pair 1.000 of the radii, 0 frames under 0.9)
selftest: ok   nothing walked through anything over 5357 frames (closest pair 0.974 of the radii, 0 frames under 0.9)
```

`watch_overlap` は格子を使わず総当たりで見ている。生き物 10 + 木 7 + 岩 9 で 26 個、325 組で、5300 フレームでも何ともない。
確かめる側が確かめられる側と同じ格子を歩いたら、格子のバグを格子で確かめることになる、というのが理由。

## ブラウザ版への影響（実測）

`web/build.sh`（sabibots）は features を足した後も通った。`game_bg.wasm` は 35,945,484 バイト（gzip 9,307,627）。
ただしこの環境に `wasm-opt` が無く（スクリプトが "wasm-opt not found: the game's module is not shrunk" と言う）、
`docs/web.md` が記録している 26.7 MB は `wasm-opt -Os` をかけた後の値なので、**この 35.9 MB と直接は比べられない**。
比べられるのは「通るかどうか」だけで、通った。`docs/web.md` の数字は条件が揃っていないので**書き換えていない**。
garden 自身の wasm はまだ測っていない（G5）。

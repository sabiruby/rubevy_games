# SabiRuby 0.8 と rubevy 0.3 — 依存のバージョンだけ

2026-10-19。SabiRuby の `docs/plans/release-0.8-plan.md` の R5（下流のバージョン上げ）。著者の指示（2026-10-19）は
「R5 の下流のバージョン上げ、進めて」。先頭は main の `232ce84`。rubevy は同じ日に 0.3.0 にした（rubevy main `3525007`、
まだ push していない）。sabiruby-playground は `2acc616`（`SABIRUBY_REF` を v0.8.0 に。これも push 前）。

## 1. 変えたもの

- `Cargo.toml` の 3 行: `sabiruby "0.7"→"0.8"`、`sabiruby-compiler "0.4"→"0.5"`、`sabiruby-serde "0.3"→"0.4"`。コメントの
  「0.7 goes with rubevy 0.2」を「0.8 goes with rubevy 0.3」に、compiler の「0.4 is the one of a 0.7 VM」を「0.5 is the one of a 0.8 VM」に。
  rubevy と rubevy-build は git のまま（指す先は `Cargo.lock` が決める）。
- `.github/workflows/pages.yml` の `PLAYGROUND_REF` を `5337b2f` → `2acc616`（3 節）。
- `docs/web.md` の「三つのピン」の表の「today `sabiruby 0.6.1`」を `0.8.0` に（0.7 のときに直し忘れていた）。
- **`Cargo.lock` はコミットしていない。** 0.2／0.7 のとき（`75be2d8`、lock は後の `1d0fadd`）と同じ。rubevy 0.3.0 がまだ GitHub に無いので、
  ここで書ける lock は手元の path を指したものだけで、それを main に置くと CI が建たない。rubevy の push の後に
  `cargo update -p rubevy -p rubevy-build` で lock を書き、別のコミットにする（5 節）。

ゲームのコードは 1 行も変えていない。SabiRuby の R2（SabiRuby `docs/worklog/2026-10-19-release-0.8.md` の 8 節）が写しで箱庭まで確かめており、
今回はそれを本物の木で 3 本ともやり直した。

## 2. 手元で確かめた形 — 一時的な `[patch]`

rubevy の 0.3.0 は push 前なので、git の rubevy を手元の木に向ける `.cargo/config.toml` を一時的に置いた（コミットしない。確かめの後に消した）:

```toml
[patch."https://github.com/sabiruby/rubevy"]
rubevy = { path = "../rubevy" }
rubevy-build = { path = "../rubevy/rubevy-build" }
```

R2 の 1 度目のしくじり（lock が git の rubevy 0.2.0 を固定していて patch が「not used」のまま VM が 2 つ入る）を避けるため、
先に `cargo update -p rubevy@0.2.0 -p rubevy-build@0.2.0` をした（`Removing rubevy v0.2.0 (…#07a5e959)`、`Adding rubevy v0.3.0 (…/rubevy)`、
同時に `sabiruby v0.7.0 -> v0.8.0`、`sabiruby-compiler v0.4.0 -> v0.5.0`、`sabiruby-serde v0.3.0 -> v0.4.0`）。
`cargo tree -i sabiruby -e normal` は `sabiruby v0.8.0` が 1 つ。

## 3. `PLAYGROUND_REF` を動かした理由

`docs/web.md` の「Three pins, and they are one pin」の手順は「VM を上げる（ピン 1）→ その版を `SABIRUBY_REF` に持つ playground の commit を探すか作る
（ピン 3）→ それを `PLAYGROUND_REF` に（ピン 2）」。0.7 のときは動かさなかった（`5337b2f` の `SABIRUBY_REF` は v0.6.1 のまま）が、
今回は playground 側に `SABIRUBY_REF` = v0.8.0 の commit（`2acc616`）を作ったので、手順どおりそれを指した。

建つかどうかは動かしても動かさなくても同じ: `git diff --stat 5337b2f 2acc616` で README・docs・`.github`・`wasm/Cargo.lock` を除くと差は無く、
`wasm/src` は同じ。その木を v0.8.0 と同じソース（隣の `../sabiruby` = `f06a23a`、tag の 1 つ後で docs だけ違う）で `tools/build.sh` して
2,469,338 bytes、playground のテストも通った（playground `docs/worklog/2026-10-19-sabiruby-0.8.md`）。
**ただし `2acc616` が GitHub に無いうちに games を push すると、CI の playground の checkout が落ちる。** push の順は playground が先（5 節）。

### 箱庭の窓なしの FAIL — 0.8 のせいではないと読んだ

1 度目の窓なし走行で、つがいが 1 組だけ数えられ、子が来ないまま 90 秒が終わった。ブラウザの走行では同じ check が ok だった。
0.8 で何か変わったのかを見るため、`git worktree add --detach` で games の `232ce84`（commit 済みの lock = SabiRuby 0.7.0・rubevy `07a5e95`）を
スクラッチパッドに出し、別の `CARGO_TARGET_DIR` で建てて（バイナリの大きさが違う: 212,167,416 と 212,407,600 bytes）、
新（0.8）と旧（0.7）を交互に 10 巡回した。

```
new 1..10:  ok ×10  [5,2,5,6,6,4,9,5,8,7 pairings]   FAIL 0
base 1..10: ok ×10  [7,7,4,4,11,10,3,12,4,3 pairings] FAIL 0
```

新は 1 度目を入れて 11 回に 1 回の FAIL、旧は 10 回に 0 回。この数で差は言えない。FAIL の 1 回はつがいが 1 組しか無かった走行で、
`close_courtings` が待っている組（`courtings_open`）が残ったまま走行が終わると、子が来る前でも FAIL になる
（`garden/src/main.rs` の 7645〜7653 行、`2026-09-18-garden-leftovers.md` の 5.4 節が「つがいから子が届くまでの 1〜2 フレーム」で
引き当てた枝と同じ文面）。その 1 組がいつ数えられたかはログに出ないので、終わり際だったかは確かめていない。
深追いはせず、気づいた点に残した。

ほかに新の 2 回（6、8 巡目）で `a hungry creature with a plant in sight reached it` が `--`（「a rabbit walked into the probe」）だった。
`--` は「測れる場面にならなかった」で、FAIL ではない（`selftest-lines.md` の Verdicts の表が probe の例を挙げている）。

## 5. 本体が打つもの（順に）

```
# 1. rubevy（main 3525007）を push し、公開
git -C ../rubevy push origin main
(cd ../rubevy && cargo publish -p rubevy-build && cargo publish -p rubevy && git tag -a v0.3.0 … && git push origin v0.3.0)

# 2. sabiruby-playground（main 2acc616）を push。games の PLAYGROUND_REF がこれを指すので、games より先
git -C ../sabiruby-playground push origin main

# 3. games: この commit の上で lock を書いて別のコミットに
cargo update -p rubevy -p rubevy-build      # git の rubevy が 3525007 に、sabiruby が 0.8.0 に
cargo tree -i sabiruby -e normal            # sabiruby v0.8.0 が 1 つ
cargo check --workspace --all-targets       # （任意）lock で建つこと
git commit -m "lock: rubevy 0.3.0 (main 3525007) and SabiRuby 0.8.0 from crates.io" -- Cargo.lock
git push origin main                        # CI（pages）が 3 本を建てて出す
```

## 迷った点

- **`PLAYGROUND_REF` を動かすか**（3 節）。0.7 の前例は「建つなら動かさない」、`docs/web.md` の手順は「3 つを同じ版に」。文書の手順を採った。
  その代わり push の順に縛りが付く（playground → games）。動かさない形に戻すなら `pages.yml` の 4 行を戻すだけ。
- 箱庭の窓なしの FAIL（4 節）。交互 10 巡で再現せず、0.8 の変更とは読まなかった。

   `courtings_open` が空でないまま走行が終わった場合）。今回 11 回に 1 回出た（つがい 1 組の走行）。`selftest-lines.md` の
   「走行で動く 3 行」には入っていない。測れなかった組として `--` に回すかは check の設計の話。**属する先**: そのゲーム固有（箱庭の check）。

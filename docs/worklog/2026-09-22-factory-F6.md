## 1. 公開の配線は 2 行だった — ただし散文が 6 段階ぶん古かった

置き方をそのまま残した。**`.github/workflows/pages.yml` は 6 段階を通じて 1 度も変えていない** —
このファイルはゲームの名前を 1 つも書いておらず、`web/build.sh all` を走らせるだけだから。
（F6 で触ったのは先頭の段落の「two games」だけで、しかも「だから変えなくてよかった」と

## 2. 予算の最終の実測 — 39,000 は動かさない

F3 が `script_budget = 39,000` を決めたあと、**F4 の control stage**（毎フレーム約 200 命令）と
**F5 の `Held` への乗り換え**（prelude が 43 行短くなった）が入っている。計画 §4 の F6 の行の
とおり、上限の工場に座り直した。

器は F3 と同じ `--arms N`、release、窓なし。作法は F2a/S11 のもの: **交互に 2 巡、さらに
向きを入れ替えて 2 巡**（340→3000 を 2 回、3000→340 を 2 回、計 8 走行）、各走行の 3 回の
報告のうち最初の 1 回は捨てる。`vmstat 1 3` が 99% idle であることを確かめてから。

| 腕 | 命令 p50 | 命令 p95 | tick µs p50 | tick µs p95 | 持ち越し | 落とした | step µs p50 |
|---|---|---|---|---|---|---|---|
| **340**（既定の 32×32 が持てる上限 = 鎖 34 本） | 1,363〜1,579 | **2,227** | 139〜196 | 258〜453 | **0** | **0** | 17〜24 |
| **3,000**（どの地図も持てない数） | 10,219〜10,435 | **14,971**（1 走行だけ 17,347） | 1,157〜1,450 | 2,527〜3,410 | **0** | **0** | 108〜126 |

**命令数は決定的だった。** 同じ腕数なら走行をまたいで 1 命令まで同じで、p50 に 2 つ値が
あるのは `inserter_stagger` の `srand(me.to_i)` が腕の並びによって違う位相に散らすから。
ばらつくのは µs だけで、それは機械の事実である — rubevy の文書が
「命令数はスクリプトについての事実」と言っているとおりの形が出た。

**導出をやり直すと 36,000 になり、39,000 と区別がつかない。**

1. 速さ: 忙しいほう（3,000 台）で 10,435 ÷ 1,157 µs = **毎 ms 9,019 命令**（同じ巡の最小の
   tick で取る。中央値 1,298 µs で取れば 8,039、340 台なら 9,806）。F3 は 9,800 だった。
2. 取り分: 1 フレームの 1/4 = 4 ms（変えていない）。
3. 4 × 9,019 = **36,000**。

差は 8%。ところが **tick µs 自身が走行間で 1,157〜1,450（25%）動く**。
つまり同じ手順が今日出す幅の中に 39,000 が入っており、**自分の測定のぶれより小さく既定値を
動かすのは、数を動かしたことにならない**。動かさないと決めた。

実害の側も 0 である: **持ち越しも `dropped` も 8 走行 24 報告すべてで 0**、
既定の地図の上限での最悪フレームは予算の **5.7%**、3,000 台でも **44%**。

**F5 の窓はこの数に入っていない**（器はヘッドレスで egui は窓のあるときだけ動く）。
窓が VM の命令数を増やすことはない（パネルは `last_frame()` を読むだけ）ので、
予算の話としてはこれで足りる。窓とページのフレームの長さは §4 の `?stress` の行が言う。

## 3. ブラウザの起動の値段 — 3 つの同期コンパイル

ページでは `platform::compile` が**フレームの中から同期で呼ぶ 2 つ目の wasm モジュール**で、
その間キャンバスは白い。F2 が `data.rb` にだけ入れていた計測を、**残る 2 つにも入れた**
（`control::compile` と `inserters::compile`）。**1 回のコンパイルにつき 1 行**なので
ループの中の行にはならない（腕のほうは*テキストごと*に 1 回 — 3,000 台が同じスクリプトなら
1 回）。行頭がファイル名で `selftest:` ではないので、**どの走行の行の一覧も動かない**。

ローカルの `web/dist` を Playwright（SwiftShader、1280×720）で 3 回:

| | 1 回目 | 2 回目 | 3 回目 |
|---|---|---|---|
| `data.rb`（読んで**走らせる**まで、最初のフレームの前） | 24.3 ms | 18.1 ms | 8.8 ms |
| `control.rb`（prelude 込み 392 行） | 7.4 | 11.9 | 3.8 |
| `inserter.rb`（244 行、最初の腕が建つとき） | 0.7 | 0.6 | 0.7 |
| **3 つの合計** | **32.4** | **30.6** | **13.3** |
| `page.goto` から最後の 1 つまで | 1.07 s | 0.80 s | 0.94 s |

**ばらつきはファイルではなくモジュールが温まるぶん**である: いちばん短い `data.rb` が
毎回いちばん高く、いちばん長い `inserter.rb` が 3 番目に呼ばれるので 0.7 ms。
F2 の「`data.rb` だけで約 7 ms」に対して増えたのは、ファイル自身（F2a の `ore`、F3a の `map`）と
**プログラムが 2 本増えた**ぶん。**全部が「35 MB のモジュールを取ってきた直後の 1 秒」の
中に入る**ので、訪問者が実際に待つ秒はモジュールのほうである。

## 4. 著者が実機で 1 度測るための道

**残っている不明は地図の既定の大きさ 1 つだけで、それが待っているのは描画である。**
この機械の描画系は 2 つともソフトウェアで、F1 が「アイテム 2 個でも 1,800 個でも同じ 5 fps」と
書いたとおり測れない。F6 はここで**数を作らず、測るのを安くした**。

**(a) 1 行に必要なものを全部載せた。** `stress:` の 1 行目に**地図の大きさ**と
**GPU のアダプタ名**を足した（`RenderAdapterInfo` は main world にあり、ヘッドレスには
無いので `Option`、無いときは `no renderer (headless)` と言う）。ms の p50 は、何を描いて
いたかと何で描いていたかが無ければ意味がない。

**(b) `?arms=1` を勧める形にした。** 理由は「**`data.rb` の言う地図のまま測れる唯一の形**」
だから: `?stress=N` はベルトの輪のために地図を √(N ÷ `items_per_tile`) まで押し上げ、
`?arms=N` は √(8N) まで押し上げるが、どちらも `data.rb` の地図より小さくはしない。
`arms=1` は下から当たらないので、残るのは宣言された大きさだけになる。

**(c) URL から地図の大きさを渡す口は作らなかった。** `games_shell::checks::asked_number` の
作法では `?map=…` を足すのは簡単だが、**地図は F3a から `data.rb` の宣言**であり、ページでも
エディタで書き換えて Apply + `Ctrl+S` できる（`localStorage` に残り、次の読み込みが読む）。
URL に 2 つ目の言い方を作れば同じ数の綴りが 2 か所になる — F3a が `map :world, size:` の
綴りを `machine` の `size:` に揃えたのと同じ原則の裏返しである。手順のほうに
「エディタで書き換えて Apply」と書いた。

手順は `docs/verification/factory-on-a-real-gpu.md` に **5 行**（著者がそのまま試せる形）。

**この機械で実際に出る数**（同じページ、SwiftShader）:

```
stress: map 48x48 items=4000 belts=2116 arms=0 frame ms p50 361.70 p95 710.80 (about 3 fps) | step us p50 100 p95 200 | ANGLE (… SwiftShader driver) (Gl, Cpu)
```

**360 ms のフレームの中に、工場の計算は 100 µs しか入っていない。** `?arms=1` の
既定の 32×32 でも 306 ms。2 桁の差が全部描画で、アダプタの行が理由を言っている
（`device_type: Cpu`）。**著者の 1 行が来るまで既定値は動かさない。**

## 5. CI の 3 つの固定をローカルで再現した

本体から: F5 の push 以降 pages が 2 回赤く、何も公開されていなかった。原因は
`PLAYGROUND_REF: d72e000` の playground が `Vm::current_line` を呼んでいて、lock の
SabiRuby 0.6.1 にその名前がもう無いこと。本体が main で `5337b2f` に上げた（取り込み済み）。

**固定は 3 つあり、3 つとも同じ SabiRuby を名指している**:
lock（games の VM）、playground 自身の `SABIRUBY_REF`、games の `PLAYGROUND_REF`。
**1 つ置き去りにすると、games 自身のビルドは緑のまま**（games はその名前を呼ばない）**、
失敗するのは CI のもう一方の checkout で、公開ページは無言で前のまま残る。**

CI の「the Ruby compiler module」の段を**スクラッチパッドで再現した**（どの repo にも書かない）:
playground を `5337b2f`、sabiruby を `v0.6.1` で**隣り合わせに** clone（playground の
`wasm/Cargo.toml` が `../../sabiruby` をパスで名指すので、兄弟でなければ建たない）して
`tools/build.sh`。**通る**: `web/sabiruby.wasm: 2448533 bytes (840475 gzipped)`。
3 つの固定が揃っていることも確かめた（playground `5337b2f` の `SABIRUBY_REF` = `479924e` =
`v0.6.1` = lock の 0.6.1 のタグ）。

`docs/web.md` に「Three pins, and they are one pin」として、表・置き去りにしたときに何が
起きるか・**動かす順番**（VM → その版で建つ playground の commit → `PLAYGROUND_REF`）・
**push の前にその 1 段だけローカルで走らせる手順**を書いた。

## 7. 気づいた点

1. **`web/games.sh` の散文は、ゲームが無いうちに書くと古くなる。** §1 の表の 3 つ。
   ビルドは `{{…}}` が埋まったかしか見ない。鍵の一覧だけはゲームの `KeyCode` から
   生成する道がありうるが、3 本とも `just_pressed` を数か所で読むだけなので静的には拾えない。
   属する先: 道具／文書。**報告のみ**。
2. **`?stress` の走行はページで終われない。** `watch_the_frames` の `exit.write` は
   `Errands::left().is_none()` を見るので、ページでは永久に `Some("a page has nothing to
   exit to")` になり、**報告が 1 秒に 1 行いつまでも出る**。著者が測るには好都合なので
   直していないが、S11 が「走行が頼まれること」を 2 つ（判定と絵）に整理したのに対し、
   **計測は 3 つ目なのに `Errands` に入っていない**。PC では正しく終わる。
   属する先: 共有 crate（3 本に効く変更）。**報告のみ**。
3. **`--shot` の絵は公開の顔にならない**（F5 の気づきのとおり 3 枚に割れる）。そして
   **README にも入口のページにも絵を置く流儀がそもそも無い**（画像があるのは `docs/*.md` だけ）。
   ブラウザの判定の走行が撮る絵は、判定の最後が世界を組み直すので**空の工場**が写る。
   本体が原則から決めた: **足さない**（無い流儀を 1 本目で作らない）。要るなら 3 本ぶん
   一度に決める話。属する先: 著者判断。
4. **`RenderAdapterInfo` はヘッドレスに無い**というのは、3 本とも「絵についての事実を
   log に出す」ときに毎回当たる形である。`games_shell` に
   `fn what_draws(app) -> String` のような 1 行があれば、次のゲームが `Option<Res<…>>` の
   綴りと「無いときの文面」を考えずに済む。属する先: 共有 crate。**報告のみ**。
5. **CI の時間は 2 本から 3 本で約 4 割増える。** 実測: GitHub の runner で 1 本あたり
   コンパイル 2 分 10 秒〜2 分 28 秒 + `wasm-bindgen` と `wasm-opt` で 1 分 29 秒 ≒ **3 分 50 秒**、
   build ジョブが 9 分 10 秒 → **約 13 分**。この機械では `web/build.sh all` が 3 本で 3 分 47 秒
   （user 35 分）、`wasm-opt` だけで 1 本 14 秒。**キャッシュの効く段（依存の build）は
   増えない**ので、伸びるのは各ゲームの最終 crate のリンクと wasm の後処理だけである。
   属する先: 道具。**報告のみ**。

## 1. (1) 45,600 の写し 2 つを 1 つに

### 何が置いてあったか

S9 の報告の 1 件目そのままである。`garden/src/window.rs` と `sabibots/src/main.rs` に、
**同じ名前・同じ値・同じ出どころの段落つき**で `const INSTRUCTIONS_A_FRAME_BUYS: f32 = 45_600.0;`
が 1 つずつ。Battle 側の rustdoc は最後に「**The two copies should be one**, in a crate both games
can reach」と自分で書いていた。

2 つのバイナリにまたがるので、`[`…`]` の intra-doc link すら張れない——
`cargo doc` は今も sabibots について
`unresolved link to 'garden::window::scheduler_frames'` と言う（これは S9 からあるもので、
S10 は減らしも増やしもしていない）。

偶然同じ数ではない。**この機械のこの VM が 8 ms で買う命令数**という 1 つの事実で、
2 本のゲームは同じ VM（sabiruby、workspace で 1 つに解決されている）を
同じ機械で走らせている。

### 置き場所 — `games_shell::checks`、`CheckPace`

`games-shell` は VM を知らない（依存に rubevy も sabiruby も無い）。しかし `checks` は
「**判定が使う数**」を置く場所ではあり、この数はゲームの数ではなく判定の物差しである
（garden 側の rustdoc が S5b-5 に「a check is allowed to know how fast the machine it is running
on is」と書いていた）。`platform`（PC とブラウザの差）でも `settings`（店そのもの）でもない。
`checks` に置いた。

形は **Resource 兼ただの値**:

```rust
#[derive(Resource, Debug, Clone, Copy, PartialEq)]
pub struct CheckPace { pub instructions_a_frame: f32 }

impl CheckPace {
    pub fn of(settings: &crate::Settings) -> CheckPace { … }   // 既定 + 店
    pub fn read_from(&mut self, settings: &crate::Settings)     // 鍵 1 つ
    pub fn frames_to_wait(&self, structural: u32, budget: u64) -> u32 {
        structural + (budget as f32 / self.instructions_a_frame).ceil() as u32
    }
}

pub const INSTRUCTIONS_A_FRAME_BUYS: f32 = 45_600.0;   // 既定値の名前としてだけ
```

鍵は **`checks_instructions_a_frame`**、2 本で同じ綴り。既存の鍵の命名
（`editor_width`、`vm_regs_frames`、`hud_bar_ticks`、`camera_*`）に合わせて
「どのパネル／どの仕組みの数か」を接頭辞にした。**出どころは rustdoc 1 か所**——
S6（2026-09-20、`frame_time` を 300 µs に絞った走行の最悪フレーム 1,708 命令 = 5.7 命令/µs）と
S5b-3（2026-09-21、上限の庭を本来の 8 ms で回して 6.85 命令/µs = 54,800）の 2 つの実測を表にし、
**少なく買う方を採る理由**（この数は予算を割って「何フレーム待ってよいか」を出すので、
大きすぎると待ちが短くなり、遅いだけの VM に偽の FAIL を出す。小さすぎれば判定が遅れるだけ）を
書いた。2 本の写しとその段落は消えて、それぞれ 1 行でここを指している。

### `2` は引数にした — 別々の理由だから

計画書の指示は「`2`（構造のフレーム数）が 2 本で同じ理由から出ているのか、たまたま同じ 2 なのかを
S9 の worklog で確かめ、**別の理由なら引数にして混ぜない**」。確かめた。**別の理由である**:

| | 何を待つ errand か | 2 の内訳 |
|---|---|---|
| 箱庭 `window::STRUCTURAL_FRAMES` | **再起動** | `Script` を `Commands` で付けるのでコンポーネントが着くのはそのフレームの終わり（1）＋ rubevy の `start_scripts` がタスクにして `RubevySet::Tick` が走らせる（2） |
| Battle `HANDLER_STRUCTURAL_FRAMES` | **publish されたメッセージ** | publish は tick の後なので、起きたハンドラに順番が回る最速は次のフレームの tick（1）＋ `handler_selftest` はその `act` を答える鎖と順序を持たないので、曲がったのを**確実に**見られるのはさらに次（2） |

どちらも S6 / S9 で実測もされている（箱庭は「1 フレームに縮めると `ScriptTask` がそもそも無い」、
Battle は静かなヘッドレス 145 件が全部 2 フレーム後）。**答えが同じ 2 なだけで、
片方の errand が変われば片方だけ動く数**である。1 つに畳むと S5b-5 の
「別々の理由の待ちを 1 つの数で賄うと、片方の理由が動いたときもう片方が黙って壊れる」を
新しい場所でやり直すことになるので、`frames_to_wait` の**第 1 引数**にした。
共有したのは**割り算だけ**で、割る数が機械と VM の事実だからである。

### 呼び出し側

* 箱庭: `window::scheduler_frames(budgets, pace)` が `pace.frames_to_wait(STRUCTURAL_FRAMES,
  budgets.creature)` を返す。`pace` は `main` が `games_shell::CheckPace::of(&settings)` で作り、
  `WindowTest::after(3.0, &budgets, &pace)` に渡す（`window_selftest` は Bevy の引数ちょうど 16 個
  なので、ここで Resource を 1 つ増やす道は無い。S9 の気づいた点 7）。
* Battle: `handler_frames(budget, pace)` が同じ。`pace` は `main` が同じく店から作って
  **Resource として入れる**（`handler_selftest` は上限をポーズでないフレームに 1 度だけ計算するので、
  読むのは system の中になる。引数は 10 → 11 個）。

箱庭では Resource にしていない。窓のチェック以外に読む者がおらず、読む場所が `main` だからで、
「使われない Resource を 1 つ置く」よりは「使う所で使う」方を採った。

### 「設定が効いている」を実物で見た

S5b-1 の教訓（「設定にした」と「設定が効いている」は別の主張）に従って、**判定の上限がログに出る
形**を 1 つ足した。Battle の `handler_selftest` が上限を計算した 1 度だけ、舞台指示を 1 行:

```
selftest: a hit's handler is given 7 frame(s) — 2 structural plus a frame's worth of 200000 instructions at 45600 a frame
```

verdict（`ok  ` / `FAIL` / `--  ` / `done`）を持たないので `tools/fixedlines.sh` は落とす。
行の一覧は動かない。**無いと外から確かめようが無い**——箱庭の窓の走行は
`waited N of M frame(s) for …` の `M` で上限を言うが（S9）、Battle にはその口が無かった。
S9 の「待ちが自分の名前を名乗るまで、どの待ちが遅かったのかは測れない」は、待ちの**上限**にも
そのまま当たる。

`sabibots.settings.txt` に 1 行ずつ置いた走行（`--headless 12`）:

| `sabibots.settings.txt` | ログが言う上限 |
|---|---|
| （無し） | `7 frame(s) — 2 structural plus a frame's worth of 200000 instructions at 45600 a frame` |
| `checks_instructions_a_frame=20000` | `12 frame(s) — … 200000 instructions at 20000 a frame` |
| `checks_instructions_a_frame=20000` + `script_budget=40000` | `4 frame(s) — … 40000 instructions at 20000 a frame` |

`2 + ceil(200,000 ÷ 20,000)` = 12、`2 + ceil(40,000 ÷ 20,000)` = 4。**和の両側が効いている。**

### 予算 0 を踏まない床

`checks_instructions_a_frame=0` と書かれたら割り算は無限大になり、`as u32` は飽和して
4,294,967,295 フレーム——**一度も何も言わない判定**になる。これは上限という仕掛けが防ぐために
ある唯一の壊れ方なので、読むときに `max(1.0)` を掛けた（`Budgets::read_from` が
`value.max(0.0) as u64` としているのと同じ形）。単体テストに 1 行。

## 2. (2) Battle の `script_budget` を測った — **案を出して止まる**

**既定値は動かしていない。** このコミットに `script_budget` の変更は 1 行も無い。
以下は著者が数を見てから決める材料である。

### 2.1 今の 200,000 は何か

`sabibots` はこの数をどこでも言っていない。`RubevyPlugin::default()` が置いた rubevy の既定を
そのまま使っていて、rubevy 自身の `ScriptWorld::budget` の rustdoc が「出どころは不明」と
書いている。この repo に残る**最後の「引き継いだ予算」**である（S5b-5 の気づいた点）。
S9 でこの数が**判定の上限の割り算に入った**（`2 + ceil(200,000 ÷ 45,600)` = 7）ので、
出どころの無い数が判定の忍耐を決めている状態になっていた。

### 2.2 計器 — S5b-3 と同じ形、**コミットしていない**

`SABIBOTS_MEASURE=1` のときだけ動く 1 システムを足し、毎フレーム `ScriptWorld::last_frame()`
（rubevy の `FrameStats`）の `instructions` / `rounds` / `carried_reflect` / `carried_in_tick` /
`time_ns` を、そのフレームの機体数・生存数・タスク数と一緒に 1 行印字した。
**判定にも遊びにも触れていない**（`Update` に `after(RubevySet::Tick)` で足すだけ）。
測り終えて外し、`git checkout sabibots/src/main.rs` で消えていることを確かめてある。

### 2.3 「上限の試合」をどう決めたか

箱庭には `world.rb` が `pop_max` を言う。**Battle には機体数の上限がどこにも無い**——
`match` は `team :red, robots: %w[…]` を好きなだけ書ける。だから「上限の試合」は
**決めて理由を書くしかない**。こう決めた:

* **チームは 4。** `Match::TEAMS` が 4 色しか名乗らず、Rust の `TEAMS` も 4 組の絵しか持たない
  （5 つ目は `team.min(TEAMS.len() - 1)` で黄色に潰れる）。これはゲーム自身が言う上限である。
* **1 チーム 9 台。** `Match#start` は半径 20 の輪の上に機体を置き、機体は `robot_radius` 1.6 =
  差し渡し 3.2。輪の周長 2π×20 = 125.7 なので、重ならずに置けるのは ⌊125.7 ÷ 3.2⌋ = **39 台**。
  4 チームなら 9 台ずつで 36（10 台ずつなら 40 で輪に入らない）。

合わせて **36 台**。`sabibots/ruby/matches/training.rb` を一時的にこの宣言に差し替えて測り、
測り終えて `git checkout` で戻した（差し替えた版は scratchpad の `training.rb.capped`）。

**途中で分かったこと**: `Match#start` の角度は `(t * 2 + i) * 6.28 / (teams.size * robots.size)`
で、`t * 2` が「1 チーム 2 台」を直に書いている。9 台ずつだと 36 台が 140° の扇に固まって出て、
`separate_robots` が最初の数フレームで押し広げる。**命令数には効かない**
（`radar` は射程 60 で闘技場（半幅 32）より広いので、誰がどこに居ても全機が返る）が、
これは一覧にも無い直書きの 2 である。下の「気づいた点」に挙げた。

### 2.4 測った分布（上限の試合、16 走行・26,398 フレーム）

走行は `--headless 180`（試合が決着すると `stop_when_over` がそこで終える）。
予算の既定と案を**交互に**回した合計で、`vmstat` で idle 99% を確かめてから始めている。

| | 中央値 | 90 パーセンタイル | 99 パーセンタイル | 最大 |
|---|---|---|---|---|
| 1 フレームの命令数 | 3,872 | 24,201 | 45,280 | **67,749** |
| tick | 0.232 ms | — | 2.289 ms | 8.828 ms |

* **持ち越し（`carried_reflect` / `carried_in_tick`）は 26,398 フレーム全部で 0。**
  予算に届いたフレームも **0**。今の 200,000 には一度も近づいていない（最悪でその 34%）。
* **箱庭のような「最初のフレームの山」が無い。** 最初の 3 フレームの最大は 1,114 で、
  全体の最大の 1.6% しかない。理由は生まれ方が違うから——箱庭は 24 体が `Startup` で一斉に
  spawn され、最初の `Update` で全員が最初のパスを走る。Battle は**試合のスクリプトが 1 台ずつ
  `spawn` を頼む**ので、36 台の最初のパスは 36 回の問いに分かれて散らばる。
  一番重いフレームは試合が始まって 1〜4 秒、全機が生きていて撃ち合っている所に来る。
* **同梱の試合（4 台）は桁が 2 つ違う。** 3 走行 8,356 フレームで最悪 **2,730**、中央値 346。
  既定の 200,000 の **1.4%**、案の 114,000 の 2.4%。

### 2.5 機械が混むと 1 フレームの命令数は変わるか — **変わらなかった**

依頼に「ヘッドレスは 60 Hz 固定の loop だが、機械が混むとフレームが延びて 1 フレームの
命令数が変わりうる。変わるかどうか自体を 1 度確かめて」とあったので確かめた。
24 コアのうち 12 を空回しのループで塞いで（`vmstat` の idle が 99% → 49%）、上限の試合を 1 走行:

| | 命令数 最大 | tick 中央値 | 持ち越し |
|---|---|---|---|
| 静かな機械（15 走行） | 46,438〜67,749 | 0.20〜0.42 ms | 0 |
| 塞いだ機械（1 走行） | **50,554** | 0.415 ms | 0 |

**最大は静かな走行の幅の中に収まり、上には出なかった。** tick の中央値は倍近くになっていて
（機械が混んでいることは計器に出ている）、それでも命令数が増えも減りもしない。
理由は素直で、**`frame_time` の 8 ms に当たっていないから**である——tick の最悪は静かな機械で
6.59 ms、塞いだ機械で 3.69 ms。壁時計の締切に当たって初めて「混むと命令数が減って持ち越しが出る」
形になるが、そこまで行っていない。なお 16 走行のうち 1 フレームだけ tick が **8.828 ms** と
8 ms を越えている（rubevy の rustdoc が「締切は少し越えうる」と書いているとおり）。

### 2.6 余裕の係数 — 箱庭の 1.74 は**そのまま写せない**

箱庭の 1.74 がどこから来たかを読んだ。**導出ではない**: 世界の VM の予算 45,000（著者が W1/W3 で
決めた数）÷ その実測最悪 25,837 = 1.74 という、**著者が選んだ数から後ろ向きに計算した比**である。
S5b-5 がそれを生き物の VM に使った理由は「同じゲームの 2 本の VM を同じ程度に信用する」だった。

**Battle にはその理由が無い。** Battle の数で 1.74 倍になっているものは 1 つも無く、
借りるとしたら「箱庭の著者がかつて選んだ余裕」を連想で持ってくることになる。
そのうえ、1.74 が掛かる**測定の質が箱庭と Battle で違う**:

| | 箱庭 | Battle |
|---|---|---|
| 最悪フレームは何か | **起動フレーム**。24 体が一斉に最初のパスを走る、1 回きりのフレーム | 撃ち合いの最中の 1 フレーム。**さいころ次第** |
| 走行ごとの再現性 | **3 走行とも 1 命令まで同じ**（23,912） | 16 走行の最悪は **46,438〜67,749**（1.46 倍の開き） |
| 上限は誰が言うか | `world.rb` の `pop_max` = 24。**規則が言う** | **誰も言わない**（36 台は輪の幾何から担当が導いた数） |

つまり Battle では、同じ 1.74 を掛けても**箱庭より弱い保証しか買えない**。
**Battle 自身の理由から係数を出せるか**を考えたが、出せなかった: 余裕が守るべき相手は
「まだ誰も書いていない試合」と「誰も上限を言っていない機体数」で、それは Battle が
わざと開けてある所だからである。**出せない、と書く。**

その代わり、係数を掛ける先を変えた。**16 走行の最悪（sample の最大）に掛ける**——
走行ごとのばらつき 1.46 倍は、その最悪の中に既に入っている。

### 2.7 案

| 案 | 式 | 数 | `handler_frames` | 何が起きるか |
|---|---|---|---|---|
| **A（担当の推奨）** | 1.74 × 65,704 を 1,000 の位に丸め | **114,000** | 7 → **5** | 上限の試合でも一度も当たらない（16 走行で確かめた）。暴走したスクリプトが 1 フレームに使う命令数が 212,600 → 122,600 に、tick が 7.9 ms → 3.2 ms に落ちる |
| B | 実測最悪を丸めただけ（余裕なし） | 68,000 | 7 → 4 | **次の走行のさいころが越えうる**（16 走行の最悪は測るたびに 59,313 → 65,704 → 67,749 と伸びた）。採らない |
| C | 据え置き、ただし**出どころを書く** | 200,000 | 7 のまま | 「上限の試合の実測最悪の 3.0 倍、持ち越し 0」と言えるようになる。失うものは無いが、暴走の 1 フレームは今のまま |

**A の 114,000 は `1.74 × 65,704 = 114,325` を丸めた数**である。65,704 は**案を決めた時点での
16 走行中 10 走行めまでの最悪**で、その後の 6 走行で最悪は 67,749 まで伸びた。
**数は 114,000 のままにした**——ここで 3 つ目の数（`1.74 × 67,749 → 118,000`）を作らない、
というのは箱庭が S5b-5 で「23,686 が 23,912 になっても 41,000 のままにした」のと同じ扱いである。
出荷される余裕の比は `114,000 ÷ 67,749` = **1.68**。そう書く。
なお `2 + ceil(114,000 ÷ 45,600)` も `2 + ceil(118,000 ÷ 45,600)` も **5** で、
どちらを採っても判定の振る舞いは 1 フレームも変わらない。

### 2.8 案の値を設定ファイルで与えて確かめた

`sabibots.settings.txt` に `script_budget=114000` の 1 行だけを置いた走行と、置かない走行を
**交互に**回した。**既定値のコードは 1 行も変えていない。**

**(a) 上限の試合で当たらないか**（`--headless 180` を交互 3 巡、6 走行 9,542 フレーム）

| | 1 フレームの命令数 最大 | 持ち越し | 予算に届いたフレーム |
|---|---|---|---|
| 既定 200,000 | 46,438 / 54,755 / 67,749 | 0 | **0** |
| 案 114,000 | 55,773 / 60,977 / 61,951 | 0 | **0** |

**(b) `handler_frames` は 7 から 5 になる。** S10 (1) が足した舞台指示がそのまま言う:

```
既定 :  selftest: a hit's handler is given 7 frame(s) — 2 structural plus a frame's worth of 200000 instructions at 45600 a frame
案   :  selftest: a hit's handler is given 5 frame(s) — 2 structural plus a frame's worth of 114000 instructions at 45600 a frame
```

**(c) 判定の行は割れない。** `SABIBOTS_SELFTEST=1 --headless 25` を交互 **9 巡**（18 走行）。
どの走行も **4 行・FAIL 0**、既定 9 走行ぶんと案 9 走行ぶんを束ねた `tools/fixedlines.sh` の
**diff は空**。ブラウザも 1 度（下）。

**(d) 試合の決着の分布**（S5b-2 の比べ方。`--headless 180` を交互 6 巡）

| | 勝者 | 撃破数 | 試合の長さ |
|---|---|---|---|
| 既定 200,000 | red 5 / blue 1 | 2〜3 | 23.0〜35.2 s（平均 28.1） |
| 案 114,000 | red 4 / blue 2 | 2〜3 | 18.7〜58.2 s（平均 37.7） |

**見分けがつかない。** 長さの平均は動いて見えるが、案の側の幅（18.7〜58.2）が平均の差より
大きく、6 巡では差とは言えない。**差を作る仕掛けも無い**——同梱の試合の最悪フレームは 2,730 で、
どちらの予算にも 20 分の 1 以下しか届かない。

**(e) 当たりの数で 1 度読み違えかけた。** 最初の交互 6 巡で、数えた当たりが
既定 13/17/16/16/24/14（平均 16.7）に対して案 28/26/15/21/28/18（平均 22.7）と出た。
**仕掛けが無いのに差がある**ので、順番を逆にして 3 巡足した（案を先、既定を後）。すると
案 17/24/16・既定 17/18/19。9 巡を「予算で」分けると 17.1 対 21.4、「対の何番目か」で分けると
**17.5 対 21.1** ——**差は予算ではなく走行の順番に付いている**。
S5b-2 の「隣の担当のビルドの最中に取った『前』は前の版の値ではない」、S5b-4 の
「交互に 2 巡でも足りないことがある」と同じ形で、**交互に回すだけでは足りず、向きも入れ替える**
必要があった。

**(f) ブラウザで 1 度。** `localStorage` の `sabibots:sabibots.settings.txt` に
`script_budget=114000` を置いてから `sabibots/?selftest` を開いた（Playwright の
`addInitScript`）。ページは `setting: the scripts get 114000 instructions a frame` と言い、
上限は **5**、**33 行・FAIL 0・pageerror 0・requestfailed 0**、既定で開いた走行との
`fixedlines` の diff は**空**。
**断り**: ページの側では 1 フレームの命令数の分布を測っていない（計器は PC だけの一時の仕掛けで、
wasm には入れていない）。確かめたのは「案の値でページの判定が前と同じことを言う」ことであって、
分布ではない。ブラウザは SwiftShader で 1 フレーム 250 ms 前後、GPU のある実機でも携帯でもない。

### 2.9 予算を変えると何を得て何を失うか — 暴走したスクリプトで測った

予算の仕事は「`sleep` の無いループを 1 フレームのうちに止めること」である。
**その仕事ぶりを実物で測った**: `run` が `loop { x += 1 }` だけの robot を 1 台混ぜた試合
（一時のファイル。測り終えて消した）を `--headless 20` で回し、予算を変えて比べた。

| `script_budget` | 暴走が居るフレームの命令数 | tick の最大 |
|---|---|---|
| 200,000（既定） | 約 212,600 | **7.91 ms** |
| **114,000（案 A）** | 約 122,600 | 3.18 ms |
| 103,000 | 約 122,600 | 3.60 ms |
| 41,000（箱庭の数） | 約 62,500 | 2.68 ms |

**得るもの**: 既定では暴走した 1 台が `script_frame_time_ms` の 8 ms をほぼ使い切る
（7.91 ms = 60 Hz の 1 フレーム 16.7 ms の 47%）。案 A では 3.2 ms（19%）で、
**壊れた behaviour を書いている最中のプレイヤーに 1 フレームあたり 4.7 ms が返る。**

**失うもの**: 36 台より大きい試合や、`numbers:` でレーダーを広げた試合や、
プレイヤーが書いた重い頭脳は、案 A の方が先に予算に当たる。答えは箱庭と同じで
`sabibots.settings.txt` の `script_budget` であり、**設定だからこそ動かしてよい**。

**ついでに分かったこと**: どの予算でも、フレームの命令数は**予算を 6〜52% 越える**
（41,000 → 62,500、114,000 → 122,600、200,000 → 212,600）。予算は「この値でぴたりと止まる床」
ではなく、**タスクの持ち分の切りの良い所まで走ってから止まる天井**である。
103,000 と 114,000 が同じ 122,600 になるのもそれで説明が付く。下の「気づいた点」に挙げた
（rubevy の話）。

## 4. 気づいた点（仕事の範囲の外。直していない）

1. **予算は「天井」であって「床」ではない。** どの予算でもフレームの命令数はそれを
   **6〜52% 越える**（41,000 → 62,500、114,000 → 122,600、200,000 → 212,600、
   しかも 103,000 と 114,000 は同じ 122,600 になる）。`ScriptWorld::budget` の rustdoc は
   「a frame that reaches the budget shows the budget」と読める書き方をしていて、実物は
   越えた数を見せる。**判定の上限を予算から割り算で出している以上**（`handler_frames` /
   `scheduler_frames`）、これは知っておく値である。
   どこ: rubevy の `tick_scripts` / `task_run_limits`、測定は本 worklog §2.9。属する先: rubevy（API と文書）。
2. **`Match#start` の角度に「1 チーム 2 台」が直に書いてある**（`(t * 2 + i) * 6.28 / …` の `t * 2`）。
   1 チーム 2 台のとき以外、機体は輪の一部に固まって出て `separate_robots` が押し広げる。
   `docs/numbers.md` にも無い数である。どこ: `sabibots/ruby/match_prelude.rb`。
   属する先: Battle（一覧の抜け／DSL の作り）。
3. **Battle には機体数の上限がどこにも無い。** `team :red, robots: %w[…]` は何台でも書ける。
   「上限の試合」を測るのに担当が輪の幾何から 36 台を導いたが、**それはゲームが言った数ではない**。
   箱庭が `world.rb` の `pop_max` を言うのと対照的で、**上限を言わないゲームでは
   「測って決めた既定値」がいつでも破られうる**。属する先: Battle（設計）／本の素材。
4. **交互に回すだけでは足りず、向きも入れ替える必要があった**（§2.8 (e)）。
   6 巡の交互で「予算を下げると当たりが増える」と読める形が出て、順番を逆にした 3 巡で消えた。
   差は「対の何番目に走ったか」に付いていた。`implementer.md` は「交互に 2 巡以上、偏って
   見えたら巡を足す」と言っているが、**巡を足しても向きが同じなら同じ偏りを買い足すだけ**である。
   属する先: 作法（`implementer.md`）／本の素材。
5. **`--headless N` の `N` は「試合の長さの上限」であって走行の長さではない**
   （`stop_when_over` は勝者が出たらそこで終える）。測定で `--headless 180` と書いた走行が
   18.7 秒で終わるのはそのためで、**走行ごとにフレーム数が違う**。分布を取るときは
   「何フレーム取れたか」を必ず書くこと。属する先: 測り方／Battle。
6. **箱庭と Battle で「最悪フレーム」の性格が違う**（§2.6 の表）。箱庭のそれは決定的な起動フレーム、
   Battle のそれはさいころ。**同じ「測って 1.74 倍」という手続きが、2 つのゲームで別の強さの
   保証になる。** 属する先: 本の素材（数の決め方）。

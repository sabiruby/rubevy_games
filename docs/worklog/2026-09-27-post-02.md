# post-02 — 0.6 の回避を外し、クリックを rubevy の pointer へ

2026-09-27。ブランチ `post-02`、先頭は main の `1d0fadd`（SabiRuby 0.7.0 と rubevy 0.2.0 の main に上がったところ）。
rubevy（`/home/kishima/book/kishima/rubevy`、main `07a5e95`、0.2.0 公開済み）は変えていない。2 項目:

1. Ruby に残っている SabiRuby 0.6 の回避（ブロックを `define_method` でメソッドにして、名前を `case` に書き出して呼ぶ）を外す
2. games-shell の `WorldClick` を rubevy 0.2 の `rubevy::pointer` に寄せる

著者の方針は「目標を満たしたら止まる、細部を深追いしない、時間のベンチは測らない」。速さに触れる変更ではないので測っていない。

## 1. 0.6 の回避を外す

### 何があったか

`grep -rn "define_method\|instance_exec\|C function\|boundary\|nested run loop" --include=*.rb` で拾えたのは 4 か所で、全部同じ形だった。

| 場所 | 何を | 上限 |
|---|---|---|
| `sabibots/ruby/prelude.rb` の `Robot.on` / `run_handler` | ハンドラのブロックを `__handler_N` にして `case slot when 0 then __handler_0(*args) …` | `ON_SLOTS = 4` |
| `garden/ruby/prelude.rb` の `Creature.on` / `run_handler` | 同じ | `ON_SLOTS = 7` |
| `garden/ruby/world_prelude.rb` の `World.each_frame` と `World.every` / `run_timer` | `each_frame` は `define_method(:each_frame, &block)`、`every` は `__every_N` と `case` | `EVERY_SLOTS = 4` |
| `factory/ruby/control_prelude.rb` の `Control.on` / `run_handler` | 同じ（引数は `what, n, x, y` の 4 つ） | `ON_SLOTS = 5` |

理由のコメントは 4 か所とも同じ — 「`instance_exec`・`send`・`Method#call` はブロックを VM の入れ子の run loop で走らせ、
タスクはそこを跨いで park できない。最初の `act` が `blocking pop cannot be called from within a C function boundary` で死ぬ。
Ruby に書き出した普通の呼び出しなら、このタスクのフレームなので待てる。だから名前をソースに書く必要があり、それがスロットの数を決める」。
上限の 4・7・5・4 は `docs/numbers.md` に **(a) 書き出した名前の数** として載っていて、どれも「測った予算ではない」と書いてあった。

`sabibots/ruby/match_prelude.rb` の `rule`／`on_destroyed`（`body.call`）と `match`（`instance_eval`）、`factory/ruby/prelude.rb` の
`inserter`（`class_eval`）はブロックの中で待たないので、元から回避していない。そのまま。

### SabiRuby 0.7 で何が変わったか

SabiRuby の `docs/design/wait-anywhere.md` の表: `instance_exec`・`instance_eval`・`class_exec`・`Method#call`・`bind_call`・`send`・`public_send`
は 0.7 で **waits**。native が SEND から直に呼ばれた（`Vm::in_frame`）ときは入れ子の loop を回さず、ブロックのフレームを積んで VM に戻る
（mruby 4.1.0-rc2 の `mrb_exec_irep` と同じ手）。`run_handler` は Ruby のメソッドから `instance_exec` を SEND するので、この条件に入る。
待てないのは `sort { }`、`ObjectSpace.each_object { }`、`sub`/`gsub`/`scan` のブロック、host の関数からのコールバックだけで、どれもここには無い。

### 直した形

4 か所とも「ブロックを持っておいて、`instance_exec` で呼ぶ」:

```ruby
def self.on(event, &block)
  raise "on needs a block" if block.nil?
  handlers << [event.to_sym, block]
  block
end

def run_handler(block, args)
  instance_exec(*args, &block)
end
```

`start_handlers` は `|event, slot|` を `|event, handler|` にして、`run_handler(handler, args)` を呼ぶ。
Factory だけは `slot` をもう 1 つの用途に使っていた — `note_dropped(slot, queue.dropped)` が購読ごとの取りこぼしの鍵にしている —
ので、`each_with_index do |(event, handler), slot|` にして番号を残した。

箱庭の world は `each_frame` を `@each_frame_block` にしまい、既定の `World#each_frame(dt)` が
`instance_exec(dt, &block) unless block.nil?` する。`each_frame` を書かない world は今までどおり何もしない。
`every` は `timers << [seconds, block]`、`run_timer(block, n)` が `instance_exec(n, &block)`。

`ON_SLOTS`（3 つ）と `EVERY_SLOTS` は消した。上限の理由が「書き出した名前の数」だけだったので、書き出しが無くなれば上限も要らない。
`docs/numbers.md` の 3 行は `UNSET` と同じ流儀で取り消し線にして「無くなった」と書いた。
`docs/sabiruby-battle.md`（*What it cost to get right* と `on` の表）と `docs/garden.md`（*The handlers are tasks of their own*）の
説明は「0.6 まではこうだった、0.7 でこうなった」に書き直した。

**意味の違いが 1 つある。** `define_method` で作ったメソッドは lambda と同じく引数の数に厳しい（数が違えば `ArgumentError`）。
`instance_exec` で呼ぶブロックは proc の扱いで、足りなければ `nil`、多ければ捨てる。同梱のスクリプトは全部数を合わせて書いてあるので、
判定の上では何も変わらない。Ruby のブロックとしてはこちらが普通なので、そのままにした（author-review A に 1 行）。
`return` をハンドラのブロックに書いているスクリプトは無い（`grep` で確かめた。`next` はあり、`instance_exec` でも同じ意味）。

### 確かめたこと

待てることそのものは Battle の判定が言う。scout の `on(:hit)` は `act` で向きを変える — `act` は `Rubevy.ask` の `pop` で待つので、
入れ子の loop の中なら 0.6 では例外で落ちていた所。

- `SABIBOTS_SELFTEST=1 cargo run -p sabibots -- --headless 25`: `a handler ran within N s of the hit (N/N)` と
  `the heading changed within N s of the hit (N/N)` が ok（30 hits）。`the handler tasks of every robot that went down ended` は
  2 回とも `--`（25 秒の間にハンドラを持つロボットが倒れなかった。selftest-lines.md に書いてある、動く 1 行）。
- 同じ判定を `--headless 90` で: 4 行とも ok、`handler hit off` が 2 回。ハンドラのタスクが `Rubevy::Unsubscribed` で終わる道も通る。
- `GARDEN_SELFTEST=1 cargo run -p garden -- --headless 90`: 13 行、`selftest-lines.md` と同じ集合、FAIL 0。
  `every 60` の季節は `world: the dry season` がログに出た（再起動の 63 秒後）。`a beetle touched by a rabbit changed heading` と
  `the creatures were asleep a second after night fell` が箱庭の `on` を通る行。
- `FACTORY_SELFTEST=1 cargo run -p factory -- --headless`: 31 行、同じ集合、FAIL 0。control.rb の `on` はログの
  `control.rb: 1 miner at 8, 8` などの行。

## 2. `WorldClick` を rubevy の pointer へ

### 2 つを並べる

| | games-shell（`camera.rs` の `report_clicks`） | rubevy 0.2（`src/pointer.rs` の `watch_the_pointer`） |
|---|---|---|
| 何を出すか | `WorldClick { at, button, cursor }` だけ | `WorldGrab`・`WorldClick { at, button, camera }`・`WorldDrop`・`WorldMove` |
| どのボタン | `CameraKeys::click_button`（左）だけ | `Pointer::buttons`（既定は 5 つ全部） |
| クリックか | 押した所と離した所の距離 ≤ `click_slop` | 同じ比べ方だが、一度 slop を越えた押しは戻ってきてもドラッグのまま |
| 世界の点 | `CameraView` と `ViewInsets` から `Lens::world_at`（**今フレーム**の値） | カメラの `GlobalTransform` から `viewport_to_world_2d`（**前フレーム**の `PostUpdate` で置いた所）|
| パネル | 押したときに egui が pointer を欲しがっていたら、その押しはクリックにしない | 知らない |
| いつ | `Update`（`CameraSet::Drive`） | `PreUpdate`（bevy の入力の後）|
| 既定の slop | `CLICK_SLOP = 6.0`（出どころは箱庭の同名の数、不明）| `DEFAULT_CLICK_SLOP = 6.0`（「rubevy_games の games-shell の値」と rubevy の rustdoc に書いてある）|

使っているのは Factory だけ（`factory/src/build.rs` の `clicks`）で、読んでいるのは `at` と `button` だけ。`cursor` を読む人はいなかった。
Battle は `ArenaPlugin`（動かないカメラ）でクリックを使っていない。箱庭は 3D のカメラで、自分で押す・離すを見ている（下の §2.3）。

### 2.1 寄せ方

games-shell に `rubevy = { workspace = true, features = ["pointer"] }` を足し、`CameraPlugin::build` が
`PointerPlugin::<PanCamera>` を足す（ゲームが先に足していれば足さない）。games-shell の `WorldClick` 構造体、`report_clicks`、
`is_click` とその単体テストは消した。`games_shell::camera` は rubevy の `Pointer`・`PointerPlugin`・`WorldClick`・`WorldGrab`・
`WorldDrop`・`WorldMove` を `pub use` するので、`games_shell::camera::WorldClick` という名前はそのまま rubevy の型を指す。

残った違いのうち、**パネルだけが上乗せを要る**。rubevy は egui を知らない（知るべきでもない）ので、パネルの上で押し始めて
世界の上で離した押しも `WorldClick` になる。games-shell に `WorldClicks`（`SystemParam`）を足した: `WorldGrab` を読んで、
その時 egui が pointer を欲しがっていたボタンを覚え（`PanelPresses`）、そのボタンの `WorldClick` を 1 回捨てる。
egui への聞き方はカメラと同じ 2 つ（`wants_pointer_input() || is_pointer_over_area()`）。Factory の `clicks` は
`MessageReader<WorldClick>` を `WorldClicks` に替えただけで、中身は同じ。`PanelPresses` には単体テストを 1 つ
（`a_click_begun_over_a_panel_is_the_panels`）。

`click_slop` は **`CameraControls::click_slop` を残した**。プレイヤーの設定 `camera_click_slop` が読み込まれる所で、
利用者が変えられる場所を動かさないため。`PreUpdate` の `slop_to_the_pointer` が、`CameraControls` が変わったときだけ
`Pointer<PanCamera>::click_slop` へ写す。既定の `CLICK_SLOP` は `rubevy::pointer::DEFAULT_CLICK_SLOP` を指す形にしたので、
6.0 という数はリポジトリの中で rubevy の 1 か所だけになった（箱庭の `window::CLICK_SLOP` は別、§2.3）。
写すのが rubevy のシステムの後になるフレームがありうるが、数が動くのは誰かが書いたときだけで、その同じフレームに押しが終わることは
考えなくてよいので、並びは指定していない。

ボタンは `Pointer::buttons` の既定（全部）のまま。右ドラッグでカメラを動かすと `WorldGrab`/`WorldDrop` が右ボタンで出るが、
Factory は左しか見ないので害は無い。左をクリック専用に絞ると、Shift + 左ドラッグ（カメラを動かす）が `WorldDrop` を出さなくなる
だけで得るものが無い。

Factory のヘッドレスは `CameraPlugin` を足さないので、`build::clicks` が起動できるように `WorldClick` と `WorldGrab` の 2 つを
`add_message` している（前は `WorldClick` だけ）。

**世界の点のずれ（今フレームか前フレームか）は吸収していない。** 押して離す間にキーで歩いていれば、rubevy の点は 1 フレームぶん
古いカメラから出る。クリックは止まった手でするものなので、その差で別のタイルになるのは、歩きながら端ぎりぎりをクリックしたときだけ。
上乗せで直すなら `CameraView` から点を出し直すことになり、rubevy に寄せた意味が無くなるので、しない。

**ゴースト（マウスの下のタイル、F7）は `Lens` のまま**にした（`factory/src/draw.rs:589, 655`）。`Pointer::at` にすると上と同じ理由で
ズームやキーで動かしている間 1 フレーム遅れて見える。これは毎フレーム目に見えるので、クリックとは話が違う。
F7 のゴーストの判定（窓のカーソルを偽って置く）もそのまま通る。

### 2.3 乗り換えなかった所 — 箱庭のクリック

箱庭は生き物をクリックで選ぶ（`garden/src/window.rs:157-170`、`creature_under`）。これは乗り換えていない。

- カメラが 3D の透視。`rubevy::pointer` は `viewport_to_world_2d` で、rubevy の rustdoc 自身が「3D のゲームはレイと面が要る。それはゲームのもの」と言っている。
- クリックかどうかの判定だけ借りる手はある — `PointerPlugin::<Camera3d>` を足して `WorldClick` を「離した」の合図にし、
  座標は同じフレームの窓のカーソルから自分でレイを飛ばす。しかし `WorldClick` は画面の位置を持たないので結局窓を読み直すことになり、
  `at` は透視カメラでは意味の無い点になる。消えるのは `pressed_at` と比べ 1 行で、足すものの方が多い。
- 箱庭には `CameraPlugin` が無い（`Eye` という自前の 3D カメラ）ので、games-shell の上乗せも使えない。

rubevy に足りないものとして報告に書いた: `WorldGrab`/`WorldClick` に窓の上の位置（`cursor`）があれば、3D のゲームもクリックの判定を借りて
自分でレイを飛ばせる。games-shell の旧 `WorldClick` は `cursor` を持っていた（誰も読んでいなかったが）。

## 気づいた点

- **rubevy: `WorldClick` に画面の位置が無い**（rubevy `src/pointer.rs` の `WorldGrab`/`WorldClick`）。3D のゲームがクリックの判定だけ借りて
  レイを飛ばすには、同じフレームの窓のカーソルを読み直すしかない。`cursor: Vec2` があれば箱庭も乗れる。rubevy の口の話。
- **rubevy: パネル（UI）の上で始まった押しを区別する口が無い。** egui を知らないのは正しいが、「この押しは誰かが取った」と
  書き込める所（たとえば `Pointer` に、ゲームが立てる「この押しは無視」の印）があれば、games-shell の `WorldClicks` の
  ような読み手ごとの上乗せは要らなくなる。rubevy の口の話。
- **rubevy: 点が前フレームのカメラから出る**（`watch_the_pointer` が `PreUpdate` でカメラの `GlobalTransform` を読む）。
  カメラを `Update` で動かすゲームでは、動かしている間の `Pointer::at` と `WorldMove` が 1 フレーム遅れる。
  rustdoc に一言あると使う側が迷わない。rubevy の文書の話。
- **rubevy の `DEFAULT_CLICK_SLOP` の rustdoc は出どころを「rubevy_games の games-shell の値」と書いている**が、games-shell の既定は今は
  rubevy のものを指している（循環）。数の出どころは箱庭の `CLICK_SLOP`、不明。rubevy の次のバージョンで rustdoc を
  「出どころ不明（箱庭の CLICK_SLOP から）」にするとよい。rubevy の文書の話。
- 箱庭の `garden/ruby/prelude.rb:365-367` のコメント（`mutation_rate` の説明）は「`@handlers` がすでに通っている道: host が
  `ivar_get` 2 回で読む class の ivar」と言っているが、host は `@handlers` を読んでいない（`grep` で 0 件）。
  このブランチで `@handlers` の中身がブロックになっても影響は無いが、コメントは古い。箱庭固有。

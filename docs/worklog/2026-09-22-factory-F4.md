## 1. F4-0: 先に片付けた 3 件（`95c162f`）

### 1.1 毎フレーム地図全体を舐める 2 か所（F3a の気づき 1）

`belts::step` のパス 1 は `lanes.tails` の**全タイル**に番兵を書いてから建物のあるタイルに本当の値を
上書きしていた。`items::run_the_factory` の `lanes.count()` は**全レーンの長さを足して**いた。
どちらも「工場の大きさ」ではなく「世界の大きさ」に比例する仕事で、**世界の大きさは F3a で利用者のもの**
になっている。

直し方:

* **尻尾**は `lanes.order`（＝ `grid.built()` の写し）だけを書く。建物が無いタイルは地図を作った
  ときの番兵のままで、**撤去のときに番兵へ戻す**（`Lanes::forget`）。読む側（`room_ahead`）は
  先に grid を見て「次が belt か」を確かめるので、建っていないタイルの尻尾は元々読まれない
  — `forget` は「読まれないが正しくない値を残さない」ための念押し。
* **個数**は `Lanes` が持つ（`n`）。そのために `Lanes::of` を**非公開**にし、出入口を 4 つに絞った:
  `put_on` / `take_off` / `forget` / `moving`（位置だけを動かす `carry`・`hold` 用、長さを変えない）。
  テストも含めて全部この口を通るようにした。

**測った**（release、空の地図に `--arms 1` の 3 タイルだけ、ヘッドレス、2026-09-22。
なお F3a の数は同じ機械・同じ器で測ったもの）:

| 地図 | step µs p50（F3a） | step µs p50（今） |
|---|---|---|
| 32 × 32 | 4 | 1 |
| 512 × 512 | 600 | 1 |
| 2048 × 2048 | **5,900**（1 フレームの 35%） | **1** |

地図の大きさに依らなくなった。確かめは `data.rb` の `map :world, size:` を書き換えて 3 通り走らせ、
`a map of N by N tiles` のログで地図が本当にその大きさだったことを見ている。

**テストを足した**（`belts.rs`）: 採掘機・ベルト 2 枚・腕・箱の線を 600 フレーム回し、**毎フレーム**
「持っている数」と「全レーンを歩いて足した数」が一致することを見る。そのあとベルトを 1 枚撤去して
（`take_away`）両者がまだ一致すること、**同じ場所に建て直したベルトがまた物を受け取ること**
（尻尾が残っていれば後ろのベルトは永久に渡せなくなる）まで。保存則の 5 分テストにも 1 行足した。

### 1.3 判定が「地図の真ん中は空いている」に寄りかかっていた（F3a の気づき 3）

`lay_out_the_machine_lines` は地図の真ん中に機械の線を建てていて、「`Ore::laid_out` は真ん中を空ける」
というコメントが付いていた。**それは畑の数が偶数のときだけ**で、`patches:` は `data.rb` の 1 行である。
判定が「鉱石がどこにあるか」を**自分で計算して知っている**形をやめ、**探す**形にした:

* `somewhere_clear(map, grid, ore, block)` — 「鉱石が無く、何も建っていない `block` の大きさの長方形」を
  **地図の真ん中から外へ**探す。真ん中から探すので**既定の地図では今までと同じ場所**に建ち、
  `--shot` の絵（カメラは真ん中を見ている）も変わらない。
* 使う所は 2 つ: 機械の線（幅 = いちばん広い機械 + 6、高さ = 機械の数と高さから）と、
  **「鉱石の無い所に採掘機は建たない」判定のタイル 1 枚**（こちらも真ん中を決め打ちしていた）。

`seed_the_machine_lines` は同じ計算をもう一度していたので、**線の場所を渡す**形にした
（`MachineCheck` が自分のレシピを持つ）。

## 2. F4-1: control stage（`a5fdc1a`）

### 2.1 イベントは 5 つ、粒度は「機械」— 64 件/フレームから逆算した

購読 1 本は **64 件**でいちばん古いものを落とし（`ScriptWorld::queue_limit`）、スクリプトは
**1 フレームに 1 回**起きる。だから「2 回の目覚めの間に publish しうる件数」が 64 を超えなければ
落ちない。**逆算の答えは「1 フレームに、種類ごとに 1 件」**:

```
on(:built)     |what, n, x, y|   建った
on(:removed)   |what, n, x, y|   壊した（更地にしたときだけ。上書きは built 1 件）
on(:crafted)   |item, n, x, y|   機械が作り終えた
on(:delivered) |item, n, x, y|   箱に入った
on(:jammed)    |what, n, x, y|   機械が詰まった
```

**4 つとも平たい値**（何が・幾つ・どこで）。`what` / `item` は番号で publish し、prelude が
`data.rb` の名前（Symbol）に直す — in-tick の答えと同じ理由で、publish も平たい値がいちばん安い。

**種類の数は `data.rb` が決める**（このゲームなら item 3 + 建物 6）ので、**データファイルに書ける
どんな値でも 64 には届かない**。1 個ずつ publish していたら、納品だけで腕 60 台あたりで天井に当たる。

**`Move` に足したもの**: `Taken { from, into, item }` と `Made { at, item }`（納品は「箱に入ったこと」で、
何が・どこへ入ったかは後から grid を見ても分からない）、そして `Jammed { at }`。

**詰まりの定義**（決めた）: **「作った物を持っていて、かつ次の一回ぶんの材料も持っている機械」**。
理由 — 動いている工場ではベルトは**いつも**詰まっている（機械の前のベルトが詰まっているのが正常
な姿）ので、ベルトの詰まりを publish するのは「工場が動いている」を publish するのと同じ。
機械が作った物を出せないのは**鎖が止まっている**ことで、止めているのは「出す側の腕が無い」こと、
つまりプレイヤーがやるべき仕事がある。`machines::craft` の「作った物があるなら次を始めない」の
分岐のところで判定するので、**追加の走査は 0**。

**状態ではなく縁**を publish する: 工場は毎フレーム「詰まっている」と言い、`Happenings` が
**そうなったフレームだけ**を 1 件にする（`backed_up` / `still` の 2 つの集合）。

**計画 §5 の罠（publish は購読者ごとに値を作り直す）には当たらない**ことを確かめた: control は
1 本で、1 つの名前につき購読は 1 つ（目標を見る本体タスクの `:delivered` を入れて 2 つ）。
インサータは**何も購読していない**（`move` は request を待つ形）。

### 2.2 DSL と prelude — インサータとは別のファイル

`ruby/control_prelude.rb`（新）。インサータの prelude と**分けた**のは指示どおりで、理由は
「3,000 台ぶんコンパイルされる単位を太らせない」。作法は箱庭の `on` に合わせた:

* `on(:built) { |…| }` は `define_method("__handler_N")` + `run_handler` の `case`（`instance_exec`
  や `send` はネストした run loop になり、その中のタスクは park できない — 箱庭と Battle と同じ理由）。
* ハンドラは**タスク 1 本ずつ**、本体タスクと同じ優先度で走る。
* **本体タスクは目標を見る**: 自分の `:delivered` を購読して数える。だから `on(:delivered)` を
  書かないファイルでも目標は働く。

**ファイルごとにクラスを作る**（`$control_class = Class.new(Control)`）。VM は 1 つで `class Control`
も 1 つなので、control.rb を差し替えると前のファイルのハンドラと目標を受け継いでしまう
（`define_method` が中身だけ静かに置き換わる）。箱庭の `creature "Beetle" do … end` と同じ形で、
包む語だけ落とした — control stage は 1 つしかないので `on` と `goal` はファイルの先頭に書く。

### 2.3 目標と勝ち — N の導出

```ruby
goal deliver: { gear: 60 }
```

**鎖 1 本 = 採掘機 2 → かまど 4 → 組立機 1 → 毎秒 1 個**（`data.rb` の数は全部ベルトに対する比で
決まっている）。だから 60 は **鎖 1 本を 1 分回した数**であり、**箱 1 杯**（`chest :crate, capacity: 60`、
これも「採掘機 1 台の 1 分」）でもある。`data.rb` の他の数と同じ「1 分」で書けた。

**勝ちの伝え方**: `win!` が `@won` を立て、**ゲームが 1 フレームに 1 回読む**。ivar を読むのは
箱庭が生き物の `@asleep` と `mutation_rate` を読むのと同じ道で、**スクリプトからの質問（request）を
1 つも増やさない** — 納品のたびに `Rubevy.ask` すると 1 件 1 フレームかかる。

ゲームが読むのは 4 つ（`@won`、画面に出す 1 行 `@saying`、イベントごとの `@seen_*`、
購読が落とした数 `@dropped`）。

### 2.4 control がゲームに働きかける口（決めた）

**「読むだけ + 勝ちを言うだけ」に留めた。** `build::Order` を control から書けるようにはしていない。
理由: 目標は**言うこと**で、建てるのはプレイヤーの手。建てられる口を作ると「建たなかったとき何を
言うか」が要り、それはエディタとセーブ（F5）の設計と絡む。Factorio の control stage は建てられるが、
ここは「小さく写す」ほうを採った。

### 2.5 壊れた control.rb

* **コンパイルできない** → `in_the_authors_lines` で `control.rb:行`、工場は目標無しで動き続ける。
* **例外** → prelude の `rescue` が `@broke_at` に置き、ゲームが `ivar_get` で読む（F3 と同じ道）。
* **Overrun** → 同じ道を通り、行が取れなければ `control.rb:?`。

**ここで 1 つ工夫が要った。** インサータのファイルは `inserter "X" do … end` なので中身は全部
prelude の `rescue` の中で走るが、**control.rb は top level に書く**ので、そのままだとファイルの
コードは `run_control` に入る前（プログラムの読み込み中）に走り、例外の行が取れない（`control.rb:?`）。
**ゲームがファイルを 1 行のメソッドで包む**ことにした（`def the_control_file` … `end`、
`crate::control::in_a_method`）。`run_control` がその中でそれを呼ぶので、`goal` と `on` の呼び出しも
ファイル内のどんな例外も `rescue` の中に入る。実測: top level の `nothing.at.all` が **`control.rb:3`**
と報告される（包む前は `control.rb:?`）。

**代償**: 閉じ忘れ（`do` に `end` が無い）のような構文エラーで、コンパイラが「入力の終わり」を指す
場合、報告される行がファイルの末尾より少し先になる（3 行のファイルで `control.rb:7`）。
F2 が書いた「半端な行はパーサが諦めた所＝次のトークンで報告される」の延長で、包んだぶん `end` と
`run_control` が後ろに増えた。**判定は例外の行のほう**（厳密に取れる）を見ている。

### 3.1 規模 — `--arms` の器に control を載せて

release、ヘッドレス、`--arms N --headless 12`、報告 3 回のうち最後の 2 回。**control.rb を出荷の

2 巡**（巡ごとに順番も入れ替えた）。**この機械では別の担当が同時に走っていた**（`vmstat` の idle が
0〜26%）ので、**命令数は信用してよく（スクリプトについての事実）、µs は信用しない**。

| 腕 | control | 命令 p50 | 命令 p95 | tick µs p50 | 落とした |
|---|---|---|---|---|---|
| 340（既定の地図が持てる上限） | 無し | 1,399 | 2,263 | 196 | 0 |
| 340 | **有り** | 1,579 | 2,443 | 301 | **0** |
| 3,400（その 10 倍） | 無し | 11,983 | 25,807 | 1,379 | 0 |
| 3,400 | **有り** | 11,947 | 18,859 | 1,427 | **0** |

**control stage は毎フレーム約 200 命令**（340 台で 1,579 − 1,399 = 180）で、**工場が 10 倍になっても
増えない** — 1 フレームに種類ごと 1 件しか流れないから。3,400 台での差はばらつきの中に埋もれている。

**予算 39,000 の中に余裕で入る**: 既定の地図が持てる上限（340 台）で p95 2,443 命令 ＝ 予算の 6%。
**`dropped` は全部 0**（VM の `ScriptWorld::dropped` も、スクリプト側の `Subscription#dropped` も）。

### 3.2 判定の行

ヘッドレス **19 → 24 行**、窓 22 → 27、ブラウザ 23 → 28。足した 5 行:

```
selftest: ok   the control stage heard what the factory did: N built, N crafted, N delivered
selftest: ok   the goal in control.rb is reached and the game is told: won — iron_ore N / N (after N s)
selftest: ok   the same factory does not win on a control.rb that asks for more than the ground holds: N delivered, won false
selftest: ok   a control.rb that will not run leaves the factory running: control.rb:N: RuntimeError, and the chest went from N to N
selftest: ok   nothing published to the control stage was dropped: N in the script, N in the VM
```

**「目標を差し替えると目標が変わる」は、同じ工場で 2 つの control を走らせて見ている**:
`iron_ore: 1` は勝ち、`iron_ore: 地面にある全部 + 1` は（同じ工場が納品を続けていても）勝たない。
**上限の数は世界が言う**（`ore.total() + 1`）ので、出どころの無い数を書いていない。

**待ちは全部条件**（秒でもフレーム数でもなく）。上限は「採掘機の線が箱にもう 1 個入れるまで」＝
`mine_seconds + 4 ÷ belt` × `CHECK_SLACK`。F4 の判定は**判定用のシステムを別に立てた**
（`control_checks`）: Bevy の system は引数 16 個までで、`selftest` はちょうど 16 個だった。
2 つは `SelfTest` の `step` で受け渡す（`CONTROL_CHECKS` = 31..40）。

**`headless_seconds` を 30 → 66 に**: 判定自身の上限の和が F3 の 20 秒から **44 秒**になった
（F4 が 6 秒の待ちを 3 つ足した）ので、F3 と同じ「和の 1.5 倍」。何も悪くない走行は **15 秒**
（F3 は 10.5 秒）。

## 4. 落ちたこと・直したこと

* **最初の判定で `crafted` が 0 だった。** 出荷の `control.rb` に `on(:crafted)` が無く、
  `@seen_*` は**ハンドラが走った所で**増えるから。`control.rb` に「作った物の最初の 1 個だけ log に
  出す」ハンドラを足した（`@made ||= {}` で覚える — ハンドラが ivar を持てることの実例でもある）。
* **「勝たないほうの control」が 0 納品と言った。** 同じ理由で、目標だけのファイルにはハンドラが
  無い。判定のスクリプトに**何もしない `on(:delivered)`** を足した（コメントに理由を書いた):
  「このスクリプトが同じ工場の話を聞いている」ことの証拠がハンドラの回数だから。
* **`delivered(item)` は 1 件遅れることがある**（本体タスクと `on(:delivered)` は別の購読で、
  どちらが先に走るかは決まっていない）。出荷の `control.rb` から「— N so far」を外した。

## 5. 気づいた点

1. **top level に書く DSL は例外の行が取れない。** インサータ（`inserter "X" do … end`）は中身が
   ブロックなので prelude の `rescue` の中だが、control.rb は top level なので `run_control` に
   入る前に走る。ゲームが 1 行のメソッドで包んで解いたが、**「プレイヤーが書くファイルをどう包むか」は
   rubevy の `Program::new` が決めている形（prelude + body + tail）の外側の話**で、`Program` に
   「body をメソッドで包む」選択肢があれば 3 本目以降のゲームが同じ 10 行を書かずに済む。
   属する先: rubevy／本の素材（行番号の話の続き）。
2. **包むと構文エラーの行が末尾より先になる。**（§2.5 の代償）。属する先: ゲーム固有／本の素材。
3. **`ScriptWorld::dropped` は VM 全体の数**で、どの購読が落としたかは言わない。今は control が
   1 本なので区別が要らないが、購読を持つスクリプトが 2 種類になったら「誰の穴か」は
   `Subscription#dropped` を全部集めるしかない（prelude がやっている）。rubevy が名前ごとの
   内訳を持てば HUD が 1 行で書ける。属する先: rubevy。
4. **`Crew` に続いて判定も 16 引数の壁に当たった。** F3 は `Editor` を `Crew` に入れて避け、F4 は
   システムを分けた。3 度目は「判定を小さく分ける」ほうが素直（F5 で窓の判定が増える）。
   属する先: ゲーム固有／F5。
5. **`docs/factory.md` の「What one step of the factory is」が F3 の時点で古かった**（4 パスと書いて
   6 つ並べ、F3 が消した `deliver` がまだ入っていた）。F4 が直した。属する先: 文書。

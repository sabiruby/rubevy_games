## 1. (6) 前任の差分 — `--shot` と判定を同時に、`fixedlines.sh` の CR

### 何が置いてあったか

## 2. (5) Battle のハンドラの判定 — 秒で待つのをやめた

### 何が壊れているか（F0 の報告）

`handler_selftest` は、ハンドラを持つ robot が被弾したら**壁時計で 0.3 秒**待って
「ハンドラが走ったか」「向きが変わったか」を判定する。F0 は、ブラウザの窓を **1600×900** にすると
この 2 行が毎回 FAIL すると書いた（1280×720 では通る。`2026-09-21-factory-F0.md` §10-1）。
`tools/fixedlines.sh` はこの 2 行を落とすので、行の集合の基準では見えない。

### 再現 — 1600×900 だけでは出なかった

まず素直に再現を試みた。`web/build.sh sabibots` → `web/serve.sh` → Playwright（Chromium 1243、
`--use-angle=swiftshader --enable-unsafe-swiftshader`、`waitUntil:'commit'`）で
**1600×900 を 3 走行、1920×1080 を 1 走行**、どれも 100 秒。

| | FAIL | 当たり |
|---|---|---|
| 1280×720 は試していない（F0 の対照） | — | — |
| 1600×900 × 3 | **0 / 0 / 0** | 4 / 3 / 1 |
| 1920×1080 × 1 | **0** | 2 |

**出なかった。** 機械がこの日は静かで（`vmstat` の idle 98〜100%、隣の worktree の cargo も docker も
止まっていた）、SwiftShader が F0 の日より速かったのだと読んだ。F0 の再現条件は「窓の大きさ」
ではなく「0.3 秒に入るフレームの数」なので、同じことを**確実に起こす**ために Chromium の CDP の
`Emulation.setCPUThrottlingRate` を使った（ページにも wasm にも手を入れずに、フレームを長くする）。

| 絞り | FAIL |
|---|---|
| ×6、1600×900、100 秒 | 0（当たり 3。振れ幅は 0.47〜0.48 rad まで下がった） |
| **×20、1600×900、120 秒** | **1**（`1 red/scout ran a handler within 0.3 s of the hit at 61.19 s`） |

**これが F0 の形である**: 落ちたのは「ハンドラが走った」の行で、同じ当たりの「向きが変わった」は
`ok`（0.50 rad）だった — 機体は曲がっていたのに、ハンドラが走ったことになっていない。

### 何が起きているのか — 測った

判定に「当たったフレーム」と「ハンドラが初めて走ったのが何フレーム後か」を持たせ
（`WatchedHit::frame` と `ran_after`。どちらも `of the hit at` を含む行に印字するので
`fixedlines.sh` が落とし、行の集合は動かない）、2 つの条件で測った。

| 走行 | 当たり | ハンドラが走るまで |
|---|---|---|
| 静かな PC のヘッドレス `--headless 25` × 4 | **105** | **全部 2 フレーム**（ばらつき 0） |
| ブラウザ ×20 絞り 1600×900 120 秒 × 5（上限を `?selftest&handler_frames=30` で外して測った） | 11 | **2 が 5、3 が 5、4 が 1** |

2 フレームは**構造で決まっている**: 当たりを publish するのは `move_bullets` で、これは
`RubevySet::Answer` の中 — つまりそのフレームの tick の**後**。だから起きたハンドラのタスクに
順番が回る最初の tick は次のフレームのもので、その同じフレームの `answer_requests` が `act` に
答え、鎖の次の `move_robots` が機体を曲げる。`handler_selftest` はその鎖と順序を持たないので、
**曲がったことを確実に見られるのはさらに次のフレーム**。合わせて 2。105 件の実測がそれと一致した。

そして絞ったブラウザでは 3 と 4 が出る。低い優先度のハンドラのタスクが、`frame_time`（8 ms の
壁時計）を使い切った tick で順番をもらえずに 1〜2 フレーム待たされている。

### 直し方 — S7 の形を Battle に

S7 が箱庭にやったことをそのまま当てる。**求めているものを待ち、待ちはそれが起きる単位で数え、
上限は導く。**

* 窓は「0.3 秒」**かつ**「ハンドラがまだ走っていないなら `handler_frames(budget)` フレーム」。
  ハンドラが走った瞬間に延長は終わるので、追いつけている機械では 1 フレームも余計に待たない。
* 上限は箱庭の `scheduler_frames` と同じ和:
  `HANDLER_STRUCTURAL_FRAMES(2) + ceil(script_budget ÷ INSTRUCTIONS_A_FRAME_BUYS(45,600))`。
  出荷時の予算 200,000 では **7**。実測の最悪 4 を覆う。
  予算は `sabibots.settings.txt` の `script_budget` なので、**数ではなく式**で持つ（S5b-3 の教訓）。
* **振れ幅の閾値も窓に従わせた**: `enough_of_a_swerve(turn_rate, window)`。今までは
  `turn_rate × 0.3 ÷ 4` で、窓が広がった走行では「0.3 秒ぶんの 4 分の 1」を 3 倍の時間のあとで
  訊くことになり、ただ走っているだけの機体が通ってしまう。**窓の取り分**が主張なので、窓は
  その当たりが実際にもらったものを使う。
* 同じ理由で、除外の 3 条件に直書きされていた `0.3` 3 つと、印字の `0.3` も窓に置き換えた
  （`HIT_WINDOW` の写しが 4 つあった）。まとめの 2 行は **`HandlerTest::widest`**（数えた当たりが
  もらった最大の窓）を言う。数は `fixedlines.sh` が伏せるので、行の集合は動かない。

`INSTRUCTIONS_A_FRAME_BUYS` 45,600 は S6 が**この機械のこの VM**を測った数で、
`garden/src/window.rs` に同じ名前で書いてある。2 つのバイナリにまたがるので cite できず、
**写しが 1 つできた** — 気づいた点に出す（本来は両方が届く crate に 1 つ置くべき数）。

### 直した後

同じ条件（1600×900、CPU ×20、120 秒）で回し直した。

| | 走行 | 当たり | FAIL | 上限に当たった回数 |
|---|---|---|---|---|

## 4. (5) の続き — 5 走行目が穴を 1 つ出した

(5) をコミットした後、絞ったブラウザの 5 走行のうち **5 走行目が 2 行 FAIL した**。
隠さずに書く: 直した後でも落ちたのだから、直し方が足りていなかった。

```
selftest: FAIL 3 blue/scout ran a handler within 0.46 s of the hit at 7.67 s (never, in 2 frame(s))
selftest: FAIL 3 blue/scout turned within 0.46 s of the hit at 7.67 s (0.00 of 0.30 rad)
```

**`in 2 frame(s)`** が印になった。上限は 7 のはずで、2 で判定しているのはおかしい。
足した計器がそのまま原因を指した。

* 上限は `handler_frames(world.budget)` を**毎フレーム**計算していた。
* `P`（一時停止）は `inspect_keys` が `ScriptWorld::budget` を **0** にする。
* したがって一時停止の間の上限は `2 + ceil(0 ÷ 45,600)` = **2** — 構造の最小値そのもので、
  混んだスケジューラのための余裕が 0 になる。
* そしてそもそも、**予算 0 の VM は 1 命令も走らない**ので、その窓の中でハンドラが走ることは
  ありえない。機体は 0.00 rad = まったく動いていない。エディタの判定は `P` を 2 秒押す。

つまり 2 つ別のことが重なっていた。両方直した:

1. **上限は「この走行が与えている予算」から 1 度だけ出す**（`HandlerTest::bound`。VM が予算を
   持っている最初のフレームで計算して憶える）。一時停止が、自分の起こした待ちを自分で
   短くすることはもうできない。
2. **窓の中に一時停止があった当たりは数えない**（`WatchedHit::paused`。既にある 3 つの除外
   理由——落ちた／ブレインが差し替わった／エディタの判定が配っていた最中——の 4 つ目）。
   走行中に新しい当たりが記録されることは無い（`move_bullets` は `world_moves` の鎖の中）ので、
   当たるのは「一時停止の直前の当たり」だけである。

これは **S9 が作った穴ではなく、S9 が見えるようにした穴**である: 直す前も、窓が一時停止を
跨いだ当たりは同じ理由で FAIL していたはずで、当たりが `P` の直前に来ることが稀だっただけ。
`(never, in 2 frame(s))` と `0.00 of 0.30 rad` を印字していなければ、「また揺れた」で終わっていた。

同じ条件（1600×900、CPU ×20、120 秒）で 3 走行: **FAIL 0**、当たり 7 件、行の一覧は 3 走行とも
33 行で一致、pageerror 0・requestfailed 0。静かなヘッドレスも 2 走行とも 4 行・FAIL 0。
（一時停止を跨ぐ当たり自体が稀なので、この 3 走行に `not counted, the scripts were stopped (P)`

## 5. (4) 箱庭の `Rubevy.ask("frame")` を rubevy の `next_frame` / `each_frame` に

`world_prelude.rb` の `run_world` は、毎フレーム 1 回だけ `Rubevy.ask("frame")` を投げ、
**ゲームの system**（`answer_world`）がそれに答えることで「1 周 = 1 フレーム」を作っていた。
rubevy は R11 で同じ約束を自分で持った（`Rubevy.next_frame` は予約された `frame.next` で、
どのゲームも答えられない。`Rubevy.each_frame` はその loop）。

```ruby
Rubevy.each_frame do |dt, n|
  break if n.nil?
  being.begin_frame(n)
  being.each_frame(dt)
end
```

`break if n.nil?` は前の形の番人をそのまま残した（`Rubevy.ask` の答えが空だったときに世界が
静かに止まる道）。`dt` は `$rubevy[:delta]` と同じもので、ブロックに渡ってくるぶん問い合わせが
1 つ減る。

### ゲーム側の `"frame"` は消した

`answer_world` の `"frame" => …` の腕を**残さなかった**。理由は S5b-2 が旧い定数について
決めたのと同じ: **写しを 1 つ残すことそのもの**が問題で、「箱庭でフレームを待つ綴りが 2 つある」
状態は、片方が正しくもう片方が古い、という形でしか終わらない。`world.rb` に
`Rubevy.ask("frame")` と書いていた人は `Answer::Nil` を受け取る（知らない問いの既定）ので、
`break if n.nil?` と同じ道で静かに止まる — これは**利用者に見える変化**なので報告に出す。
同梱の `world.rb` は `Rubevy.ask` を 1 度も書いていない（規則の DSL は `garden.…` の Proxy だけ）。

### 前後で測った

* **selftest の行**: ヘッドレス 13 行・FAIL 0 が前後とも一致（差分空）。
* **VM パネルの文面が 1 つ変わる**: 「何を待っているか」は待っているメソッドの名前で、
  `run_world` → `next_frame` になった。これは `selftest:` の行ではない（`vm:` の行）ので、
  行の一覧には出ない。
* **世界の VM の 1 パスあたりの命令数**（`ran_in` と総数から）。別の target には建てず、
  **2 つのバイナリを別ファイルに copy して `md5sum` で別物だと確かめ**、交互に 6 巡:

| | 1 パスあたりの命令数（6 走行） | 平均 |
|---|---|---|
| 前 | 9,988 / 10,919 / 9,551 / 8,931 / 9,457 / 9,964 | 9,802 |
| 後 | 9,338 / 8,586 / 9,682 / 7,906 / 9,856 / 8,597 | 8,994 |

**「後の方が 8% 安い」と読んではいけない。** 群内のばらつき（前 8,931〜10,919、後 7,906〜9,856）は
群間の差より大きく、範囲はほとんど重なっている。1 パスの費用は**庭がどれだけ混んでいたか**
（株 × 生き物の総当たり）で決まり、90 秒の走行ごとにそれが違う（生き残りは前 16.3 匹・後 15.3 匹）。
**導出では、後の方が 1 パスあたり数命令だけ高い**はずである（`next_frame` のメソッド呼び出しと
`each_frame` のブロック yield が増え、`Rubevy.ask` が 1 つ減る）。9,000 命令の 0.1% 未満で、
この測り方では解像できない。**この測定が言えるのは「桁で変わってはいない」までである。**

## 6. (2) egui の待ちに自分の上限を持たせた

S5b-5 の気づきの 1 行目:

> **egui の待ちが VM の数に相乗りしている**。`Turn::EguiHasThePointer` の上限が
> `scheduler_frames`（予算から計算）で、予算が 1/5 になった結果 7 → 3 フレームになり、
> egui の待ちが先に足りなくなった（8 本同時 88 走行中 3 が諦めた）。

S7 は「3 つの待ちのうち最大の 1 つの数でよい、1 つの数の方がよい」と決めていた。
前半（egui は 1 フレームで足りる、それが 3 つの中で最大）は今も正しく、**後半が間違っていた**:
上限は「何を待っているか」についての主張なので、別の理由で待つものには別の上限が要る。
片方を動かしたときにもう片方が黙って動いてはいけない。

### 直し方

* `WindowTest::bound()` が `Turn` を見て上限を返す。VM の 3 つ（`RestartedBeetles` /
  `AMeterMoved` / `TheDayIs`）は今までどおり `scheduler_frames`、`EguiHasThePointer` は
  `EGUI_FRAMES`。
* **待ちの舞台指示が「何を待ったか」を名乗る**ようになった:
  `selftest: waited 1 of 2 frame(s) for egui to take the pointer, and it happened`。
  `tools/fixedlines.sh` は verdict の無い行を落とすので**行の一覧は動かない**。
  これが無いと、ログは「待ちが何フレームかかったか」は言うが「どの待ちか」を言わないので、
  2 つの上限を測り分けられない（S5b-5 の「3/88 が諦めた」が、どの待ちの話かを
  直接には確かめられなかった理由でもある）。
* つまみ `GARDEN_EGUI_FRAMES=N` / `?selftest&egui_frames=N`（測るため。ブラウザでも回せる）。

### 測った — egui は「取る」に 2 フレーム、「離す」に 1 フレーム

上限を 30 に外して（`?selftest&egui_frames=30`）ブラウザで 2 走行。名乗るようになった舞台指示が
そのまま表になる:

```
selftest: waited 2 of 30 frame(s) for egui to take the pointer, and it happened
selftest: waited 1 of 30 frame(s) for egui to let the pointer go, and it happened
```

2 走行とも同じ値だった。そして**これは導出と 1 フレームも違わない**:

* **離すのは 1 フレーム**。`wants_pointer_input` は「ポインタが欲しくない場所にある」と
  egui が知った時点で false になる — 書いた `CursorMoved` の次のフレームの pass。
* **取るのは 2 フレーム**。答えの後半が**レイアウト**だから:
  `is_pointer_over_area` は「その点の下にあるのはどの層か」を訊き、訊く矩形は**前の pass が
  残したもの**である。だから N+1 の pass で egui が位置を持ち、N+2 が「その位置を使った答え」を
  system が読める最初のフレームになる。

`EGUI_FRAMES = 2`。**実測の最悪に合わせたのではなく、導出が 2 で実測も 2 だった**。

ついでに分かったこと: 同じ走行で `scheduler_frames`（3）の側は
`every beetle's task to run an instruction` に 2〜3 フレーム、`the applied rules to be running`
に 2〜3 フレーム使っていた（後者は `spare` の 1 フレームを足した 4 が上限）。
**VM の待ちは上限ぎりぎりで、egui の待ちは 2 のうち 2** — 別々の理由の待ちが別々の数を
必要としていたことが、名乗る 1 行で読めるようになった。

## 7. (1) Save を安全に押す段

S5b-3 の気づき「`save_file` の設定が実走行で確かめられていない。窓のチェックは**リポジトリに
書くので Save はわざと入れていない**」に対して、S5b-5 が §13 に設計だけ置いていったもの。
設計はそのまま使えた。

* 押すのは**庭のセーブ**（F5 / `Asked::save`）で、エディタの Save ではない。エディタの Save は
  `garden/ruby/*.rb` に書くので行き先を変えられない。
* 行き先は `SaveFile::path` を判定が**一時的に差し替える**。PC は `std::env::temp_dir()` の下、
  ブラウザは `localStorage` の別の鍵 `garden:garden.checks.save.json` —
  `platform::read` / `write` が両方を同じ 2 行で扱うので、判定の側は 1 つの道で書ける。
* `window_selftest` は Bevy の引数 15 個だったので、`SaveFile` / `Asked` / `SaveNote` の 3 つを
  **`TheSave` という `SystemParam` 1 つ**にまとめた（`FakePointer`・`HudLook`・`BothVms` に
  続いて 4 度目）。16 個ちょうどになった。
* **利用者の道を元に戻すのは、判定を書く前**。落ちた判定が「庭のセーブが一時ファイルを
  指したまま」を残さないため。
* 後片付けは PC ではファイルを消し、ページでは鍵を空にする（`platform::forget`）。

### 実物が設計に無かった穴を 1 つ出した

最初のブラウザ走行で **2 行とも FAIL**:

```
selftest: FAIL F5 writes a garden where `save_file` says (0 bytes, version 1)
selftest: FAIL and the game says so rather than reporting trouble (garden.from-another-version.json: …)
```

`0 bytes` が印だった。待ちの条件を `platform::read(path).is_ok()` と書いていたが、
**ページの `forget` は鍵を消さずに空文字を書く**ので、押す直前の後片付けが自分で条件を
満たしてしまい、`save_world` が書く前のフレームで判定していた。待つのは「ファイルがあること」
ではなく「庭があること」なので、`is_ok_and(|t| !t.is_empty())` に直した。
2 行目の FAIL はその巻き添えで、`SaveNote` が更新されないまま前の（版違いのセーブを断った）
文面を持っていた。

待ちの上限は `SAVE_FRAMES = 2` で、**導出**: 判定が `Asked::save` を立て、
`save_load_keys` がそれを `SaveNow` にし、`save_world`（その後に順序づけられている）が書く。
`window_selftest` はどれとも順序を持たないので、旗が読まれるのはこのフレームか次のフレーム、
書かれるのは読まれたのと同じフレーム。**2 で、1 にはできない**。

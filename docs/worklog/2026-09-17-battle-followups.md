## 1. reflex の優先度をひっくり返す（`prelude.rb`、`scout.rb`）

### 何が間違っていたのか

計画書（D1）は「reflex の優先度はメインより高く（数が小さい）」と書いていた。実装してみると、
これは**後勝ちの `act` と噛み合わない**。優先度が高い＝そのフレームで**先に**走る＝リクエストが
先に積まれる＝あとから積まれた脳の `act` が上書きする。速いことが負ける理由になる、という形である。
D1 はそれを仕様として受け入れて、スカウトの側に回避策を置いた——reflex が 0.05 秒ごとに `act` を
言い直して舵を握り直し、脳は `@swerve` が立っている間は手を引く。worklog には
「優先度を**下げれば**後勝ちで勝てる、というひっくり返った解もある」と書いて残してあった。
今回はその解を採る、という判断である。

### 変えたのは 2 行

`prelude.rb` の `start_reflexes`:

```ruby
priority = here.priority - 20   # 前: 脳より高い
priority = here.priority + 20   # 後: 脳より低い（255 で頭打ち）
```

脳は `Script::with_priority(100)`（再読み込みは 128）なので、reflex は 120（148）になる。

### 回避策は本当に要らなくなったのか——測った

スカウトの reflex を「`act` 1 回 + `sleep 0.3`」に縮めて、selftest の
`the heading changed within 0.3 s of the hit`（被弾から 0.3 秒のうちに 0.2 rad 以上向きが変わること）を
`--headless 20` で回した。**この段の数字はすべて「質問の往復が 2 フレーム」の状態のものである**
（2 番はまだ入っていない）。あとで効いてくるので断っておく。

| reflex の優先度 | reflex の書き方 | 5 回（3 回）の結果 |
|---|---|---|
| 低い（`+20`、今） | `act` 1 回 + `sleep 0.3` | **5/5 通過**（12/12、16/16、17/17、13/13、11/11） |
| 高い（`-20`、前） | `act` 1 回 + `sleep 0.3` | **3 回中 2 回 FAIL**（13/14、24/26、13/13） |
| 高い（`-20`、前） | `6.times { act; sleep 0.05 }` | 3/3 通過（12/12、13/13、14/14） |

対照（真ん中の行）を取ったのは、「通るようになった」のが優先度のおかげだと言うためである。
同じ 1 回の `act` で、優先度だけを戻すと落ちる。

**旋回の大きさも変わった。** 1 回の走りの `(… rad)` を並べると、低い優先度では最小 0.48・
最頻 0.74（旋回速度の頭打ち）で、15 回すべてが 0.48 以上。前の「握り直す」形では 0.25・0.30・0.31 が
混じっていた。握り直しは**舵を取り合っている**ので、脳が上書きした frame のぶんだけ旋回が痩せる。
優先度を直すと取り合いそのものが無くなる。

### `@swerve` は残す（そして見る場所が足りていなかった）

優先度で直るのは「同じフレームの中でどちらが後か」だけである。被弾の瞬間、脳はたいてい質問を飛ばしていて
（`@swerve` を見て、レーダーを聞いた）、その答えが返ってから出す `act` は**別のフレーム**に来る。
これは順序では止まらないので、脳が `@swerve` を見て手を引く取り決めは要る。
`scout.rb` のコメントもそう書き直した。

**この段の 5/5 は、2 番を入れたら 2/5 になる。** 脳が `@swerve` を見る場所が
ループの頭だけだったからで、そこは「番外」の 3 つめで直している。

## 2. `answer_requests` を `RubevySet::Answer` に入れる（`main.rs`）

### 鎖ごと動かすか、1 本だけ出すか

rubevy の worklog は「13 本の `.chain()` の中にいるので、鎖ごと `Answer` に入れるか、
`answer_requests` だけ鎖から出して `Answer` に入れるかはゲーム側の判断」と書いていた。
**鎖ごとにした。** 鎖の中の順序はこのゲームの規則そのものだからである——
`restart_match` → `answer_requests` → `move_robots` → … の並びは、
「答えを返してコントロールを設定してから、そのコントロールで戦車を動かす」という意味を持っている。
`answer_requests` だけを抜くと、この 1 本と `move_robots` の間の順序が指定なしに戻り、
`act` が効くのが 1 フレーム遅れるかどうかが executor のくじ引きになる。
往復を 1 フレームにする作業で、別のところに 1 フレームのくじを作るのは筋が悪い。

鎖の他の 12 本が `Answer` の中で回ることになるが、`ScriptWorld` を触るのは `answer_requests` と
`restart_match`／`reload_changed`（`Script`/`ScriptTask` の付け外し、どれも `Commands` 経由）だけで、
`Answer` の中に rubevy 自身の `answer_components` が同居しても順序の要求は無い。

### 測り直した

`sabibots/ruby/robots/study.rb` として置き、`matches/training.rb` を
「study 1 体 + 的の scout 1 体」に差し替えて `--headless 12`。測ったあと両方とも消してある。

変更前（rubevy `fa37eaa` に上げただけ、`in_set` なし）:

```
study: act x20 = 20 frames (1.0 each)
study: A: the scout's decision (radar + incoming + act) x20 = 60 frames (3.0 each)
study: Proxy#method_missing -> ask x20 = 20 frames (1.0 each)
```

**ask の往復 2 → 1、スカウトの 1 判断 6 → 3。**

成分読みの側も測り直した。こちらは `--headless` が `MinimalPlugins` で型レジストリが空なので、
D3 のときと同じく `register_type::<Transform>()` を一時的に足して（測ったあと消した）:

**成分読みは 1 フレームのまま。** rubevy が `answer_components` を鎖の先頭から末尾に動かしても
起きるフレームは同じ、と向こうの worklog が書いていたとおりである。
つまり今回の変更で消えたのは「ゲームが答える質問だけが 2 フレームだった」という**差**で、
`docs/sabiruby-battle.md` の *Why not `Rubevy.entity[:Transform]` and `Rubevy::Proxy`* の
「成分読みのほうが速い」という但し書きは要らなくなった（結論は変わらない——値段は質問の**数**である）。
`find(:Transform)` は 344 件で、D3 のときの 345 件とは 1 件違う。飛んでいる弾の数が違うだけである。

### 手触りは変わった。ロボットは調整していない

スカウトの 1 判断が 6 フレーム（100 ms）から 3 フレーム（50 ms）になり、`sleep 0.05` と合わせて
ループの周期が約 150 ms → 約 100 ms になる。**狙って撃つ回数が 1.5 倍になる**ということなので、
当たる数も増える。selftest が見ている被弾（reflex を持つロボットが受けた命中）を
20 秒の走り 5 回で数えると:

| | 5 回の被弾数 |
|---|---|
| 変更前（優先度の変更だけ入れた状態） | 12, 16, 17, 13, 11 |
| `RubevySet::Answer` のあと | 18, 17, 15, 21, 27 |

指示どおりロボットは**調整していない**。ここに書いておくのは、あとでロボットの強さを比べる人が
「このコミットの前後の数字は比べられない」と分かるようにするためである。
selftest は 5 回とも通る（reflex が走った・向きが変わった、どちらも全件）。

## 3. 一時停止——呼ぶものは無い。測る形を決めるのに時間を使った（`main.rs` の selftest）

rubevy `fa37eaa` は「`budget == 0` のフレームは `task_advance_ticks` を呼ばない」という規則にした。
`P` は前から `world.budget = 0` と書いているので、**ゲームのコードは 1 行も変わらない**。
D2 の worklog が「再開の瞬間に寝ていたタスクが全部起きる。直すなら rubevy の `tick_scripts`」と
書いて残した穴が、向こうで埋まったという話である。仕事は「埋まったことをこちらで測る」だけ。

### 何で測るか——3 つ考えて 2 つ捨てた

**捨てた 1: 命令数。** 「再開のフレームで走った命令が 0」。いちばん素直に見えるが、判定にならない。
1 ティックは 4 ms（`TICK_UNIT_MS`）で 1 フレームは約 16 ms＝4 ティック、脳の `sleep 0.05` は 13 ティック。
止めた瞬間に残り 3 ティックだったタスクは、直っていても再開のフレームで起きる。
「0 であるべき」は止める瞬間の位相しだいで、5 回に 1 回くらい落ちる検査になる。

**捨てた 2: 起きたタスクの数を数えて「全部ではない」と言う。** 直っていなければ寝ていたタスクは
**全部**起きる（0.5 秒分の締め切りが全部過ぎている）ので、「全部より少ない」は一応の判定になる。
ただし 5 本のタスクの残りティックがそろって 4 以下になる目は残るし、
「全部ではない」は主張として弱い。これも捨てた。

**採った: スケジューラの時計そのもの。** `Vm::task_next_wakeup_ticks()` は
「いちばん早い寝ているタスクがあと何ティックで起きるか」を返す。時計が止まっていれば、
0.5 秒止めているあいだこの値は**動かない**。時計が動いていれば、13 ティック（52 ms）で 0 に落ちて
そこに貼り付く。つまり**同じ数であること**が「寝ていたものの締め切りが 1 ティックも近づかなかった」
＝「再開のフレームで起きるものは、止めなかった場合と同じ」の言い換えになる。
位相に依らないし、直っていなければ必ず落ちる。

### 手順

止めた 0.1 秒後（`P` の効果がそのフレームに入ったかどうかを気にしなくてよくなる位置）に
`task_next_wakeup_ticks()` を控え、そこからさらに 0.5 秒——脳の `sleep 0.05` の 10 倍——置いて、
同じ値かを見る。控えた値が `Some(0)`（止めた瞬間に既に締め切りが過ぎていたタスクがあった）や
`None`（誰も寝ていない）のときは**測れないので数えない**——`selftest: --` の行を出す。
reflex の検査が「0.3 秒のうちに落ちたロボットは数えない」と同じ扱いで、
`ok`/`FAIL` に化けた `--` があとで嘘をつくよりよい。

一時停止の段は「`P` を押す」「0.1 秒後に時計を控える」「0.5 秒後に見て `P` を戻す」
「0.5 秒後に走り出したことを見る」の 4 つになった。段が 1 つ増えたので `step` の番号は
1 つずつ後ろにずれている（このあとの「番外」でもう 1 つ増えて、最終的に 0..9 の 10 段になる）。
「止めているあいだ命令が 1 つも増えない」「パネルにフレームとヒープがある」の 4 本は
`P` を戻す直前の段に移してあり、測る区間（`P` を押す前から 0.6 秒後まで）は前と同じである。

## 番外. 2 番が見えるようにした 3 つの穴（`main.rs` の selftest、`scout.rb`）

どれも 2 番（往復 1 フレーム）そのものの不具合ではない。前からあって、
ロボットが 1.5 倍の頻度で判断するようになったせいで踏むようになったものである。
コミットは 1 つにまとめた。

### 1 つめ——「再起動したロボットは満タン」

窓の selftest を回したら、`every robot starts with full health` が**毎回落ちる**ようになっていた
（4 回中 4 回）。これは 2 番の副作用である。この検査は `R` で試合をやり直したあと **2 秒待って**
hp を見ていた。往復が 1 フレームになってロボットの判断が 1.5 倍の頻度になったので、
仕切り直しから 2 秒のうちにもう誰かが被弾している。ロボットは悪くないし、
検査が言いたいこと（「やり直すと新しいロボットが満タンで出てくる」）も間違っていない。
**待ち時間が測りたいものと関係なかった**だけである。

やり直しの直前に今いるロボットのエンティティを控えておき、
「控えたものに含まれないロボットが 4 体そろったフレーム」で hp を見るようにした
（そろわなければ 2 秒で諦めて、そのまま検査して落とす）。出てきた瞬間なら誰も撃たれていないので、
試合の速さに依らない。残りの検査（ロボット 3 はファイルに戻る、4 は当てた脳のまま、
壁が角で終わる）は壁の作り直しを待つ必要があるので、そこからさらに 1 秒置いた段に残した。

### 2 つめ——3 回に 1 回の `ran a reflex` の FAIL。原因はログに書いてあった

`1 red/scout ran a reflex within 0.3 s of the hit at …` が 7 回中 2 回落ちた。
落ちた回のログをその時刻の前後で読んだら、命中のすぐ前に

```
Scout: reflex hit off
Scout: reflex hit off
Scout: online
Scout: online
```

が並んでいた。**エディタの Apply（ApplyAll）でロボットの脳が差し替えられている最中の命中**である。
差し替えは古い `ScriptTask` を外す——購読が閉じ、reflex のタスクが `Unsubscribed` で終わり
（`reflex hit off`）、新しいタスクが `online` と言ってから購読を取り直す。
その間に publish された `hit` は**誰にも届かない**。同じ命中で `turned` も 0.12 rad で落ちていて、
「reflex が走らなかった」は本当だった——走るべきロボットがそこに居なかっただけである。

これは 2 番で増えた命中の頻度が、もともと空いていた穴を踏みやすくしたものである
（エディタの selftest は試合の最中に脳を 3 回当て直す）。
検査の側に「倒れたロボットは数えない」と同じ扱いをもう 1 つ足した——
**窓の中で脳が差し替わったロボットは数えない**。

目印を 1 回間違えている。最初は `reflex_off`（そのロボットの reflex タスクが終わった回数）を
控えて、0.3 秒後に増えていたら数えない、とした。4 回回すと `ran a reflex` の FAIL は消えたが、
今度は `turned … (0.12 rad)` だけが 1 回落ちた——**reflex は走ったのに舵が戻っている**。
理由は同じ差し替えの、別の入り口である。reflex のタスクが `queue.pop` で待っているときに購読が
閉じれば `Unsubscribed` が上がって `reflex :off` を言うが、**`sleep 0.3` の最中に外から
terminate されたタスクは巻き戻らない**ので `:off` を言わない。`reflex_off` は増えず、
振り出した舵だけが途中で消える。

目印を「そのロボットの脳が走っているタスク」（`ScriptTask::task()`）に変えた。
差し替えは古い `ScriptTask` を外して新しい `Script` を入れるので、タスクは必ず別のものになる。
命中の時点の `Option<ObjId>` を控え、0.3 秒後に違っていれば `--` の行を出して数えない。
これは上の 2 つの入り口を両方とも覆う。

### 3 つめ——1 番の「回避策は要らなくなった」は、2 番のあとでは早すぎた

1 番を入れた時点で、スカウトの reflex は `act` 1 回 + `sleep 0.3` で `--headless 20` の
5 回すべてを通っていた。2 番（往復 1 フレーム）を入れたあとに同じ検査を回すと、
**5 回中 3 回落ちる**。落ち方は `ran a reflex` は通って `turned … (0.09 / 0.11 / 0.18 rad)` だけが
落ちる、つまり**舵は振ったのに 0.3 秒のうちに戻されている**という形である。

理由は 1 番の worklog に書いた「優先度では直らないほう」がそのまま表に出ただけである。
被弾の瞬間、脳はたいてい質問を飛ばしている。脳は `@swerve` をループの**頭**で見てから
`radar` → `incoming` と聞き、その答えが返ってから `act` する。頭で見たときにはまだ
`@swerve` は立っていないので、**被弾前に決めた `act`** が数フレーム後に舵を打ち消す。
往復が 2 フレームだったころ、その `act` は被弾の 6 フレーム（約 100 ms）後に届いていた。
0.3 秒の窓のうち 100 ms ぶん舵が入れば 0.2 rad は超えるので、検査は通っていた。
往復が 1 フレームになって、同じ `act` が**3 フレーム（約 50 ms）後**に届くようになった。
50 ms ぶんの旋回は 0.09〜0.18 rad で、しきい値に届かない。
**速くしたことが、取り決めの穴を見えるようにした。**

直したのは reflex ではなく脳のほうである。`@swerve` を見る場所を、ループの頭だけでなく
**`act` を呼ぶ直前**にも置いた。取り決めは「reflex が舵を握っているあいだ脳は操作に触らない」で、
触るのは `act` の行なのだから、見るのもそこでなければならない。ループの頭で見るのは
「質問を無駄にしない」ためのもので、取り決めの本体ではなかった。

これで reflex 側の回避策（0.05 秒ごとに `act` を言い直す）は入れ直さずに済んでいる。
`--headless 20` を 10 回回して 10 回とも通る（下の「確認」）。

余裕も測った。直したあとにもう 3 回回して、命中 57 件の旋回はすべて **0.74 rad**——
0.3 秒で戦車が回れるいっぱいである。**誰も舵を取り返していない。** 前の形（握り直す）では
0.25〜0.78 rad にばらけていて、そのばらつきこそが脳と reflex の取り合いだったことになる。

## 4. `Vm::task_context` で文字列解析を捨てる（`crates/rubevy-arena/src/inspect.rs`）

D2 で VM パネルを作ったとき、「このタスクは VM の何番目のコンテキストに立っているか」を
返す入り口が sabiruby に無かった。`Vm::snapshot` は全コンテキストを返し、`Vm::task_*` は
1 タスクについて答えるが、2 つをつなぐものが無い。ところが `Vm::render` がタスクを
`#<Task 12 ctx=3>` と描くので、**ctx は文字列としてなら公開されていた**。
`inspect.rs` はそれを読んでいた——`ctx=` を探して、続く数字を取って、`parse` する 4 行である。
デバッグ用の書式は API ではないので、読めなければ静かに諦める（コンテキスト無し、
パネルが理由を出す）ようにしてあった。

sabiruby 0.5.0 に `Vm::task_context(task) -> Option<usize>` が入った（`src/vm.rs:930`）。
`pub fn task_context` とその長い注意書きごと消して、呼び出し側を `vm.task_context(task)` にした。
返り値の型も `Option<usize>` で同じなので、`let Some(ctx) = … else { … }` の形はそのままである。
`sabiruby::Value` の import も要らなくなった（`Value::Obj(task)` を `render` に渡すのが
最後の用途だった）。差分は 20 行減って 1 行増える。

パネルの見え方が変わっていないことは `--headless 8` で確かめた。ヘッドレスは VM パネルの中身を
テキストで吐くので、コンテキスト番号（`context 2 Suspended`）、フレーム
（`#0 scout.rb:58 run pc 326`）、レジスタ（`target=#<Contact:…> threat=nil …`）が
前と同じ形で出る。

この 4 つ目は、D2 の worklog が「VM に欲しいのは `Vm::task_context(task)` か
`Vm::task_snapshot(task, regs_frames)`、**小さいほうで足りる**」と書いて残していたものが、
小さいほうで入って戻ってきた、という形になっている。

## 全体の確認

```
cargo build --release -p sabibots                                   ok（warning 0）
SABIBOTS_SELFTEST=1 ./target/release/sabibots --headless 20   ×5    全件 ok
SABIBOTS_SELFTEST=1 docker/run.sh sabibots release            ×5    全件 ok（窓の検査、lavapipe）
docker/run.sh sabibots release --shot …                             撮れた
web/build.sh sabibots                                               ok
```

窓の検査は WSL2 に GPU ドライバが無いので Docker + lavapipe（`docs/wsl-gpu.md`）で回した。
素の `./target/release/sabibots` は `bevy_render` がアダプタを見つけられずに panic する——
これは前からで、今回の変更とは関係ない。

`--shot` は `target/shot.png` に撮って中身を見た。スコアボードの `1 scout x1` / `3 scout x5`
（reflex が走った回数）、VM パネルの `context 2 Suspended`・フレーム 5 段
（`scout.rb:64` → `loop` → `scout.rb:28` → `prelude.rb:230` → `scout.rb:69`）・
名前つきレジスタ（`target` / `threat` / `heading`）、エディタの scout.rb——全部出ている。
4 番でパネルの中身が変わっていないことの、ヘッドレス以外の確認でもある。

`web/build.sh sabibots` は通る。この機械には `wasm-opt` が入っていないので
`game_bg.wasm` は 36.0 MB（gzip 9.3 MB）と出るが、`docs/web.md` の表（26.7 MB / 8.1 MB）は
`wasm-opt -Os` をかけた値なので**比べられない**。表は触っていない。

ベンチは取っていない（指示どおり。このリポジトリにベンチは無い）。
この作業のあいだ、同じ機械で別の担当が `garden` を Docker でビルドしていた——
時間のかかり方には効いているが、測っているのはフレーム数と検査の通過数なので影響はない。

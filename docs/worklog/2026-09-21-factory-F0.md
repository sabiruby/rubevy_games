## 2. `TilemapChunk` は WebGL2 で描けるか — PC は一発、ブラウザは真っ黒

計画のいちばん危ない前提。結論は「**描ける。ただし条件がある**」で、条件は素材の側にあった。

### 2.1 PC（docker / lavapipe）

`bevy-0.19.1/examples/2d/tilemap_chunk.rs` のとおりに書いた。タイルセットは
`AssetServer::load_builder().with_settings(|s| s.array_layout = …)` で配列テクスチャとして読む
（`.meta` は `AssetMetaCheck::Never` なので使えない。計画書 §5）。最初は
`ImageArrayLayout::GridSize { 16, 16 }` で Kenney のシートをそのまま 12×11 に切った。

`docker/build.sh factory release` → `docker/run.sh factory release --shot /app/factory-shot.png 3`。
**床が出た。** 絵の確かめ方は `2026-09-18-web-black-screen.md` の流儀で画素を数える:

```
pc-floor.png  1600x900  distinct 4  パックの床の色が画面の 99.9998%
  #eaa56c  892225  61.96%
  #da9256  547772  38.04%
  （残り 3 画素は縁のにじみ。2.4 参照）
```

色が 2 つしかないのは床のタイル 0/1/2 がその 2 色で描かれているからで、
**その 2 色はパックの `tilemap_packed.png` の 0–2 番から読み出したものと一致する**。
真っ黒でも真っ白でもない、という以上のことが言える。

判定も同じ走行で `ok`:
`the tileset arrived as an array of 132 layers of 16 by 16 px (frame 3)`。

### 2.2 ブラウザ — 真っ黒、pageerror 0、判定は全部 ok

`web/build.sh factory` → Playwright（SwiftShader、`waitUntil:'commit'`）。

```
pageerror: 0        requestfailed or >=400: 0
selftest lines: 5   ok 4  FAIL 0  -- 0  done 1
web-floor.png  1600x900  distinct 1   (0,0,0) が 1,440,000 画素 = 100%
```

**判定が全部 ok なのに画面は真っ黒。** これは 2026-09-18 の黒画面より質が悪い: あのときは
`pageerror` に `Instant::now()` の panic が出ていた。今度は例外も 404 も無く、判定も
「画像は届いた、132 層 16×16、床のデータは正しい」と言う — **どれも bind の話ではない**から。

言っていたのは console のほうで、278 行のうち 250 行以上が

```
WebGL: INVALID_ENUM: bindTexture: invalid target
WebGL: INVALID_ENUM: texSubImage3D: invalid texture target
```

で、その手前に wgpu 自身のログが 1 行:

```
wgpu-hal heuristics assumed that the view dimension will be equal to `CubeArray` rather than `D2Array`.
`D2` textures with `depth_or_array_layers > 6 && depth_or_array_layers % 6 == 0`
  are assumed to have view dimension `CubeArray`
```

### 2.3 原因

`wgpu-hal-29.0.4/src/gles/mod.rs:458`、`TextureDescriptor::is_cube_compatible`
（`wgpu-hal-29.0.4/src/lib.rs:2053`）:

```rust
self.dimension == D2 && self.size.depth_or_array_layers.is_multiple_of(6)
    && self.sample_count == 1 && self.size.width == self.size.height
```

OpenGL はテクスチャを作るときに bind target を決めないといけないが、wgpu の API には
「この配列をどう見るか」を渡す所が無いので、**形から推測する**。
16×16 のタイルセットは層が**正方形**で、Kenney のシートは **132 = 6 × 22** 層。
条件が両方そろって `TEXTURE_CUBE_MAP_ARRAY` で bind され、**WebGL2 にはそれが無い**。

PC が通ったのは Vulkan では `CUBE_COMPATIBLE` は「キューブとしても見られる」という
作成フラグにすぎず、2D 配列として見ることを妨げないため。**つまりこれはバックエンドの差で、
`TilemapChunk` や WebGL2 の限界ではない。**

### 2.4 直し方 — 層の数を選べるようにした

直せるのは「層の数」だけ（正方形はやめられない）。12 列のグリッドでは何行にしても
12R で必ず 6 の倍数なので、**グリッドをやめて縦 1 列のストリップにした**。
`ImageArrayLayout::RowHeight { pixels: 16 }` は高さ ÷ 16 を層の数にするので、
枚数を 1 枚単位で選べる。

`tools/factory-tileset.py` が `factory/assets/tiles/factory-tiles.png` を組む:
Kenney の 132 枚を**パックと同じ順**で並べ（＝ **0–131 はパックの番号のまま**。
著者が拡大画像から読んだ番号がそのまま使える）、6 の倍数から外れるまで空白タイルを足す。
今は 133 層、16×2128 px、**8,812 B**。

再測定:

```
web-floor.png  1600x900  distinct 2   パックの床の色が画面の 100.0000%
  #eaa56c  892170  61.96%
  #da9256  547830  38.04%
console lines: 19（250 行の INVALID_ENUM は消えた）
pageerror 0, requestfailed 0, selftest 5 行（ok 4, done 1）
```

**PC の絵とブラウザの絵を直接比べた**: 1,440,000 画素のうち **1,439,113（99.94%）が完全に同じ**。
違う 887 画素は行・列に沿って散っていて、縮尺が非整数（900 ÷ 256 = 3.515625 画面 px /
素材 px）のときの標本化の丸めの差である。PC 側に 3 画素だけ中間色が出たのも同じ理由。
**計画書 §5 の「非整数倍のズームでにじむ」が、F0 の段階ですでに 0.06% の形で見えている** —
F1 でズームを整数倍に丸めるか、1 px 間隔つきのシートを使うかを決めるときの材料。

数 `TILESET_LAYERS = 133` はゲームの `const` に置き、判定が読み返して
「6 の倍数でないこと」まで見る。シートに何かを足したときに黙って戻らないようにするため。
スクリプトは自分で空白を足して、その理由をファイルの頭に書いている。

# F0a — 自作シートと、ベルトの向きの見本

## 6. パックのベルトを 1 画素ずつ読んだら、仕事が半分に減った

計画書 §3.6 と調査（§4）は「コンベアは右向きと上向きの直線だけ。3/4 見下ろしなので回転では
他の向きを作れない（左は反転で作れる）」と言っていた。自作シートを描く前に、パックの
ベルトのタイルを 1 画素ずつ書き出して確かめた（`scratchpad/f0/kenney/`）。**半分は違っていた。**

```
tile 26（右向き、中）            tile 16（上向き、中）
kkkkkkkkkkkkkkkk               kkLMLLLLLLLLMLkk
kkkkkkkkkkkkkkkk               kkLMLLLMMLLLMLkk
MMMMMMMMMMMMMMMM               kkLMLLMMMMLLMLkk
MLLLMMMMMLLLMMMM               kkLMMMMMMMMMMLkk
MMLLLMMMMMLLLMMM               kkLMMMMMMMMMMLkk
MMMLLLMMMMMLLLMM               kkLMMMMLLMMMMLkk
MMMLLLMMMMMLLLMM               kkLMMMLLLLMMMLkk
MMLLLMMMMMLLLMMM               kkLMMLLLLLLMMLkk
MLLLMMMMMLLLMMMM               （以下 8 行の繰り返し）
MMMMMMMMMMMMMMMM
DDDDDDDDDDDDDDDD   ← ここから下 6 行が「手前の側面」
DDDDDDDDDDDDDDDD
ddMMddddddddMMdd
MMLLMMMMMMMMLLMM
DDDDDDDDDDDDDDDD
DDDDDDDDDDDDDDDD
```

- **右向きのタイルは、シェブロンを除けば上下対称である。** 手前の側面（下 6 行）も左右対称。
  → **左向きは `MirrorH` で作れる。**（これは調査も言っていた）
- **上向きのタイルには手前の側面が無い。** 左右対称で、幅 12 px（列 2〜13）に両側の枠、
  中身はシェブロンだけ。**つまり上向きのベルトは初めから真上から見た絵である。**
  → **下向きは `MirrorV` で作れる**し、90 度回せばそのまま横向きの真上ベルトになる。

**足りないのは曲がりだけだった。** 「4 向きを個別に描く」という (i) の仕事の大半は、そもそも
要らない。残る違いは曲がりの枚数と、見た目である。

| | 直線に要る絵 | 曲がりに要る絵 | 合計 |
|---|---|---|---|
| **(i) 3/4 を活かす** | 0（パックの 2 枚 + 反転） | **4**（形 4 つ × 流れる向き 2 つ = 8 通り。`MirrorH` は側面を下に保つので半分になるが、回転は側面を横や上に持っていくので使えない） | **4 枚 × 2 コマ = 8 タイル** |

## 8. 見本 2 枚

`factory/src/belt_sample.rs`（**F1 が消す**。ファイルの頭にそう書いてある）。

見本のときだけ地図は 16 タイル、視野は 12 タイル（絵が 11 行 + 余白 1）に切り替わる。

**スクリーンショット**（PC、docker/lavapipe、`--shot`）:

| | |
|---|---|
| (i) 3/4 を活かす | `scratchpad/f0/belts-i.png`（拡大 `belts-i-left.png` / `belts-i-right.png`） |
| (ii) 真上から | `scratchpad/f0/belts-ii.png`（拡大 `belts-ii-left.png` / `belts-ii-right.png`） |

見た所見（著者が決める材料であって、決めてはいない）:

- **(i)** は横向きのベルトに手前の側面があるぶん**機械と同じ立体感**で並ぶ。かわりに、
  横のベルトは 14 px（面 8 + 側面 6）、縦のベルトは 12 px で、**曲がる所で幅と高さが変わる**のが
  拡大すると見える。ループの上辺と下辺が縦辺より太く見えるのもそのため。
- **(ii)** は 4 辺が同じ太さで、曲がりも滑らかにつながる。かわりに**ベルトだけ真上**になるので、
  3/4 で描かれた機械（75–77 など）と並ぶと平たく見える。
- **2 コマのアニメーション**: どちらもシェブロンを進行方向へ半周期（4 px）ずらした 2 枚目を
  持っている。(i) は絵が 4 枚 × 2 = 8 タイル、(ii) は 2 枚 × 2 = 4 タイルで、
  **アニメーションの枚数は絵の枚数にそのまま比例する** — F1 で鉱石・インサータ・アイコンが
  増えることを思うと、ここは (ii) が軽い。
- **(i) の曲がりはパックの縦ベルトとぴったりは繋がらない**: 曲がりの上端の断面は
  `kkkMMMMMMMMMMLDD` で、パックの縦ベルトの `kkLMLLLLLLLLMLkk` と両端が違う（側面が
  タイルの外へはみ出す）。描き直せば直るが、(i) を選ぶなら**その手直しが F1 の仕事に入る**。
- どちらの絵も**下書き**である。著者に聞いているのは「どちらの方向で進めるか」であって、
  この画素で良いかではない。

## 10. 気づいた点（仕事の範囲の外。直していない）

1. **Battle のハンドラの判定が、ブラウザの窓を大きくすると落ちる。**
   `sabibots/src/main.rs:1908,1912`（`handler_selftest`）。`?selftest` のページを Playwright の
   **既定のビューポート（1280×720）**で回すと FAIL 0 だが、**1600×900** にすると
   `N blue/scout ran a handler within 0.3 s of the hit at … s` と `… turned within 0.3 s …` が
   毎回 2 行 FAIL する（1600×900 で 3 走行、1280×720 で 2 走行。同じビルド、同じページ）。
   canvas が大きいぶん SwiftShader のフレームが遅くなり、**壁時計の 0.3 秒に入るフレーム数が
   減る**のが読み。S7（`2026-09-20-window-check-fixes.md`）が箱庭の判定に対してやった
   「秒で待たずに条件で待ち、上限はフレームで導く」が、Battle のこの判定には入っていない。
   `tools/fixedlines.sh` はこの 2 行を落とす（`of the hit at` を含む行）ので**行の集合は
   一致したまま**で、一覧の基準では見えない。属する先: **バグ（再現手順つき）** ／ Battle 固有。
   再現: `web/build.sh sabibots` の後、`page = await browser.newPage({viewport:{width:1600,height:900}})`
   で `…/sabibots/?selftest` を 100 秒開く。

2. **`tools/fixedlines.sh` が CR を落とさない。** `docker/run.sh` は `-t` 付きで走らせるので
   窓の走行の各行は `\r` で終わり、`diff` が 32 行すべて違うと言う。`tr -d '\r'` を挟めば直る。
   1 行足せば済むが、道具の振る舞いを変えると過去の比較と揃わなくなるので触っていない。
   `verification/selftest-lines.md` に注意書きだけ足した。属する先: **道具**。

3. **`TilemapChunk` の層の数の罠は rubevy_games に限らない。** 「正方形のタイル × 6 の倍数の
   枚数」で WebGL2 が黙って真っ黒になるのは、Bevy 0.19 の `TilemapChunk` を配列テクスチャで
   使う誰にでも起きる。Bevy 本体の example（`2d/tilemap_chunk.rs`）は 4 層なので当たらない。
   例外も 404 も出ず、ゲームの判定は全部 `ok` を出すので、**スクリーンショットの画素を数える
   以外に気づく道が無い**。属する先: **本（移植の章）の素材** ／ 上流（wgpu か Bevy）に
   報告する価値がありそう。rubevy 側の話ではない。

4. **`--shot` と `<GAME>_SELFTEST` は同時に使えない。** 判定が済むと
   `CHECKS_EXIT_WHEN_DONE` でアプリが終わるので、`--shot` の時刻が来る前に窓が閉じる。
   3 本とも同じ作り。絵を撮るときは判定を外す、で回避した。属する先: **共有 crate**
   （`games_shell::checks`）か、各ゲームの `take_shot`。

5. **Kenney の縦ベルトは初めから真上の絵である**（§6）。調査（`2026-09-20-factory-survey.md` §4）の
   「3/4 見下ろしなので回転では他の向きを作れない」は横向きのタイルにだけ当てはまる。
   属する先: **計画書の前提違い**（§3.6 の「足りないもの」の行）。

6. **PC（Vulkan）とブラウザ（WebGL2）で絵が 0.06% 違う。** 1,440,000 画素のうち 887 画素で、
   縮尺が非整数（1 素材 px あたり 3.515625 画面 px）のときの標本化の丸めの差。今は無害だが、
   計画書 §5 の「非整数倍のズームでにじむ」はこの形で既に出ている。属する先: **Factory 固有**
   （F1 でズームを整数倍に丸めるかどうかの材料）。

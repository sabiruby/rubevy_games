## 2. `TilemapChunk` は WebGL2 で描けるか — PC は一発、ブラウザは真っ黒

計画のいちばん危ない前提。結論は「**描ける。ただし条件がある**」で、条件は素材の側にあった。

### 2.1 PC（docker / lavapipe）

`bevy-0.19.1/examples/2d/tilemap_chunk.rs` のとおりに書いた。タイルセットは
`AssetServer::load_builder().with_settings(|s| s.array_layout = …)` で配列テクスチャとして読む
（`.meta` は `AssetMetaCheck::Never` なので使えない。計画書 §5）。最初は
`ImageArrayLayout::GridSize { 16, 16 }` で Kenney のシートをそのまま 12×11 に切った。

`docker/build.sh factory release` → `docker/run.sh factory release --shot /app/factory-shot.png 3`。
**床が出た。** 絵の確かめ方は `2026-09-18-web-black-screen.md` の流儀で画素を数える:

```
pc-floor.png  1600x900  distinct 4  パックの床の色が画面の 99.9998%
  #eaa56c  892225  61.96%
  #da9256  547772  38.04%
  （残り 3 画素は縁のにじみ。2.4 参照）
```

色が 2 つしかないのは床のタイル 0/1/2 がその 2 色で描かれているからで、
**その 2 色はパックの `tilemap_packed.png` の 0–2 番から読み出したものと一致する**。
真っ黒でも真っ白でもない、という以上のことが言える。

判定も同じ走行で `ok`:
`the tileset arrived as an array of 132 layers of 16 by 16 px (frame 3)`。

### 2.2 ブラウザ — 真っ黒、pageerror 0、判定は全部 ok

`web/build.sh factory` → Playwright（SwiftShader、`waitUntil:'commit'`）。

```
pageerror: 0        requestfailed or >=400: 0
selftest lines: 5   ok 4  FAIL 0  -- 0  done 1
web-floor.png  1600x900  distinct 1   (0,0,0) が 1,440,000 画素 = 100%
```

**判定が全部 ok なのに画面は真っ黒。** これは 2026-09-18 の黒画面より質が悪い: あのときは
`pageerror` に `Instant::now()` の panic が出ていた。今度は例外も 404 も無く、判定も
「画像は届いた、132 層 16×16、床のデータは正しい」と言う — **どれも bind の話ではない**から。

言っていたのは console のほうで、278 行のうち 250 行以上が

```
WebGL: INVALID_ENUM: bindTexture: invalid target
WebGL: INVALID_ENUM: texSubImage3D: invalid texture target
```

で、その手前に wgpu 自身のログが 1 行:

```
wgpu-hal heuristics assumed that the view dimension will be equal to `CubeArray` rather than `D2Array`.
`D2` textures with `depth_or_array_layers > 6 && depth_or_array_layers % 6 == 0`
  are assumed to have view dimension `CubeArray`
```

### 2.3 原因

`wgpu-hal-29.0.4/src/gles/mod.rs:458`、`TextureDescriptor::is_cube_compatible`
（`wgpu-hal-29.0.4/src/lib.rs:2053`）:

```rust
self.dimension == D2 && self.size.depth_or_array_layers.is_multiple_of(6)
    && self.sample_count == 1 && self.size.width == self.size.height
```

OpenGL はテクスチャを作るときに bind target を決めないといけないが、wgpu の API には
「この配列をどう見るか」を渡す所が無いので、**形から推測する**。
16×16 のタイルセットは層が**正方形**で、Kenney のシートは **132 = 6 × 22** 層。
条件が両方そろって `TEXTURE_CUBE_MAP_ARRAY` で bind され、**WebGL2 にはそれが無い**。

PC が通ったのは Vulkan では `CUBE_COMPATIBLE` は「キューブとしても見られる」という
作成フラグにすぎず、2D 配列として見ることを妨げないため。**つまりこれはバックエンドの差で、
`TilemapChunk` や WebGL2 の限界ではない。**

### 2.4 直し方 — 層の数を選べるようにした

直せるのは「層の数」だけ（正方形はやめられない）。12 列のグリッドでは何行にしても
12R で必ず 6 の倍数なので、**グリッドをやめて縦 1 列のストリップにした**。
`ImageArrayLayout::RowHeight { pixels: 16 }` は高さ ÷ 16 を層の数にするので、
枚数を 1 枚単位で選べる。

`tools/factory-tileset.py` が `factory/assets/tiles/factory-tiles.png` を組む:
Kenney の 132 枚を**パックと同じ順**で並べ（＝ **0–131 はパックの番号のまま**。
著者が拡大画像から読んだ番号がそのまま使える）、6 の倍数から外れるまで空白タイルを足す。
今は 133 層、16×2128 px、**8,812 B**。

再測定:

```
web-floor.png  1600x900  distinct 2   パックの床の色が画面の 100.0000%
  #eaa56c  892170  61.96%
  #da9256  547830  38.04%
console lines: 19（250 行の INVALID_ENUM は消えた）
pageerror 0, requestfailed 0, selftest 5 行（ok 4, done 1）
```

**PC の絵とブラウザの絵を直接比べた**: 1,440,000 画素のうち **1,439,113（99.94%）が完全に同じ**。
違う 887 画素は行・列に沿って散っていて、縮尺が非整数（900 ÷ 256 = 3.515625 画面 px /
素材 px）のときの標本化の丸めの差である。PC 側に 3 画素だけ中間色が出たのも同じ理由。
**計画書 §5 の「非整数倍のズームでにじむ」が、F0 の段階ですでに 0.06% の形で見えている** —
F1 でズームを整数倍に丸めるか、1 px 間隔つきのシートを使うかを決めるときの材料。

数 `TILESET_LAYERS = 133` はゲームの `const` に置き、判定が読み返して
「6 の倍数でないこと」まで見る。シートに何かを足したときに黙って戻らないようにするため。
スクリプトは自分で空白を足して、その理由をファイルの頭に書いている。

## 3. crate の骨組み

`factory/`。`sabibots/` を手本にしたが、**写さなかったものを Cargo.toml にコメントで挙げた**
（`sabiruby-serde` は F2、`rubevy-egui` と `bevy_egui` は F5、`sabiruby-compiler`・`web-sys`・
`js-sys`・`wasm-bindgen` は S1 以降 `games_shell::platform` が持っている）。
`build.rs` は `rubevy_build::Embed::new("ruby").write()` の 1 行、`src/platform.rs` は
ゲーム固有の名前だけ（`factory:`、`factory.settings.txt`、`factoryCompile` / `factoryHighlight`、
`FACTORY_SELFTEST`）。

`Cargo.toml`（workspace）の bevy の feature に `bevy_sprite_render` を**明示で**足した。
`bevy_ui_render` 経由で既に有効なので**ビルドは 1 バイトも変わらない**が、3 本目の床が
一覧に出てこない feature に寄りかかっている状態をやめた。

### 3.1 ヘッドレスで 2 回落ちた

1 回目: `TilemapChunk` を spawn した瞬間に panic。挿入フックが `TilemapChunkMeshCache` と
`Assets<TilemapChunkMaterial>` を要求するが、どちらも `SpriteRenderPlugin` のもので、
ヘッドレスには無い。

直し方は**設計を分けること**にした。格子はゲームの `Floor`（`Vec<u16>`）という Resource で、
`TilemapChunk` は**その絵**でしかなく、窓のある走行だけが spawn する。
これは F1 がどのみち要る形でもある（コンベアと機械は Rust の格子で、描くのはその view）。

2 回目: `MessageReader<WorldClick>` が "Message not initialized" で落ちた。`WorldClick` を
登録しているのは `CameraPlugin` で、ヘッドレスはそれを足さない。ヘッドレス側で
`add_message::<WorldClick>()` を足した。クリックの道が両方の走行で 1 本になるので、
**判定がクリックを偽造して、マウスの無い所で座標変換を測れる**。

### 3.2 判定（4 行）

秒ではなく条件で待つ:

| 行 | どう待つか |
|---|---|
| `the floor is N by N tiles, all N of them laid with a tile of the sheet` | `Floor` が入ったフレーム |
| `a world point and the tile it is in agree at the corners and the middle (N/N), and a point off the map is off it` | 純粋な計算。四隅と中央と、地図の外 1 点 |
| `the tileset arrived as an array of N layers of N by N px (frame N)` | `Assets<Image>` に入るまで。上限は **400 フレーム**（実測はコンテナ 3・ブラウザ 4 フレーム、その 100 倍）。chunk が無い走行（ヘッドレス）は待たずに `--` |
| `a click in the middle of a tile is read as that tile (asked …, read …)` | `WorldClick` を書いた次のフレームに `LastClick` を読む |

行の形（`selftest: ok   …` の空白 3 つ）は既存 2 本に合わせてある — 最初 4 つにしていて、
`tools/fixedlines.sh` には通るが一覧の書式と揃わないので直した。

単体テストも 3 本（`cargo test -p factory`）: タイルの中心はそのタイルに入る、
地図の縁はちょうど 1 タイルに属して外は外、床のどのタイルもシートの範囲に収まる。

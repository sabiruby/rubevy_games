# 2026-09-16 `reflex`（`showpieces-plan.md` の D1）

`docs/plans/showpieces-plan.md` の D1。被弾のたびに、ロボットのメインのループとは別のタスクでブロックを走らせる。
ブランチ `reflex`（main `1f26f23` から）。1 体のロボットが mruby-task のタスクを 2 本以上使う最初の機能なので、
「タスクが増えると何が壊れるか」を洗い出すのが実質の仕事だった。結論から書くと、**壊れたのは 3 か所**で、
どれも計画書には書かれていなかった。

## まず読んだところ

rubevy 側の `docs/host-api.md` の Events 節と `assets/scripts/events.rb`、`src/lib.rs:1306` の
`Rubevy.subscribe`、`src/lib.rs:550` の `publish` / `publish_value`。`subscribe` は
`current_entity(vm)`（`src/lib.rs:1346`、走っているタスクの `@rubevy_entity` を読む）が `nil` なら
`raise_arg` する。計画書が「`Task.new` のタスクからの `subscribe` は断られるので、購読はメインのタスクで取って
ブロックに渡す形に」と書いているのはこれのこと。ここまでは計画書の通りに書けた。

ゲーム側は `sabibots/src/main.rs` の `move_bullets`（命中の判定）、`answer_requests`（`Rubevy.ask` の答え）、
`draw_scoreboard`（egui のスコアボード）、`stop_when_over`（`--headless` の最後の行）、`selftest`（エディタの
ボタンを押して確かめるもの。`headless.is_none()` で窓のあるときだけ動く）。

## 何を publish するか

計画書は `Answer::List([owner_bits, damage])`、指示は「スクリプトが直に使える形（撃った側の名前の方が親切）」。
`Answer::List` は `Vec<f64>` なので文字列が入らない。`publish_value(entity, name, |vm| …)` で VM の中で組んだ
（`main.rs:1669`）。中身は `[撃った側の名前, ダメージ]`、名前はスコアボードと同じ `"2 red/hunter"`。
エンティティの id ではなく名前にしたのは、スクリプトが何も聞かずにログにも比較にも使えるからで、id が要る用途には
radar が既に id を配っている。`&mut Robot` を握ったまま撃った側の名前は読めないので、ループの前に
`Vec<(Entity, String)>` を作っておく（`main.rs:1630`）。

## 壊れたところ 1: `Task.new` のタスクは何も聞けない

最初の版は計画書の通り `bot.instance_exec(*args, &block)` で、ヘッドレスで回したらこうなった。

```
Scout: reflex hit ["4 blue/scout", 7.6]
Scout: reflex hit: RuntimeError: blocking pop cannot be called from within a C function boundary
```

publish も subscribe もタスクも動いていて、reflex のブロックの中の `act` だけが死ぬ。
`act` は `Rubevy.ask("act", …).pop` で、`pop` は `ext_task.rs:887` で
`vm.fiber_check_native(vm.cur)`（`vm.rs:2266`、フレームのどれかが `Cci::Skip` か）を見て断る。
`instance_exec` は `ext_object.rs:21` → `call_block_with_self_kw` → `call_proc_with` で、これは
**VM の入れ子の実行ループ**（ネイティブが Ruby を呼んで戻りを待つ形）。タスクはその境界をまたいで park できない。
`send` も `Method#call` も `Vm::funcall` 経由で同じ。

一方 `Proc#call` は違った。`src/builtins/proc_.rs:38` で `call` / `()` / `[]` / `yield` / `===` は
**本体が `OP_CALL` の Ruby メソッド**として定義されていて、`vm.rs:3432` の `Op::Call` は
`vm_call_proc` で今のフレームを置き換える。入れ子のループにならない。ただし `vm_call_proc` は self を
proc の env から取る（`vm.rs:4268`）ので、`class_eval` の中で作ったブロックの self はクラスのままで、
`bot` にならない。

そこで、**ブロックをクラスの普通のメソッドにする**ことにした。`reflex` が
`define_method("__reflex_#{slot}", &block)` で登録し（`prelude.rb:120`）、`run_reflex(slot, args)` が
`case` でソース上に書かれた名前で呼ぶ（`prelude.rb:132`）。普通の `OP_SEND` なので入れ子にならず、
中で `act` も `sleep` もできる。名前をソースに書き出す必要があるぶん数は固定で、`REFLEX_SLOTS = 4` にした。
ここは「動的な呼び出しはだいたい入れ子のループになる」という VM の性質がそのまま設計に出た場所で、
`docs/host-api.md` が `e[:Transform]` について書いている OP_GETIDX の話と同じ形をしている。

## 壊れたところ 2: reflex のタスクにはエンティティが無い

1 を直しても `act` は `nil` を返した。`Rubevy.ask` も `current_entity(vm)` を読んでいて
（`rubevy/src/lib.rs:1284`）、`Task.new` のタスクには `@rubevy_entity` が無いから、
リクエストの `entity` が `None` になり、`answer_requests` の
`let Some(me) = request.entity else { Answer::Nil }` に落ちる。そこから `fired > 0` で `NoMethodError`。

計画書は subscribe だけを問題にしていたが、**同じ穴が ask 側にもある**。
`host-api.md` に「A script can see it — it is an ordinary `@ivar`」と書いてあるので、
メインのタスクの `@rubevy_entity` を新しいタスクにそのまま写した（`prelude.rb:248` と `prelude.rb:268`）。
`Task.new` は ready キューに入れるだけで、こちらが yield するまで走らないので、
`Task.new` の直後に写しても間に合う。
本当は rubevy が `Task.new` のときに引き継ぐか、`Rubevy.adopt(task)` のようなものを出すべきで、報告に書いた。

## 壊れたところ 3: 後勝ちだと reflex が必ず負ける

計画書は「メインと reflex が同時に `act` を呼ぶので後勝ちと決める」。決めた上で動かすと、
被弾しても向きがほとんど変わらない。理由は 2 つある。

* **優先度が高い（数が小さい）タスクは先に走る**ので、reflex の `act` のリクエストはメインのより
  **先に**キューに積まれ、同じフレームなら**あとから来たメインが勝つ**。速く動けるほど綱引きに負ける。
* さらに悪いことに、被弾した瞬間メインはたいてい質問を投げた途中にいる（`@swerve` を見てから radar を聞いた）。
  その答えが数フレーム後に返ってきてから出す `act` が、reflex の舵を打ち消す。

最初は scout の reflex を「`act turn: ±1.0` を 1 回出して `sleep 0.3`」にしていた。
ヘッドレスの自己テストで、26 回の被弾のうち向きが 0.2 rad 以上変わったのは 24 回。落ちた 2 回は
0.09 rad と 0.00 rad だった。0.00 の方はその一発で倒れた機体（倒れると `move_robots` が早期 return するので
向きは固定）、0.09 の方は上の「飛んでいる質問」に打ち消された回だった。

直した順に書くと、

1. 倒した一発は数えない、走っている最中の reflex に重なった被弾も数えない（`main.rs:1673`）。
   前者は「残骸は曲がれない」、後者は「1 つのイベントの reflex は 1 本のタスクを共有するので、
   2 発目は 1 発目が終わってから」という仕様どおりの挙動。これで 18 回中 16〜17 回まで上がったが、まだ落ちる。
2. 判定を「0.3 秒後の向き」から「0.3 秒の間の向きの最大のずれ」に変えた（`main.rs:879` の `peak`）。
   2 回連続で逆向きに曲がると終点が元に戻るので、「曲がったか」を見るならこちらが正しい。
3. **reflex が舵を握り続ける**ようにした。`act` を 1 回でなく 0.05 秒ごとに 6 回出す（`scout.rb`）。
   飛んでいた質問の `act` に一度だけ打ち消されても 0.05 秒で取り返せて、メインは次の周から
   `@swerve` を見て手を引く。

3 まで入れて、25 秒のヘッドレスを 4 回: 16/16、19/19、15/15、16/16 で全部 ok。
「後勝ち」は仕様として残し、**2 つのタスクが 1 台の戦車を動かすなら、どちらが舵を持つかは
ロボットの側で決める**ということを `docs/sabiruby-battle.md` に書いた。`@swerve` がその取り決めで、
同じオブジェクトのインスタンス変数で足りるのは、2 本のタスクが同じ `bot` を見ているから。

## 捨てた案

* **reflex の優先度をメインより低くする。** そうすればリクエストがあとに積まれて後勝ちで勝てる、という
  ひっくり返った解。同じフレーム内で走るのは変わらないので遅くもならない。計画書が「優先度はメインより高く」と
  明示しているので採らなかったが、「後勝ち」と「優先度が高いほど先に積む」を組み合わせると
  優先度の意味が逆転する、というのは書き残しておく価値がある。
* **HUD の印をゲーム側だけで作る。** 命中の回数を数えれば Ruby に手を入れずに済むが、それは「被弾の回数」で
  あって「reflex が走った回数」ではない（hunter には reflex が無い）。prelude から
  `Rubevy.ask("reflex", :begin)` / `:end` を投げる形にした。ただし **`.pop` しない**。
  `Rubevy.ask` は待つためのキューを返すだけで、pop しなければ park しない（`rubevy/src/lib.rs:1256`）。
  「誰も待たない質問は命令」で、これなら印のために reflex が 1 フレーム損をしない。
  答えは `answer_requests` が普通に返すのでキューは毎回 `gc_unregister` される。
* **reflex の中で `Task#suspend` してメインを止める。** 取り決めが要らなくなるが、被弾のたびに脳を止めるのは
  やりすぎで、`suspend` / `resume` は寝ているタスクに対して寝ていた時間を失う。

## `ensure` は外から終わらされると走らない

計画書は「`run_robot` が終わるときに `terminate` する（`ensure`）」。書いた上で、本当に走るのか確かめた。
`ensure` に `Rubevy.log "PROBE: …"` を仕込んで 60 秒回し、3 体が倒れたが PROBE は一行も出ない。
`sabiruby/src/builtins/ext_task.rs:398` の `stop_task` はコンテキストの `ci` と `stack` を clear して
`Terminated` にするだけで、巻き戻さない。ロボットが倒れたときの `gray_out_downed` は `ScriptTask` を外し、
rubevy はそこでタスクを terminate するので、`ensure` は通らない。

残るのか確かめるために、マッチの側に `Task.list` を 3 秒ごとに出すだけのタスクを足して回した。

```
PROBE tasks=9 probe:RUNNING,match:READY,1 red/scout:READY,3 blue/scout:READY,
              Scout-hit:WAITING,Scout-hit:WAITING,Scout-hit:WAITING,4 blue/scout:WAITING,2 red/hunter:WAITING
（blue の scout が倒れたあと）
PROBE tasks=9 3 blue/scout:DORMANT,probe:RUNNING,Scout-hit:READY,1 red/scout:READY,2 red/hunter:READY,
              Scout-hit:WAITING,Scout-hit:WAITING,match:WAITING,4 blue/scout:WAITING
```

倒れた機体の本体のタスクは `DORMANT` になってリストに残り（これは元からそう）、その `Scout-hit` は
`WAITING` のまま残る。誰も publish しないキューで永久に待つ。`ensure` は「脳が自分で終わったとき」しか
効かないので、これは直っていない。直す場所はここではなく rubevy で、`unsubscribe` がキューを close すれば
`pop` が `Task::Error` を上げてタスクが自分で終わる。`docs/sabiruby-battle.md` の
「まだやっていないこと」に入れて、報告にも書いた。

## 確認

* `cargo check -p sabibots` 警告なし。`cargo build --release -p sabibots` 通る。
* `--headless` に reflex が 1 命中につき 1 行出る（`Scout: reflex hit ["2 red/hunter", 14.8]`）。
* `SABIBOTS_SELFTEST=1 … --headless 25` を 4 回: 「被弾から 0.3 秒以内に reflex が走った」「向きが変わった」
  がどちらも 16/16、19/19、15/15、16/16。
* 窓（`docker/run.sh`、lavapipe）でエディタの自己テストも通る。ただし
  `every robot starts with full health` は落ちることがある。**これは元からで**、
  手を入れる前の main を `git stash` して同じ image で 3 回回したら 2 回落ちた（再開の 2 秒後に見ているので、
  もう撃ち合いが始まっている）。今回の範囲外なので触っていない。
* `--shot`（docker/lavapipe）でスコアボードに `> 1 scout !2` / `4 scout x2` が出ているのを目で確認した。
* `web/build.sh`: wasm-opt が無いので「縮まない」と言われるだけで通る（`docs/web.md` の通り）。
  Ruby は AOT ではコンパイルされず `build.rs` が `.rb` を丸ごと埋め込むので、prelude の変更は
  ブラウザ側では再コンパイルだけで載る。

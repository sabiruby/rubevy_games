## 2. セーブの版番号 — 版だけを先に読む

`GardenSave` の先頭に `version: u32` を足した。実装で考えたのは 2 点だけで、どちらも「どう失敗するか」の話。

**版だけを先に、単独で読む。** `GardenSave` 全体を `serde_json::from_str` に通して失敗を見る、では駄目だった。
別の版のファイルは**たまたま変わったフィールド**で落ちるので、出てくる文はそのフィールドについての serde の文
（``missing field `sight` at line 214``）で、何が起きたのかを一言も言っていない。
なので `version: Option<u32>` だけを持つ 1 フィールドの struct を**同じテキストに先に通す**。
serde_json は知らないフィールドを黙って捨てるので、これは「どんな JSON オブジェクトでも通る」パーサになる。
`1` と書いてあるファイルだけが残りを読まれる。

```
$ ./target/release/garden --headless 3 --load v2.json
ERROR garden: v2.json: saved with version 2, this garden reads 1
...
10 creatures, 42 plants, day at phase 0.13      ← Loading が入らないので新しい世界が建つ
$ ./target/release/garden --headless 3 --load v0.json     # version を消したファイル
ERROR garden: v0.json: saved with no version, this garden reads 1
```

**版は struct から導かず定数にした。** serde が default できるフィールドを 1 つ足す・1 つ消す、は
どちらも「読めてしまうが意味が違う」ファイルを残す。版はファイルの**意味**についての約束で、
約束は人にしか作れない。`SAVE_VERSION` を上げるのは「古い版で書いた庭が、読めないのではなく**違う庭として**
戻ってくる」ときだけ、とコメントに書いた。

**10 個目の判定は `--load` そのものにした。** 計画書は「version 99 の JSON を書いて `--load` する」。
`read_save` を横から呼ぶ関数を書くと、テストしているのは `--load` ではなくその関数になる。なので
`main` の `--load` の腕に置いた: selftest で、かつ `--load` が指定されていないときだけ、
`GardenSave::default()` に `version: 99` だけ入れたファイルを書いて、**その腕にそのまま渡す**。
ファイルを「版以外は完全に正しい保存」にしたのも意図で、`read_save` が版を見なくなったら
このファイルは**読めてしまい**、判定は「たまたま通る」ではなく落ちる。

```
selftest: ok   a save with the wrong version is refused (/tmp/garden-from-another-version.json: saved with version 99, this garden reads 1)
```

`GARDEN_SELFTEST=1 --headless 90` は **10/10**。往復（`--headless 0 --load a --save b`）も
2 つのファイルが同一のまま（12162 バイト）。

**HUD に出す場所が無かった**ので `SaveNote` を足した。窓では F5 が書いた 1 行は stdout に行くだけで
プレイヤーは見ない。版を断る文はその人の庭についての文なので、届かないと意味が無い。
成功も同じ経路に載せた（異常時にしか出ない行は、出たときに誰も読まない）。

## 3. 1 つの Pages に 2 本 — 複製を選んだところ

`web/build.sh <game>` が `web/dist/<game>/` に書き、`web/build.sh all`（引数なしの既定）が
2 本と入口の `index.html` を書く。`web/index.html` は入口になり、Battle のページは
`web/sabibots.html`（rename）、箱庭は `web/garden.html`。

**各ゲームのディレクトリを自己完結にした**（コンパイラ module 2.4 MB を 2 回置く）。
共有すれば 2.4 MB 減るが、`web/build.sh garden` が作るものが「親が無いと意味が無いディレクトリ」になる。
このスクリプトが一番よく使われるのは 1 本だけ焼いて `serve.sh` で開くときなので、そちらを取った。
訪問者が読むのは片方だけなので、転送量は変わらない。

**アセットは何も言わなくてよかった。** bevy の wasm リーダは `assets/…` を
**相対 URL** で `fetch` する（`bevy_asset-0.19.1/src/io/wasm.rs`、`window.fetch_with_str(path)`）ので、
ページが `…/rubevy_games/garden/` に居れば `…/rubevy_games/garden/assets/…` を取りに行く。
`cp -r garden/assets` が `models/Textures/colormap.png` ごと持っていき、`.glb` は自分からの相対で
テクスチャを名指すので、サブディレクトリについても言うことは無い。実測で 404 は 1 本も出ていない。

`?selftest` を足した（`platform::selftest_asked`）。ページには `GARDEN_SELFTEST` を置く環境が無く、
**「誰かが食べた」と言う行は判定が書いている行**なので、これが無いとブラウザは「見る」ことはできても
「確かめる」ことができない。PC は環境変数、ページはクエリ文字列、読むのは `main` の同じ 1 行。

## 4. ブラウザで動かす — 最初の 2 回は道具の問題だった

**`page.goto(..., { waitUntil: 'load' })` は返ってこない。** ページのモジュールスクリプトは
`await game.default()` で終わり、ゲームが動いている間それは返らない。`load` イベントは
モジュールの実行を待つので、**正しく動いているページほど `load` が来ない**。60 秒の timeout まで待って
落ちる。`'commit'` が正しい。これで 8 分溶かした。

動かしてしまえば中身はすぐ出た。150 秒の `garden/?selftest` で:

```
ERROR garden.from-another-version.json: saved with version 99, this garden reads 1
INFO  selftest: a hungry beetle at (17.0, 12.0) with one plant 5.0 away
INFO  Beetle walks, idles and eats from its model
INFO  selftest: first meal at 1.63 s
INFO  selftest: the hungry beetle reached its plant at 2.45 s
INFO  Beetle 398v0 starved at 2.0 s (age 2.0 s)
INFO  a Beetle was born at 4.2 s (770v0) — speed 2.18, sight 8.6, appetite 1.07
INFO  night at 25.3 s
```

page error 0、失敗したリクエスト 0、404 0。**版の判定がいちばん効くべき場所で効いている**のが見えたのは
気分が良かった: `?selftest` が version 99 の保存を `localStorage` に書き、ページがそれを断り、新しい庭を建てる。

セーブの往復（判定を付けないページで）:

```
F5    → saved 11 creatures, 44 plants at 43.6 s to garden.save.json (11918 bytes)
        localStorage["garden:garden.save.json"] = 11918 文字、version 1、11 creatures、44 plants
reload
F9    → loaded 11 creatures, 44 plants, 7 trees, 9 rocks at 43.6 s (69 entities made way)
        ドキュメントのロード回数は 2（= F5 も F9 もページを再読み込みしていない）
```

**フレームレートは測り直した。** 最初「SwiftShader だから 5 fps」と書きかけたが、40 秒で 221 回という
その測定は 35 MB の wasm を落として compile している時間が大半だった。150 秒では 7531 回、
つまり**動き出せば 50 fps 前後**出ている。sabibots の記録にある「1 フレーム以内に押して離した鍵は取りこぼす」も
この箱庭では再現しない（`keyboard.press` を 3 回、3 回とも保存された）。**前の記録をそのまま引き写さなくてよかった。**

## 5. サイズ — `wasm-opt` はファイルを小さくして、ダウンロードを大きくする

| | bytes | gzip -9 | `wasm-opt -Os` | その gzip |
|---|---|---|---|---|
| `sabibots/pkg/game_bg.wasm` | 38,772,420 | 9,877,837 | 34,794,885 | 10,593,848 |
| `garden/pkg/game_bg.wasm` | 39,250,319 | 10,011,447 | 35,227,757 | 10,719,930 |
| `compiler/sabiruby.wasm`（各ゲームに 1 つ） | 2,435,191 | 835,234 | — | — |
| `garden/assets/`（10 ファイル） | 322,924 | 64,744 | | |

`wasm-opt -Os` は生のモジュールを 10% 削り、**gzip を 7% 増やす**（sabibots 9.88 → 10.59 MB、
箱庭 10.01 → 10.72 MB）。Pages が実際に送るのは gzip の方なので、**`wasm-opt` の言い分は「ダウンロードが速くなる」ではない**。
最適化の出力は小さいが繰り返しが減り、gzip は繰り返しで食っている。CI は今まで通り回すことにした
（ブラウザが decode して持つのは生の大きさなので）。やめるかどうかは著者の判断。

箱庭が Battle より 1.2% 大きいのが 3D 一式（`bevy_pbr` / `bevy_gltf` / `bevy_animation`）。
計画書の見込み「Battle の 30 MB から 35〜40 MB」は当たっているが、**Battle 自身が 26.7 MB から
34.8 MB に育っている**（`docs/web.md` に前回の数字が残っていた）。`web` プロファイルは同じなので、
育てたのは bevy 0.19 / bevy_egui 0.42 / rubevy-arena のどれか。**分解していない。**

## 6. 見つけた 3 つ — 1 つ直し、1 つ原因不明、1 つは VM 側

### (a) エディタを使ったあと、鍵がゲームに届かなくなる（原因未特定、直していない）

`garden/?selftest` は G4 の窓の判定（エディタを機械が叩く）も回る。**その判定が終わったあと、
F5 も F9 も P も二度と効かない**。判定を付けないページでは 25/45/65/85 秒のどこで押しても効く。

最初は自分の仕業を疑った。G5 で `save_load_keys` に
「エディタに caret があるときは F5/F9 を無視する」（`EguiWantsInput::wants_keyboard_input()`）という
guard を足していたからで、**外して焼き直して測ったが直らなかった**。ついでに分かったのは、
その guard はそもそも間違いだったということ: `P` は文字なのでエディタに取られるべきだが、
F5 と F9 は egui が欲しがらない鍵で、guard を付けると「一度でも編集したらセーブ鍵が死ぬ」になる。
guard は外したまま（コメントに理由を書いた）。

DOM 側は無実だった: フォーカスは `CANVAS#garden` のまま、`keydown` は `#garden` に届いている
（`F5@garden`）。`Escape` を送っても、庭をクリックしても戻らない。残る疑いは
**bevy_egui が「egui がキーボードを欲しがっている」間 Bevy の入力を吸っている**（egui の TextEdit が
フォーカスを持ったまま離さない）ことだが、**確かめていない**。lavapipe の PC では G4 の判定が
21/21 通っていて、そのあと鍵を押す試験はしていないので、ブラウザ固有かどうかも分からない。

これが**ボタンを付けておいた理由そのもの**になった。鍵が死んでもボタンは生きている。

### (b) HUD のボタンが VM パネルの下に隠れていた（直した）

最初はボタンを HUD の一番下、鍵の説明の横に置いた。読み物としてはそこが正しい。
**1280×800 のブラウザで生き物が 14 匹居ると、その行はパネルの外に出て VM パネルの下に潜る**
（スクリーンショットで確認。クリックを 6 か所試して 1 つも届かなかった）。
**一覧より上**に移した。上にあるものは一覧に押し出されない。
(a) と合わせると、「鍵が効かない状態でボタンも隠れている」が実際に起きうる配置だった。

### (c) 全部を一度に入れ替えると、新しいタスクが `Created` のまま走らない（VM 側、直していない）

G4 の記録にある「一度に 10 匹入れ替えると VM のスケジューラが止まる」と同じ形が、ブラウザで 2 か所に出た。

* 窓の判定 22 本のうち **1 本だけ落ちる**: `every restarted beetle's new task has run`。
  Apply が甲虫を 0.4 秒に 1 匹ずつ入れ替えたあと 0.6 秒待って見ると、まだ 1 匹も命令を走らせていない。
  そのあとの判定（VM 全体は生きている、Revert が戻す）は通り、FAIL のあとにも甲虫の
  `[script] Beetle: {...}` が 17 行出ているので、**止まりっぱなしではない**。
* **F9 のロードで記憶が戻らない**: `11 creatures never started; the garden is running anyway`。
  `load_world` は全部を despawn して 11 匹を**同じフレームで**作り直すので、Apply の待ち行列のような
  散らし方をしていない。生き物は数秒後に動き出すが `@memory` は空（`{"meals":1}` から数え直している）。
  PC の起動時 `--load`（11 匹）では記憶は全部戻る — 往復のファイルがバイト単位で同一 — ので、
  **「動いている庭に読み込む」方だけが踏んでいる**。

`docs/garden.md` と `docs/web.md` に書いた。直すのは VM のスケジューラ側の仕事で、
別の担当が `../sabiruby-wt-sched` で見ている場所。ゲーム側で散らす回避を書くこともできるが、
それは G4 が `Restarting` で 1 回やった回避をもう 1 か所に増やすことなので、手を付けていない。

## 7. ブラウザのコンパイラはファイル名を渡せない

HUD の「待っている行」の列が、ブラウザでは `beetle.rb:102` ではなく **`playground.rb:102`** と出る。
PC の `platform::compile` は `sabiruby_compiler::Options { filename }` に生き物のファイル名を渡すが、
ページの橋（`window.gardenCompile(source)`）はソースしか取らないので、debug info の名前は
playground が付けた `playground.rb` になる。**行番号は正しく、行番号を使うものは全部正しい**
（箱庭は prelude の長さを引いて「自分のファイルの行」を出しているので、名前を見ていない）。
名前を渡せるようにするのは sabiruby-playground 側の変更なので、ここでは直さず記録した。

## 1. 設計 — 何をどこに置いたか（コミット 2）

F0 が残した形（**格子はゲームの Resource、`TilemapChunk` はその絵**）をそのまま広げた。
`factory/src/` は 1 ファイル 660 行から 6 つに分かれている:

| ファイル | 中身 |
|---|---|
| `grid.rs` | `Dir`（4 方向と左右の回り）、`What`（ベルト・採掘機・箱）、`Building`、`Grid`、`Ore`、`Flow`（どの向きから来たか）、アイテムの世界座標 |
| `belts.rs` | **規則**: `Rules`（遊びの数）、`Lanes`（タイルごとの列）、`step()` の 4 パス、単体テスト 7 本 |
| `items.rs` | アイテムの持ち方 2 通りと、どちらを選ぶかの計測 |
| `build.rs` | キーとクリック（`Hand`） |
| `draw.rs` | 2 枚の chunk、スプライト、ズームの丸め |
| `main.rs` | 配線、引数と設定、判定、stress の計測 |

**ベルトの模型は「タイルごとの列」**。ベルト 1 タイルは長さ 1 で、載っているアイテムは
`0..=1` の数（そのタイルをどこまで来たか）。列は**前から順**で、隣り合う 2 つは必ず
`spacing`（= 1 ÷ `items_per_tile`）以上離れている。この不変条件が模型のすべてで、
運ぶ = 全部に一歩足す、詰まる = 前が動けない、合流 = 2 本が 1 本へ渡して互いの隙間を見る、になる。

`step()` の 4 パスは順番が模型そのものである:

1. **尻尾を控える** — 各ベルトが隣にどれだけ押し込めるかは「フレームの最初の状態」から読む。
   こうすると**タイルを walk する順番に答えが依らない**（3 本目のタイルへ 2 本が合流するとき、
   2 本とも同じ絵を見る）。
2. **運ぶ** — 先頭は `1.0 + 次のタイルの尻尾 − spacing`（次がベルトでなければ `1.0`）まで、
   後ろは前の 1 つから `spacing` 引いた所まで。
3. **渡す** — 先頭が `1.0` を越えていたら次のタイルへ。**渡す瞬間にもう一度隙間を見る**ので、
   合流したとき先に回ってきた側（index の小さい方）が隙間を取り、もう片方はその場で待つ。
   箱が相手なら箱の数が 1 増えてアイテムは消える。満杯の箱は断り、ベルトは詰まる。
4. **掘る** — 採掘機は `mine_seconds` ごとに 1 個。置き場所が無ければ**掘り終わったまま待つ**
   （`work` を `mine_seconds` で止める）ので、地面の鉱石は減らない。塞がっていた採掘機は
   受け口ができた次のフレームに出す。

**向かい合った 2 本のベルトは詰まる**（キャッチボールしない）。`room_ahead` が
「次のベルトの向きが自分の逆でないこと」を見る。

**曲がりは絵と道の両方**。`Flow::refresh` が「このタイルへは**どの向きから**入ってくるか」を
近所から求め（後ろから来ていれば直線、横から 1 本だけなら曲がり、2 本以上の合流は直線）、
絵は `belt_picture` が 1 枚の曲がりを回して 8 通りを作り、アイテムの道は
`item_at` が「入り口の辺 → タイルの中心 → 出口の辺」の 2 本の直線として描く。
**著者が (ii) を選んだ意味がここに出ている**: 直線 1 枚 + 曲がり 1 枚 + `TileOrientation` で、
4 向き + 8 通りの曲がりが全部出る。単体テスト
`eight_turns_and_four_directions_out_of_two_pictures` が「8 通りの向きが全部違うこと」を見ている
（同じ向きを 2 回使っていたら曲がりのどれかが逆を向く）。

**1 タイルに何個載るか**は `items_per_tile`（既定 2）で、**詰まったタイルには 3 個**並ぶ。
off-by-one ではない: 位置 `0.0` はそのタイルの入口の辺で、それは 1 つ前のタイルの `1.0` と
**世界の同じ点**である。`items_per_tile` は「タイルの長さに入る隙間の数」で、隙間 N 個の列には
N+1 個が並ぶ。テストのコメントにも書いた。

## 3. アイテムの表現 — 両方作って測った（計画 §3.1・§3.7）

計画が紙の上で決めないと言った 1 件。**両方を本当に作って**、`--holding lanes` /
`--holding entities` で切り替えられるようにし、`--stress N` で数千個の工場を建てて測った。

**規則は 1 つしか書いていない。** どちらも同じ `belts::step` を同じ `VecDeque<f32>` の列に対して
走らせる。違うのは**その列と数がフレームの間どこに住んでいるか**である:

| | lanes | entities |
|---|---|---|
| 位置 | 列の中の `f32` | アイテムの component |
| 並び | 列が持っている | **どこにも無い**。毎フレーム、query をタイルごとに bucket して sort し直す |
| 1 個の値段 | 4 バイト | エンティティ 1 つ、archetype の行、`Transform`、`Sprite` |
| 描画 | プールのスプライトに書く | 各アイテムが自分の `Transform` に書く |

**entities の側が毎フレーム並べ直さなければならないのが、この計測でいちばん言いたいこと**である。
規則は「1 つ前のアイテム」を要求し、ECS の query にはそんなものは無い。だから
「アイテムをエンティティにする」を素直に書くと、列の構造を**毎フレーム作り直す**ことになる。

### 3.1 測り方

機械は `vmstat 1 3` で idle 99〜100%、隣で動く cargo・docker・ブラウザは無し。
**交互に 2 巡**（lanes → entities → lanes → entities）、1 走行につき報告 3 回のうち
**最初の 1 回は捨てる**（窓が開く・asset が届くフレームが入っている）。
`--stress N` は**自分で地図の大きさを決める**（ループが 1 タイルに `items_per_tile` 載せるので
必要な辺は √(N ÷ items_per_tile)）。ページには `map_tiles` を渡す口が無く、**ブラウザで取れない
計測はブラウザの計測ではない**から、ここは引数ではなく走行が決める形にした。
時計は `bevy::platform::time::Instant`（wasm に無い `std::time::Instant` を道に置かない）。

### 3.2 PC・窓なし（`cargo run --release -p factory -- --headless 20 --stress N --holding X`）

1 フレームの中で「工場の 1 歩」だけを測った数（µs、p50。2 巡 × 各 2 報告の範囲）:

| アイテム | lanes | entities | 比 |
|---|---|---|---|
| 1,000 | 29〜39 | 59〜85 | 約 2.2 倍 |
| 4,000 | 63〜98 | 134〜274 | 約 2.9 倍 |
| 16,000 | 263〜337 | 657〜911 | 約 2.8 倍 |

どちらも 60 fps のフレーム（16.7 ms）には遠い。**16,000 個でも lanes は 0.3 ms、entities は 0.8 ms**。
ヘッドレスは `ScheduleRunnerPlugin::run_loop(1/60)` で頭打ちなので、フレーム時間は
どの走行も 16.7 ms で、意味があるのは中の µs だけである。

### 3.3 PC・窓あり（`docker/run.sh factory release --stress 4000 --holding X`、lavapipe）

| | frame ms p50 | step µs p50 |
|---|---|---|
| lanes | 20.5〜20.9 | 48〜51 |
| entities | 20.7〜21.0 | 123〜126 |

**フレームは同じ**（どちらも約 48 fps）で、中の工場だけが 2.5 倍違う。つまり PC の窓では
**描画（lavapipe のソフトウェア描画で 4,000 枚のスプライト）が支配的**で、持ち方の差はその中に
埋もれる。2 巡とも同じ形だった。

### 3.4 ブラウザ（Playwright の SwiftShader、1280×720、`?stress=N&holding=0|1`）

**ここでは表現の差は測れない、と正直に書く。** 理由は 2 つあって、どちらも機械の側の話である:

- **フレームがアイテムの数にほとんど依らない。** 900 本のベルトのループで、アイテム **2 個**でも
  186〜189 ms、**1,800 個**でも 205〜208 ms、48 タイルの地図に **4,000 個**でも 214〜215 ms。
  つまり 5 fps は工場ではなく**全画面をソフトウェアで塗る値段**である。
- **時計の分解能が足りない。** ブラウザの `performance.now()` は 100 µs に丸められるので、
  step の µs は 0 / 100 / 200 / 300 しか出てこない（lanes は 0〜100、entities は 100〜300 と
  読めるが、これは「2〜3 倍」を支持する以上の精度を持たない）。

pageerror 0・requestfailed 0 は 8 走行とも。**SwiftShader は実機の GPU ではない**ので、
この 5 fps から「ブラウザでは 4,000 個は無理」とは言えないし、言っていない。

### 3.5 選んだのは lanes（コミット 3 で entities を消した）

速いからだけではない。**規則が順番を要求するのに ECS は順番を持たない**ので、
entities の側は「毎フレーム bucket して sort する」という、模型には要らない仕事を
構造的に背負う。2.2〜2.9 倍はその値段の実測である。
描画の側は互角（どちらも N 枚のスプライトに `Transform` を書く）で、差は全部 ECS の側にある。

捨てた側のコードは履歴にある（`git show e3af41a:factory/src/items.rs`。消したのは `778e99e`）。
残したのは lanes の道と、計測の仕掛け（`--stress`）そのもの。
**`--holding` は消えた**ので、ページの `?holding=` も無くなった。

## 4. 決めた小さなこと（理由をここに残す）

- **キー割り当て**は `1` ベルト / `2` 採掘機 / `3` 箱 / `0` 撤去 / `R` 回す。撤去を右クリックに
  しなかったのは、右ボタンは共有 crate のカメラのドラッグに割り当たっているから
  （`CameraKeys::drag_buttons`）。`WorldClick` が出るのは左だけである。
- **採掘機は鉱石の上にしか置けない**（置こうとすると log に断りが出る）。そうしないと畑を
  探す意味が無い。それ以外は上書きで建つ。
- **ベルトを撤去すると載っていたものは消える**。列はタイルのもので、ベルトの無いタイルが
  物を運んでいる状態を作らないため。判定 1 行がこれを見ている。
- **`Grid` の「変わった」は `bool` ではなく数**。絵と `Flow` の 2 つが追いかけるので、
  片方が倒すフラグはもう片方が取りこぼす。それぞれが「最後に追いついた番号」を持つ。
- **ヘッドレスにキーを足さなかった**。`ButtonInput<KeyCode>` は `InputPlugin` のもので
  `MinimalPlugins` には無い（最初 `Res<ButtonInput>` を要求して panic した）。判定は
  `Hand` を直接書くので、窓のある走行だけがキーを読む。
- **`--shot` と判定を同時に使えるようにした**（F0 の気づいた点 4）。判定が済んだら終わる
  仕掛け（`CHECKS_EXIT_WHEN_DONE`）に「絵を頼まれている走行は終わらない」を足しただけで、
  共有 crate には触っていない。これで**判定が建てた工場の写真**が撮れる。
- **stress の地図は走行が自分で決める**。`map_tiles` を渡す口がページに無いので、
  `--stress N` は √(N ÷ `items_per_tile`) から必要な辺を出す。ブラウザでも数千個が測れる。

### 5.2 本体のレビューから来た 4 点（belts.rs）

**(1) 「詰まったタイルには N+1 個」は f32 で成り立つか。** 成り立たない値がある。
`items_per_tile` を 1・2・3・4・5・7・8 で走らせて詰まったタイルの個数を数える単体テスト
（`a_jam_keeps_the_gap_even_when_the_gap_is_not_an_exact_number`）を足したら:

```
items_per_tile 1: a jammed tile holds 2
items_per_tile 2: a jammed tile holds 3
items_per_tile 3: a jammed tile holds 3   ← N+1 ではない
items_per_tile 4: a jammed tile holds 5
items_per_tile 5: a jammed tile holds 6
items_per_tile 7: a jammed tile holds 8
items_per_tile 8: a jammed tile holds 9
```

レビューの読みは **3 について当たり、5 については外れた**。「正確に表せる値だけ通る」という
形ではない。f32 の 1/3 は切り上げなので隙間 3 つがタイル 1 枚より**長く**なり、2 パス目の
`room = 1.0 + tail - spacing` が 0.99999988 になって先頭が 1.0 に届かず、4 個目は
`while front >= 1.0` に入る前に断られる。1/5 も切り上げだが、`hold` の**引き算の連鎖**が
丸め戻って最後の位置が +2/2^26 になり、6 個目が入る。つまり結果は
「spacing が正確か」ではなく「連鎖の丸めがどちらに転んだか」で決まる。

**直していない。** 不変条件（隣と spacing 以上、1 個も失わない、先頭はタイルの端）は
どの値でも保たれていて、テストがそれを全部見ている。違うのは**詰まったベルトの緩衝が
1 個ぶん少ないことがある**という一点で、これは壊れた工場ではなく 1/3 という数である。
許容誤差を足す道も考えたが、足す数（何 ulp か）の出どころが言えないので選ばなかった
（CLAUDE.md）。位置を整数の刻みで持つ形は F1 の範囲を超えるので、報告に選択肢として出すに
とどめる。テストの主張は**個数ではなく不変条件**にし、測った値はコメントに書いた。
`items_pile_up_behind_a_belt_that_runs_into_nothing` の「N+1 個」にも但し書きを足した。

**(2) `.max(0.001)` を消した。** `Rules::spacing`、`Rules::belt_frame_seconds`、
`draw::snapped` の 3 か所にあった、「0 で割らないため」だけの数である。読み込み時に断る形へ移した:
`main.rs` の `positive`（0 以下なら log に出して既定値）と `counted`（個数なので 1 未満に丸まる
ものも断る）。`chest_capacity` / `ore_per_tile` の `.max(1.0)` と `camera_half_height` も同じ道へ。
`Rules` の rustdoc に「全部 0 より大きい。それを保証するのは埋める側で、F2 の data stage も
同じことをする」と書いた。**算術の中に下限を置かないのは、下限が「どこから来たか言えない数」に
なるから**である。`map_tiles` の `.max(8.0)` だけは残っている（5.1 の 3 番目）。

**(3) 採掘機が箱へ直接入れたとき `Move` が記録されていなかった。** 今の判定と食い違ってはいない
（判定は `dug == 箱の中 + ベルトの上` を数えていて、`Moves` を見ていない）が、`made()` は
「採掘機が出した数」と名乗っていて**採掘機が箱の隣に立っているぶんだけ少なく数える**。
F5 の HUD が読む数なので直した: 箱の枝でも `Move::Made { at: n }` を積み、`Made.at` は
「入れた先のタイル（ベルトの列か、箱そのもの）」だと doc に書いた。`Taken` は積まない
（ベルトに乗ったことがないので、`carried + taken` が「ベルトがしたこと」の意味を保つ）。
`a_miner_with_nowhere_to_put_it_takes_nothing_out_of_the_ground` に
`made() == 1` / `taken() == 0` の 2 行を足した。

**(4) `.min(2.0)`** は「次のタイルの**向こう端**まで」という上限である（空の隣の尻尾は
`INFINITY` なので、これが無いと先頭が無限に進む）。1 行のコメントを足した。
渡すのは 1 タイルずつなので、**1 フレームで 1 タイル以上進む速さ**にすると
「2 つ先のタイルへ同じフレームに入れるかどうか」が index の順に依る（3 パス目は index の
昇順に歩くので、次のタイルの番号が大きければもう一歩進み、小さければ次のフレームになる）。
既定（1 フレーム 0.033 タイル）からは 30 倍離れているので F1 では起きないが、
気づいた点（§6）に書いた。

## 6. 気づいた点

仕事の範囲の外で気づいたことを、直さずに書く（`implementer.md` の報告の形式 6）。
本体が計画書 §7 へ写す。

1. **`map_tiles` の下限 `8` に出どころが無い。** `factory/src/main.rs:229` の
   `.max(8.0)`。F1 が置いた下限で、なぜ 8 なのかがどこにも無い。導くなら
   `4 × (ore_patch_radius + 1)`（= 既定で 16）で、これは「畑を地図の 4 象限の中心に半径ぶん置く」
   という `Ore::laid_out` の形から出る。既定の 32 では効かないので実害は無い。
   **属する先**: 埋め込みの数。`numbers.md` §9.4 に「不明」として載せた。F2 で導き直す候補。

2. **1 フレームに 1 タイル以上進むベルトでは、渡す順が walk の順に見える。**
   `belts.rs` の 3 パス目は先頭を 1 タイルずつしか渡さず、その pass を **index の昇順**に
   歩く。だから `.min(2.0)` まで進んだアイテムが「2 つ先のタイル」へ同じフレームに入れるかは、
   次のタイルの番号が自分より大きいかどうかで決まる。2 パス目は
   フレーム頭の尻尾の写しを見るので**順に依らない**のに、この 1 点だけが依る。
   既定は 1 フレーム 0.033 タイル（`belt_tiles_per_second` 2.0 ÷ 60）なので 30 倍の余裕があり、
   F1 では起きない。**属する先**: そのゲーム固有（将来 `belt_tiles_per_second` を
   大きくしたとき、または F2 以降でフレームが飛んだとき）。

3. **「隙間 N 個なら N+1 個」は f32 では成り立ったり成り立たなかったりする。**
   5.2 (1) の実測。`items_per_tile` が 3 のときだけ N 個になり、5 や 7 では N+1 個になる。
   分かれ目は「spacing が正確か」ではなく「`hold` の引き算の連鎖の丸めがどちらに転んだか」で、
   紙の上では決まらない。**属する先**: 本（mruby の移植の章）の素材になりそうなこと —
   「不変条件は保たれるが、そこから数えた個数は保たれない」という形の話。

4. **「0 以下の設定を断る」は共有 crate の口になりうる。** F1 は `main.rs` に
   `positive` / `counted` を書いた。速さ・時間・容量・個数を設定から読むゲームは 3 本とも
   同じことをしたくなるはずで、`games_shell::Settings` に `positive(key, default)` と
   `counted(key, default)` があれば、**算術の中の `.max(0.001)` が repo から消える**。
   箱庭と Battle にも同じ形の下限が残っていないか、移す前に見る価値がある。
   **属する先**: 共有 crate（`games-shell`）。

5. **「ドット絵のズームを整数倍に丸める」も共有 crate の口になりうる。**
   `draw::snap_zoom` / `snapped` はゲーム側に置いた（「どれだけ世界を見せるか」はカメラの話、
   「世界がドット絵である」はゲームの話、という切り方）。ただし**次に 2D のドット絵の
   ゲームを足したら 2 本目の同じコードになる**。`CameraControls` の 1 つのつまみ
   （`whole_pixel_zoom: Option<f32>` — 1 世界単位が素材の何 px か）にできる形。
   **属する先**: 共有 crate（`games_shell::camera`）。

6. **`--shot` と判定が同時に使えなかったのは 3 本に共通の形だった。** F1 は factory の
   `selftest` の中で「絵を頼まれている走行は終わらない」を足しただけで、
   `games_shell::checks::CHECKS_EXIT_WHEN_DONE` には触っていない。箱庭と Battle でも
   「判定が作った局面の写真」は撮りたいはずで、同じ 2 行がそちらにも要る。
   **属する先**: 共有 crate（`games-shell`）。計画書 §7 の 09-21 F0 の 3 行目と同じ話。

7. **`Moves` が list である理由が 1 つ消えた。** `belts.rs` の `Moves` の doc は
   「entities 側が順番を要るので list にした」と書いているが、その側は `778e99e` で消えた。
   今 list であることの取り分は「HUD が数えるだけでなく追える」という将来の話だけで、
   3 つの `u32` で足りる。**直していない**（F5 の HUD が何を要るかが決まってから）。
   **属する先**: そのゲーム固有。

8. **Docker が使えず、窓ありの走行が 1 つも確かめられなかった。** `docker info` が通らない。
   Docker Desktop は起動しない（CLAUDE.md）。**未実施**なのは、窓ありの判定 8 行（PC）と、
   判定が建てた工場の `--shot` 1 枚。ブラウザ側は Playwright で取れているので、
   「絵が出ること」の確認はブラウザの画素で代えてある。

9. **F2 へ渡す注意。** (a) `Rules` の 6 件は `ruby/data.rb` へ移す予定で、**移す側が
   「全部 0 より大きい」を保証する**（`Rules` の rustdoc にそう書いた。Ruby から 0 が来ると
   `spacing` が `inf` になる）。(b) 計画書 §0 のとおり、F2 の最初に sabiruby の rev を上げる
   （`pages.yml` が lock から rev を grep する）。(c) `--stress` と `Stress` は計測の器として
   残してある。(d) `map_tiles` は F1 では決められなかったので、F3 の計測まで 32 のまま。

# G9 — `P` で世界ごと止める / VM パネルを人向けに（2026-09-17）

計画書 `docs/plans/garden-plan.md` の G9。著者の指摘は 2 行だった —
**「VM パネルは一時停止しないと追えない」**、**「`P` で世界は止まるのか？」**。
答えは「止まらない」で、それが G4 から 5 段階そのままだった。以下、読んだ場所・試したこと・測ったこと・
捨てたことを順に書く。間引き（throttle）と 1 フレーム実行は**著者判断で不要**。

## 1. 「`P` は何を止めていたのか」を先に読む

`garden/src/window.rs:inspect_keys` は `ScriptWorld::budget` を 0 にするだけだった。
rubevy の `docs/host-api.md` の通り、予算 0 はスケジューラの時計も止める（`fa37eaa`）ので
**VM の中は完全に止まる**。止まらないのは Rust 側で、`garden/src/main.rs` の規則の chain
（`day_night` → `move_creatures` → `separate` → `grow_plants` → `sprout_plants` → `get_hungry` →
`eat` → `startle` → `court` → `starve`）は毎フレーム走り続ける。つまり一時停止中の箱庭は

* 生き物が**最後に書いた `Velocity` で滑り続け**（`move_creatures` が積分する）、
* 腹が減り続け（`get_hungry`）、
* 昼夜が回り（`day_night`）、
* 長く止めれば**全部餓死する**（`starve`）

という世界だった。著者の 2 行はこれを言っている。

## 2. 止め方は「新しい仕組み」ではなく「もう在る run condition」

chain にはすでに `run_if(is_still)` が付いていた（G3。セーブを読み戻している間は世界を止める、が理由）。
`is_still` に `Paused` を足すだけで、`P` は **世界を止める既存の道**に乗る:

```rust
fn is_still(restoring: Option<Res<Restoring>>, paused: Option<Res<window::Paused>>) -> bool {
    restoring.is_none() && !paused.is_some_and(|p| p.on())
}
```

`Option<Res<Paused>>` なのは headless ビルドが `Paused` を挿さないから（キーボードが無い）。
「誰にも止められない世界は常に動く」を型で言っている。

**時計は別に止める必要があった。** `day_night` を止めれば `sky.phase` は動かないが、
再開した瞬間に `world_now = time.elapsed_secs() + sky.shift` が一時停止の分だけ飛ぶ。
`restore_memory` が同じ問題を `sky.shift = restoring.tick - time.elapsed_secs()` で解いていたので、
差分の形で書いた:

```rust
fn hold_the_clock(time: Res<Time>, mut sky: ResMut<Sky>) { sky.shift -= time.delta_secs(); }
```

**これが「取りこぼさない」の答えでもある。** 計画書は「再開時に `"night"`/`"day"` を取りこぼさないこと
（時計が止まるので自然に満たされるはず — 確認する）」と書いていた。確認した通りで、
`"night"`/`"day"` を publish するのは `day_night` が位相をまたいだ瞬間だけであり、
**動かない時計はまたげない**。止めている間に publish されるイベントは 1 つも無く、
止める前にキューに入ったものはキューに残る（スクリプトが予算 0 で pop できないだけ）。

**繁殖のクールダウンだけは時計を差し替えた。** `Breeding::ready_at` は `court` と `hatch` が
`time.elapsed_secs()` と比べていた。ここだけ `world_now(&time, &sky)` にした
（`shift` が 0 の普通の実行では同じ数なので、挙動は変わらない）。しなければ、
1 分止めた後の最初のフレームで庭中のつがいが一斉に「待ち時間終了」になる。
`Eating { until }` は**あえて触っていない**: 0.35 秒の咀嚼アニメは見た目で、
それを読む `animate_creatures` は描画側（止まらない）なので、片方だけ世界時計にすると `--at midnight` で壊れる。

## 3. Battle 側は「時計」が本体だった

`sabibots/src/main.rs` の chain は 1 本（`restart_match` … `update_hud`）。
`world_moves` を **5 つのシステムにだけ**付けた（`answer_requests`・`move_robots`・`separate_robots`・
`move_bullets`・`fade_blasts`）。chain の順序は 1 つも動かしていない —
コメントにある通り「`answer_requests` が設定した操作を `move_robots` が同じフレームで適用する」順序は
ゲームの意味そのものなので、グループに括り直すより条件を 1 つずつ吊るす方が安全だと判断した。

**試合の時計 `WorldClock` を足した。** `Rubevy.ask("clock")` は `time.elapsed_secs()` を返していて、
`match_prelude.rb` の `rule(:sudden_death, after: 20, every: 2.0)` はそれと開始時刻を比べている。
止まっている間に時計が進むと、再開後に**取りこぼした回数ぶんの `shrink` が連続で走る**（0.2 秒ごとに 1 枚ずつ壁が寄る）。
`status` と `radar` の `time` も同じ数にした: ロボットに渡す「今」は、そのロボットが戦っている試合の今であるべきだから。

`gray_out_downed` は止めていない。hp が 0 になるのは `move_bullets` の中だけで、それが止まっている間は
新しく倒れようがないから、条件を足しても増える保証は無く、見た目の仕事（灰色のハル）だけが残る。

## 4. 判定（selftest）は 0.5 秒 → 2 秒、そして「VM の数」から「世界の数」へ

窓の判定は G4 から「予算が 0 になったか」「命令数が増えていないか」しか見ていなかった。G9 で 3 本足した:

```
ok   2 s paused: every creature is where it was
ok   2 s paused: nobody got hungrier
ok   2 s paused: the day did not turn
```

比較は**厳密な等値**（`Vec<(Entity, Vec3)>` と `Vec<(Entity, f32)>` と `f32`）。走らない規則は 1 バイトも書かないので、
許容誤差を置く理由が無い。2 秒なのは、動いていれば確実に見える長さだから（生き物は約 4 単位歩き、
メーターは 1 割落ち、1 日は 1/30 回る）。

**1 本だけ書き直した。** 最初は再開側を「メーターの合計が減る」にして **FAIL した**:

```
selftest: FAIL the meters fall again
```

草を食べている生き物はメーターが**増える**し、子が生まれれば合計も増える。
0.5 秒の窓では庭全体はどちらにも転ぶ。見たいのは「`get_hungry` と `eat` がまた走っていること」なので、
**同じ entity のメーターが変わったか**に変えた（`the meters move again`）。位置も同じ理由で
「誰かが歩いた」にしてある — 夜の生き物もハンドラに操作を預けた生き物も、その場に居てよい。

Battle 側も同じ 2 本（`every robot is where it was` / `the match's clock did not move`）。

## 5. VM パネル: 上半分を人向けに

G4 のパネルは開くと「レジスタ・ヒープ・context 数・全フレーム」だった。
`(no debug info)` / `prelude.rb:47` / `beetle.rb:118` という並びは**デバッガの窓**で、
開いた人が最初に知りたい 1 文ではない。上から

1. 名前（+ 世界が動いているか）、
2. **待っている理由**（1 文）、
3. **自分のファイルの行だけ**、
4. insn/frame・タスク数・VM の時間

に並べ替え、レジスタ・ヒープ・context・全フレームは `CollapsingHeader`（既定で閉じる）に落とした。
既定で**閉じて**開く（`F2`、`--shot` は `--vm` のときだけ）。

### 5a. 「待っている理由」はどう出しているか

パネルは Ruby を走らせない（`Vm::snapshot` は Rust で値を描くだけ）ので、タスクに「今なぜ止まっているか」を
**聞く手段が無い**。`Task#status` は Ruby のメソッドで、しかも `show_vm` が持っているのは `Res<ScriptWorld>`（不変）だ。
そこで **フレームから当てる**ことにし、当てられる根拠を先に測った。

計測は捨て道具を 1 つ足した（`GARDEN_DUMP_CONTEXTS`、コミットには入れていない）。
`stop_when_over` で `world.vm.snapshot(6)` の**全 context**について、内側から 4 フレームぶんの
`mid@target_class line pc` を出す。`--headless 20` の出力から:

```
ctx   1 Suspended | run@#<Class:0xb940> line Some(591) | loop@Kernel line None | run@… line Some(562) | run_creature@Object
ctx  11 Suspended | pop@Task::Queue line None | pop@Rubevy::Subscription line None | (block)@Object line Some(448) | loop@Kernel
ctx   3 Suspended | pop@Task::Queue line None | get@Rubevy::Entity line None | []@Rubevy::Entity line None | hunger@Creature line Some(138)
```

読めたことは 3 つ:

* **`Task::Queue#pop` は Ruby（mrblib）**なので、キューで待っているタスクには必ず `pop` のフレームが在る。
* **その 1 つ外のフレームが「どのキューか」を言っている。** `Rubevy.subscribe` が配るキューは
  `Rubevy::Subscription` で `extend` されている（rubevy `src/prelude.rb`）ので `pop@Rubevy::Subscription` が挟まる。
  コンポーネント読みは `get@Rubevy::Entity`、`garden.nearest` は `method_missing@Rubevy::Proxy`。
  **クラス名は VM が報告する事実**で、描画された文字列（`#<Task 12 ctx=3>`）を parse するのとは違う。
* **`sleep` はネイティブでフレームを積まない**（sabiruby の `call_native` は ci を push しない）。
  だから「`pop` が無い」＝「キューで待っていない」＝ ほぼ `sleep` で、その行は `sleep` を呼んだ行そのものになる。

名前も取れる。レジスタは内側 6 フレームまで載っている（`REGS_FRAMES`）ので、
`get` の `name` が `:Hunger`、`method_missing` の `name` と `args` が `:nearest` と `[:Plant]`。
最初、Proxy の側を `name` そのまま出して `` `:nearest(:Plant)` `` になった（単体テストが落ちた）。
Symbol の描画は `:nearest` で、著者が書いたのは `nearest` なので、先頭の `:` だけ落としている。

**当てられない場合を隠さない。** タイムスライスを使い切って「実行可能だがまだ走っていない」タスクは、
ここからは `sleep` と**見分けが付かない**。パネルのホバーと `Waiting` の doc にそう書いた。
このゲームの Ruby では `sleep` と `pop` 以外にタスクを止める道が無いので実害は小さいが、
`rubevy-arena` はライブラリなので、言わずに済ませてはいけない。

もう 1 つ。**イベント待ち（`on(:…)`）は、パネルが追っている本体タスクには普通は現れない。**
パネルが見るのは entity の `ScriptTask`＝行動アルゴリズムのタスクで、ハンドラは別タスクだからだ。
`Waiting::Event` は「自分の `run` が自分で `Rubevy.subscribe(...).pop` したとき」に出る。
どのイベントかは**言えない**（`event` はタスクを作ったブロックのローカルで、そのタスクのスタックには無い）。
これも doc とホバーに書いた。

### 5b. 単体テストを 6 本足した

4 種のうち 2 種（イベント・Proxy 経由の質問）は**実行中に捕まえにくい**。
`--headless` を 9 本走らせて出たのは `component read` と `sleeping` だけで、`nearest` の瞬間は 1 パスに 1 フレームしかない。
上の dump で読んだフレームの形をそのまま `#[cfg(test)]` に写し、`why()` に食わせている（7 passed）。
**捨て道具の出力が、そのままテストの入力になった。**

### 5c. `VmClock` が `rubevy-arena` に移った

`VM 1.30 / 8.0 ms` は G4 で箱庭の `window.rs` に書かれていたが、それを見せるのは VM パネルで、
パネルは両ゲームのものだ。`VmInspectorPlugin` が測るようにして、窓のない箱庭（`--headless`）だけが
自分で 2 つのシステムを足す。Battle は 1 行も書かずに同じ数を得た。

**insn/frame は 2 通り持っている。** 箱庭は HUD と同じ生涯平均を渡す。Battle は平均を持っていないので、
パネルが自分で数える（開いている間の差分を 0.95/0.05 で平滑化）。最初これを入れ忘れて、
`docs/vm-inspector.png` の 1 枚目が `0 insn/frame` になった（パークしたタスクの「直前フレームの消費」は 0）。
撮り直して `202 insn/frame`、スコアボードの `thinking` 列（198）と同じ桁で、辻褄は合っている。

## 9. 迷った点・やっていないこと

* **`P` で VM パネルを開かなくした。** G4 では `P` が押されるとパネルが開いた（一時停止はパネルのためだったから）。
  G9 で一時停止は世界のものになり、パネルは既定で閉じるので、両方を残すと「止めると勝手にデバッガが出る」になる。
  計画書は明示していない。判断して外し、判定に `the VM panel starts closed` / `F2 opens it` を足した。
* **`Eating { until }` と `starve` のログの時刻は process の時計のまま**（§2）。
* **甲虫 3 枚は撮り直していない**（§6）。
* **タスク数は VM 全体の数**（context の生存数）。「この生き物のタスク数」は Rust 側が知らない
  （箱庭はハンドラ数を持っていない。Battle は `handler` の ask で知っている）。計画書の「タスク数」は
  パネルの数字なので VM 全体で埋めたが、生き物ごとにしたければ箱庭側に数を持たせる必要がある。
